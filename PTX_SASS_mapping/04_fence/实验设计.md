# Fence/Barrier 族实验设计

> 适用范围：PTX ISA 9.0、NVIDIA Thor、`sm_110a`、CUDA 13.0（ptxas V13.0.88、nvdisasm V13.0.85）
> 本文性质：实验设计裁决 + 首轮校准记录。文中"实测"来自本机会话 scratchpad（`fence_probe/`）内约 90 个孤立探针 kernel 的 O0/O3 编译反汇编，以及已建成的两个套件（`fence/thor_ptx90` 16 syntax + 29 expanded、`membar/thor_ptx90` 3 syntax + 11 expanded）的 O0–O3 全量自检。每张映射表、每条合法面结论都来自这些编译产物，不来自规范阅读；规范阅读得出的预期若与实测冲突，以实测为准并在文中标出（对应 `建族套件指南.md` 的 P0-2 证伪记录要求）。
> 设计基线：`01_tcgen05` 的静态实验分层（A/B/C/D 结构分类 + syntax/expanded/negative + O0–O3 + 归属 + 规则挖掘）与 `02_tma/实验设计.md` 的文档结构，逐条吸收 `01_tcgen05/对抗式审查_实验设计缺口.md` 的 P0/P1 结论。

## 结论

Fence/barrier 族 10 个目录里，没有一个是 tcgen05 意义上干净的"1 条 PTX → 1 条 SASS"直译。**一对多固定序列 lowering 是本族常态**：多数合法组合展开成 1–4 条 SASS 的确定序列，序列长度由 modifier 组合决定，不由周边上下文决定（在已测配置内）。除此之外还出现了 tcgen05 分类法里没有的两种结构：

1. **D 类零指令**（沿用 tcgen05 记法）：`fence.acquire.cta` 与 `fence.mbarrier_init.release.cluster` 编译后不产生任何可归属指令，只留一条 `NOP` 占位；观测量必须换成相邻指令的控制字，不能用"是否出现某条 SASS"。
2. **R 类运行时构型条件 lowering**（本族新增，tcgen05 的 A/B/C/D 四类都不能贴切描述）：`fence.proxy.alias`、`barrier.cluster.arrive`、`barrier.cluster.wait` 编译后不是一条固定序列，而是一段**由编译器插入的运行时分支**——从常量库读一个位（`LDCU`/`LDCU.64` + 位提取 + `UISETP`/`ULOP3.LUT` 产生 uniform predicate `UP0`），再 `BRA.U` 到两条完全不同的指令序列之一。这个谓词无法在编译期折叠：即使显式声明 `.reqnctapercluster N`，分支依然存在。`barrier.cluster.wait` 的假分支（cluster 未激活）直接退化成 CTA 内 `BAR.SYNC.DEFER_BLOCKING 0x0`——与 `bar.sync 0` 逐位相同，这是 fence 族与 barrier 族在 SASS 层的一条真实交汇点，不是巧合。R 类比 tcgen05 的 B 类（`alloc` 那种自旋循环+影子状态+trap stub）更简单，但同样不能套用"opcode+qualifier→助记符+修饰符"模板：产出是候选序列而非单一序列，必须记录"谓词来源 + 真分支 + 假分支"三元组。

| 类别 | 目录 | PTX→SASS 结构 |
|---|---|---|
| A 一对多固定序列 | `fence`（除 D 类坐标外）、`membar`、`fence.proxy.async`、`fence.proxy.tensormap` | modifier 组合 → 长度 1–4 的确定 SASS 序列，序列不随已测的周边访存上下文变化 |
| A 单指令直译（含操作数打包） | `bar.arrive`、`bar.sync` | 1 条 PTX → 1 条 SASS；两个操作数都是寄存器时，先出现 2 条打包指令（`SHF.L`+`LOP3.LUT`）把 barrier id 和 count 拼进一个 32-bit 寄存器 |
| D 零指令 | `fence`（仅 `acquire.cta` 坐标）、`fence.mbarrier_init` | 0 条可归属指令，效应在相邻指令控制字 |
| R 运行时构型条件 | `fence.proxy.alias`、`barrier.cluster.arrive`、`barrier.cluster.wait` | 编译器插入常量库谓词判断 + 双分支，各分支持有独立的固定序列 |

## 实测助记符总表

### `fence` / `membar`

`fence.{sem}.{scope}` 实测合法 sem 为**四个**：`sc`、`acq_rel`、`acquire`、`release`——多数资料只强调 `sc`/`acq_rel` 组合，`acquire`/`release` 单独使用是否合法需要实测确认，结果是合法，且各自产生独立的、非平凡的 SASS。scope 为 `cta`/`cluster`/`gpu`/`sys`，4×4=16 种组合全部编译通过。

| sem | scope=cta | scope=cluster | scope=gpu | scope=sys |
|---|---|---|---|---|
| `sc` | `MEMBAR.SC.CTA` | `MEMBAR.SC.GPU`+`ERRBAR`+`CGAERRBAR`+`CCTL.IVALL` | 同 cluster（逐位相同） | `MEMBAR.SC.SYS`+`ERRBAR`+`CGAERRBAR`+`CCTL.IVALL` |
| `acq_rel` | `MEMBAR.ALL.CTA` | `MEMBAR.ALL.GPU`+`ERRBAR`+`CGAERRBAR`+`CCTL.IVALL` | 同 cluster | `MEMBAR.ALL.SYS`+`ERRBAR`+`CGAERRBAR`+`CCTL.IVALL` |
| `acquire` | **0 条指令（D 类）** | `CCTL.IVALL` | 同 cluster | 同 cluster（scope 完全不影响 acquire 的编码） |
| `release` | `MEMBAR.ALL.CTA` | `MEMBAR.ALL.GPU`+`ERRBAR`+`CGAERRBAR`（**无** `CCTL.IVALL`） | 同 cluster | `MEMBAR.ALL.SYS`+`ERRBAR`+`CGAERRBAR` |

可分解为一条组合规律（已用 `release.gpu` 紧跟 `acquire.gpu` 双指令拼接实测验证：拼接结果与单条 `acq_rel.gpu` 逐位相同，4 条指令一一对应，无冗余无缺失）：

- **release 部分**贡献 `MEMBAR.{SC 或 ALL}.<scope>`，scope>cta 时再加 `ERRBAR`+`CGAERRBAR`；MEMBAR 变体由 sem 决定（`sc`→`SC`，`acq_rel`/`release`→`ALL`）。
- **acquire 部分**贡献 `CCTL.IVALL`；cta scope 下为空。
- `sc.<scope>` = SC 变体 release 部分 + acquire 部分；`acq_rel.<scope>` = ALL 变体 release 部分 + acquire 部分；`acquire.<scope>`/`release.<scope>` 是各自的裸部分。

省略 sem 的简写 `fence.<scope>;` 合法，且与 `fence.acq_rel.<scope>;` 逐位相同——**默认 sem 是 `acq_rel`，不是 `sc`**，这是按直觉最容易猜错的一点（"没写强度限定符应该退到最强的顺序一致"是错的假设，已被实测推翻）。

`membar` 是 `fence.sc.*` 的严格子集，只有三档传统 level，**没有 `cluster`**，也**没有 `gpu` 拼写**（`gpu` 是 `fence` 独有的新记号，`membar.gpu` 语法拒绝）：

| PTX | SASS | 与 fence 的关系 |
|---|---|---|
| `membar.cta` | `MEMBAR.SC.CTA` | 与 `fence.sc.cta` 逐位相同 |
| `membar.gl` | `MEMBAR.SC.GPU`+`ERRBAR`+`CGAERRBAR`+`CCTL.IVALL` | 与 `fence.sc.gpu`/`fence.sc.cluster` 逐位相同 |
| `membar.sys` | `MEMBAR.SC.SYS`+`ERRBAR`+`CGAERRBAR`+`CCTL.IVALL` | 与 `fence.sc.sys` 逐位相同 |

双 fence/membar 相邻**不合并不去重**：两条相同 `fence.sc.gpu` 相邻，编译产物是 8 条指令（两份完整序列首尾相接）；`fence.sc.cta` 后接 `fence.sc.gpu`，产物是 5 条（1+4，无交互）。guard 谓词 `@%p` 落到 `@P0 BRA` 分支，fence 序列整体位于真分支内，不被拆散。

### `fence.proxy.async`

| PTX | SASS |
|---|---|
| `fence.proxy.async`（裸/generic） | `MEMBAR.ALL.GPU`+`FENCE.VIEW.ASYNC.S` — **与 `.shared::cluster` 逐位相同** |
| `fence.proxy.async.global` | `FENCE.VIEW.ASYNC.G`（无 `MEMBAR`） |
| `fence.proxy.async.shared::cta` | `MEMBAR.ALL.CTA`+`FENCE.VIEW.ASYNC.S` |
| `fence.proxy.async.shared::cluster` | `MEMBAR.ALL.GPU`+`FENCE.VIEW.ASYNC.S` |
| `.local` 等非法 state space | 语法拒绝（"State space incorrect for instruction 'fence.proxy'"） |

裸形态与 `.shared::cluster` 的坍缩是本族第二处 scope/space 别名（第一处是 `fence`/`membar` 的 `cluster`≡`gpu`）：generic proxy fence 的隐含语义边界恰好落在 cluster 粒度，而不是 CTA 粒度。

### `fence.proxy.alias`（R 类）

唯一合法形态是裸 `fence.proxy.alias;`（带操作数语法拒绝，"Arguments mismatch"）。lowering 不是固定序列：

```
LDCU UR79, c[0x0][0x2d8]         // 读一个 launch-config 位
UP2UR.B3 UR79, UPR, UR79, 0xff
ULOP3.LUT UP0, ..., 0xc0, !UPT   // UP0 = 该位
BRA.U !UP0, L0
  MEMBAR.SC.GPU                  // 真分支
L0:
BRA.U UP0, L1
  MEMBAR.SC.SYS                  // 假分支
L1:
CCTL.IVALL                        // 两条分支共有
UR2UP UPR, UR79.B3                // 恢复隐藏谓词寄存器
```

即：按某个编译期无法判定的条件，在 `MEMBAR.SC.GPU` 与 `MEMBAR.SC.SYS` 之间二选一，随后统一 `CCTL.IVALL`。这与 P2P/UVA 场景下"该分配是否需要系统级可见性"的运行时判定吻合，但本套件的裁决口径下不做语义解释，只记录分支结构本身是静态可归属的事实。

### `fence.proxy.tensormap`

| PTX | SASS |
|---|---|
| `fence.proxy.tensormap::generic.release.cta` | `MEMBAR.ALL.GPU`+`ERRBAR`+`CGAERRBAR` |
| `.release.cluster` | 同 `.release.cta`（逐位相同——**release 侧 cta/cluster/gpu 三档全部坍缩到 GPU 级**） |
| `.release.gpu` | 同上 |
| `.release.sys` | `MEMBAR.ALL.SYS`+`ERRBAR`+`CGAERRBAR` |
| `fence.proxy.tensormap::generic.acquire.{cta,cluster,gpu,sys} [addr], 128` | 四档**逐位相同**：`LDCU.64`+`DEPBAR {5,4,3,2,1,0}`+`CCTL.E.C.LDCU.IV.DEEP [UR]`+`UTMACCTL.IV [UR]`——scope 修饰符完全不进编码 |
| acquire size ≠ 128（立即数） | 语法拒绝："unexpected value 'N', expected to be 128" |
| acquire size 为寄存器 | 语法拒绝（"Arguments mismatch"） |
| release 带地址操作数 / acquire 缺 size 操作数 | 语法拒绝（"Arguments mismatch"） |

`release` 的三档坍缩比 `fence`/`membar` 更激进（cta 也并入 GPU 级，不像 `fence.release.cta` 单独保留 `MEMBAR.ALL.CTA`）；`acquire` 的四档坍缩更是把 scope 修饰符从编码里完全抹除——这是本族里 scope 参数对 SASS 影响最弱的一条指令，逆向时四个 scope 候选无法从指令文本区分，只能作为候选集合登记。

### `fence.mbarrier_init`（D 类）

唯一合法形态是 `fence.mbarrier_init.release.cluster;`；`.cta`/`.gpu`/`.sys` 与 `.acquire`/`.sc`/`.acq_rel` 全部语法拒绝（"Modifier '.mbarrier_init' cannot be combined with modifier '.xxx'"）。编译产物是 0 条可归属指令（仅 `NOP` 占位），O0/O3 一致。

### `barrier.cluster.arrive` / `barrier.cluster.wait`（R 类）

真分支 = 谓词为真（cluster 已激活）时执行的序列；假分支 = 谓词为假（单 CTA 集群，退化）时执行的序列。

| PTX | 真分支 | 假分支 |
|---|---|---|
| `barrier.cluster.arrive`（裸）/`.release`/`.aligned`/`.release.aligned` | `MEMBAR.ALL.GPU`+`ERRBAR`+`CGAERRBAR`+`UCGABAR_ARV` | `NOP` |
| `barrier.cluster.arrive.relaxed`/`.relaxed.aligned` | `UCGABAR_ARV` | `NOP` |
| `barrier.cluster.wait`（裸）/`.acquire`/`.aligned`/`.acquire.aligned` | `UCGABAR_WAIT`+`CCTL.IVALL` | **`BAR.SYNC.DEFER_BLOCKING 0x0`** |

四种拼写（裸 / 显式 sem / `.aligned` / 显式 sem+`.aligned`）在 arrive 侧两两归并成两组、在 wait 侧全部归并成一组：`.aligned` 不改变 SASS 形状；裸 arrive 的默认 sem 是 `release`，裸 wait 的默认 sem 是 `acquire`。谓词来源 `LDCU UR4, c[0x0][0x36c]` + `UISETP.EQ.U32.AND` 即使在声明 `.reqnctapercluster N` 时依然出现——`.reqnctapercluster` 只是元数据校验，不会让 ptxas 把分支折叠掉。`.acquire` 用在 arrive 上、`.release` 用在 wait 上均语法拒绝（"Illegal modifier '.acquire' for instruction 'barrier.cluster.arrive'" / 同理 wait/`.release`）；两者带操作数均 "Arguments mismatch"。

`barrier.cluster.wait` 假分支退化为 `BAR.SYNC.DEFER_BLOCKING 0x0`，与 `bar.sync 0` 的实测映射逐位相同——这是族内两个不同目录在 SASS 层的真实交汇，值得在 `barrier.cluster.wait` 的套件里显式与 `bar.sync/thor_ptx90` 做交叉核对（详见"各指令研究重点"）。

### `bar.arrive` / `bar.sync`

| PTX | SASS |
|---|---|
| `bar.sync imm` | `BAR.SYNC.DEFER_BLOCKING 0x..`（单操作数，count 隐含为全部线程） |
| `bar.sync imm, imm` | `BAR.SYNC.DEFER_BLOCKING 0x.., 0x..` |
| `bar.sync %r`（寄存器 id，无 count） | `BAR.SYNC.DEFER_BLOCKING R` |
| `bar.sync %r, %r`（寄存器 id + count） | 先 `SHF.L.U32`+`LOP3.LUT` 把两个 32-bit 值打包进一个寄存器，再 `BAR.SYNC.DEFER_BLOCKING R, R` |
| `bar.arrive imm, imm` | `BAR.ARV 0x.., 0x..`（**`bar.arrive` 必须带两个操作数**，只给 barrier id 是 "Arguments mismatch"） |
| `bar.arrive %r, %r` | 同 `bar.sync` 的寄存器打包模式，`BAR.ARV R, R` |

编译期边界检查：barrier id 立即数超出 `[0..15]` 直接语法拒绝（"Barrier number 'N' out of range, expected to be in range [0..15]"）；thread count 立即数不是 warp size（32）整数倍同样语法拒绝（"Number of threads participating in barrier must be in multiple of warp size"）——这两条检查是编译期静态完成的，不是留给运行时。

## 合法面实测（贯穿全族的诊断锚点）

| 探针 | 诊断 |
|---|---|
| `fence` 缺 scope（裸 `fence;` 或 `fence.acq_rel;`） | "Scope modifier required for instruction 'fence'" / "Modifier '.acq_rel' requires scope with 'fence' instruction" |
| `fence.sc.warp`（不存在的 scope token） | "Unknown modifier '.warp'" |
| `fence.sc.cta %r0`（fence 带操作数） | "Arguments mismatch for instruction 'fence'" |
| `fence.relaxed.cta` / `fence.weak.cta`（非 fence 的 sem 词汇） | "Illegal modifier '.relaxed'/'.weak' for instruction 'fence'" |
| `fence.sc.cta.aligned`（`.aligned` 借用自 barrier.cluster） | "Illegal modifier '.aligned' for instruction 'fence'" |
| `fence.acquire.release.cta`（双 sem 词） | "Duplicate .release modifier" |
| `fence.sc.cta.sc.cta`（双 scope 词） | "Duplicate .sc modifier" / "Multiple scope modifiers specified" |
| `membar` 缺 level / 带操作数 / `.cluster` / `.gpu` / `.sc.cta` | 各自独立诊断（"Membar level required" / "Arguments mismatch" / "Illegal modifier '.cluster'" / "Illegal modifier '.gpu'" / "Illegal modifier '.sc'"） |
| `fence.proxy.async.local`（非法 state space） | "State space incorrect for instruction 'fence.proxy'" |
| `fence.proxy.alias` 带操作数 | "Arguments mismatch for instruction 'fence.proxy'" |
| `fence.mbarrier_init.release.{cta,gpu,sys}` / `.acquire.cluster` | "Modifier '.mbarrier_init' cannot be combined with modifier '.xxx'" |
| `fence.proxy.tensormap::generic.acquire` size≠128（立即数）/ size 为寄存器 / release 带操作数 / acquire 缺 size | 各自独立诊断（"unexpected value 'N', expected to be 128" / "Arguments mismatch" ×3） |
| `barrier.cluster.arrive.acquire` / `barrier.cluster.wait.release` | "Illegal modifier '.acquire' for instruction 'barrier.cluster.arrive'" / "Illegal modifier '.release' for instruction 'barrier.cluster.wait'" |
| `barrier.cluster.arrive`/`.wait` 带操作数 | "Arguments mismatch for instruction 'barrier.cluster.arrive'"（wait 同理） |
| `bar.sync 16`（越界 barrier id） | "Barrier number '16' out of range, expected to be in range [0..15]" |
| `bar.sync 0, 33`（count 非 warp size 整数倍） | "Number of threads participating in barrier must be in multiple of warp size" |
| `bar.arrive 0`（缺 count 操作数） | "Arguments mismatch for instruction 'bar.arrive'" |

三个被校准推翻或补全的假设，均已写进套件正向矩阵而非当作负向：

1. `fence` 的合法 sem 集合是四个（`sc`/`acq_rel`/`acquire`/`release`），不是常见资料强调的两个；`acquire`/`release` 单独使用合法且产生独立 SASS。
2. 省略 sem 的 `fence.<scope>;` 合法，默认等价于 `acq_rel`，不是更符合直觉的 `sc`。
3. `fence.sc.cta` 本身合法（任务交底里特别要求核实的一点）：单条 `MEMBAR.SC.CTA`，不需要任何 `CCTL`/`ERRBAR` 伴随。

## 对抗式审查缺口在本族的落实

| tcgen05 缺口 | 本族对应设计 |
|---|---|
| P0-1 控制位是全局资源 | `fence`/`membar` 两个套件的 expanded 均含 `inflight_depth_{2,4}`（前置独立 load 条数）；已测配置下未观测到目标指令编码字变化（`ctxA`/`ctxB` 对照，word1 逐位相同）——这是一条有意义的负向结果：fence 自身控制字对简单的前置访存深度不敏感，与 tcgen05 async scoreboard 字段随深度变化形成对照，留作待更复杂上下文（跨基本块、多 warp 竞争）复测的基线 |
| P0-2 合法面未证伪 | 全部负向探针登记 `expected_diagnostic` 子串；`fence`/`membar` 两套件各含 ≥2 条补集抽样（重复 sem/scope 词、`.aligned` 借用、fence 带操作数等）；已发现三条"预期外合法"（见上节）并入正向矩阵 |
| P0-3 组合/序列不足 | 双 fence/membar 相邻的合并/去重观察已入两套件的 expanded（同 scope、不同 scope 两种组合均确认不合并）；`release`+`acquire` 互补对的拼接实验直接验证了 P0-1 式"控制位/序列是编译单元"论点的反面证据——这里序列可以安全拆分复用（互补对拼接结果与对应单条 `acq_rel` 逐位相同），与 tcgen05 `probe:splice` 的"序列不可拆分复用"结论形成鲜明对照，值得作为反例保留 |
| P1-1 模板未受控 | 两套件的 expanded 均含 `template_wide`（加宽 kernel 参数签名）case |
| P1-2 重物化前提 | 不适用：`fence`/`membar`/`fence.proxy.alias`/`barrier.cluster.*` 均无操作数，没有"关键操作数"可做 indirect producer；`fence.proxy.tensormap::generic.acquire` 的地址操作数是本族唯一例外，留给该目录建套件时补 indirect producer case |
| P2-1 单版本 | 两套件与既有套件一样接受 `--ptxas`/`--nvdisasm` 路径参数，跨版本差分只需换工具链重跑 |

## 各指令研究重点

### `fence`（A/D 混合，套件已建，`FRAMEWORK_VALIDATED`）

1. 16 个 sem×scope 组合已全部校准；核心待办是把"release 部分 + acquire 部分"的组合规律从观测升级为可用于逆向的显式规则（已在 `analyze_mapping_rules.py` 产出的正向/逆向签名候选里体现，需要人工审阅签名分组是否与本文的组合规律一致）。
2. scope 坍缩（`cluster`≡`gpu`）目前只在 `fence`/`membar`/`fence.proxy.tensormap` 三处观测到，`fence.proxy.async` 的坍缩边界不同（裸≡`shared::cluster`，不是 cluster≡gpu）——需要在跨指令规则文档里分别登记，不能假设全族共用一条坍缩规则。
3. `inflight_depth` 轴目前只测了独立 global load 前置，还没测跨基本块、多路径汇合、与 tcgen05/TMA 异步操作混排的上下文；P0-1 的"控制位是全局资源"结论在 fence 自身上暂时是负向证据，不代表其他上下文同样成立。

### `membar`（A，套件已建，`FRAMEWORK_VALIDATED`）

1. 已证是 `fence.sc.*` 的严格子集，三档 level 全部逐位对应；后续若要生成逆向规则，应该把 `membar.*` 直接作为 `fence.sc.*` 的一个"别名分支"合并登记，而不是独立维护一份签名表。
2. `membar.gpu` 语法拒绝、`membar.gl` 才是合法拼写，这一点在生成器/校验器里必须写成硬编码常量表，不能从 `fence` 的 scope 词表派生（词表不共享）。

### `fence.proxy.async`（A，`DESIGNED`）

1. 四种形态已全部校准，`.global` 是唯一不产生 `MEMBAR` 的形态（只有 `FENCE.VIEW.ASYNC.G`）——需要确认这是否意味着 global 侧的可见性保证完全交给 L2 一致性，不需要 SM 内 drain。
2. 裸形态≡`.shared::cluster` 的坍缩需要与 `03_mbarrier`、`02_tma` 的 mbarrier 完成协议交叉验证：TMA load 的 PREPARATION 区已经有 `SYNCS.EXCH.64`，需要确认 `fence.proxy.async` 通常插在 TMA pipeline 的哪个位置，建套件时把这个上下文补进 expanded。
3. 待建套件的负向面：非 shared/global 的 state space（已测 `.local` 拒绝）、多余操作数、scope 相关 token 是否被接受（`fence.proxy.async` 本身没有 scope 轴，需要验证这一点而非假设）。

### `fence.proxy.alias`（R，`DESIGNED`）

1. 核心研究问题不是"SASS 是什么"（已确定：二选一 `MEMBAR.SC.GPU`/`MEMBAR.SC.SYS`+`CCTL.IVALL`），而是**谓词读的常量库偏移 `c[0x0][0x2d8]` 对应哪个 launch-time 属性**——本文不做解释，留给运行时验证边界（很可能与统一内存/多 GPU 可见性设置有关，需要 driver 层交叉验证，超出 `STATIC_ONLY`）。
2. 建套件时必须把"真分支序列"和"假分支序列"分别登记为两条归属记录，`target_patterns` 需要同时覆盖 `MEMBAR.SC.GPU`、`MEMBAR.SC.SYS`、`CCTL.IVALL`；不能假设某一分支必然出现，两条分支都要在 expanded 里通过某种方式强制可见（例如反汇编全函数而非只看第一条命中）。
3. 唯一合法语法只有裸 `fence.proxy.alias;`，语法轴几乎是空的——这个目录的"套件"价值主要在于把 R 类的分支结构固化为可回归的证据，而不是覆盖组合矩阵。

### `fence.proxy.tensormap`（A，`DESIGNED`）

1. `release` 的三档坍缩（cta/cluster/gpu→GPU 级）和 `acquire` 的四档坍缩（全部相同）需要作为核心发现写进套件文档；逆向签名会天然产生"候选集合"而非唯一映射，这是 `evidence_grade: CONDITIONAL` 该出现的地方。
2. size 操作数被硬编码为字面量 128（立即数，寄存器形态拒绝）——这是一个静态可验证但语义上奇怪的约束（"为什么必须恰好 128"),值得在文档里标注为"已证但未解释"。
3. 与 `02_tma` 的 tensormap 相关指令（`tensormap.replace` 等，若existing）有语义关联，需要交叉核对哪个目录持有 tensormap 内容修改后必须调用 acquire/release 的顺序约束——这属于运行时语义，本族只能证明"编译器为 acquire/release 生成了这些指令"，不能证明程序员真的按协议调用了它们。

### `fence.mbarrier_init`（D，`DESIGNED`）

1. 唯一合法形态零指令，观测量必须换成相邻指令控制字（同 tcgen05 `wait`/`fence::before_thread_sync` 的处理方式）；建套件时的核心 case 是"`mbarrier.init` 后紧跟 `fence.mbarrier_init.release.cluster` 再跟 `mbarrier.arrive`"的三段序列，比较有无该 fence 时相邻指令（尤其是 `mbarrier.init` lowering 出的 `SYNCS.EXCH.64`，规则由 `03_mbarrier` 持有）的控制字差异。
2. 只接受 `.release.cluster` 这一种拼写，语法轴几乎不需要正向枚举，负向面（4 个非法 scope × 2 个非法 sem 的代表性抽样）是这个目录的主要工作量。

### `barrier.cluster.arrive`（R，`DESIGNED`）

1. 已证 4 种拼写归并成 2 组 SASS（`release`/裸/`aligned`/`release.aligned` 一组，`relaxed`/`relaxed.aligned` 一组），且假分支恒为 `NOP`（不像 `wait` 那样退化成有实际效果的指令）。
2. 谓词来源 `c[0x0][0x36c]`（注意与 `fence.proxy.alias` 的 `c[0x0][0x2d8]` 是不同偏移，不是同一个隐藏状态）需要交叉确认是否与 `.reqnctapercluster` 声明的具体维度值有关——已排除的是"声明了就能静态折叠分支"，未排除的是"不同维度值是否影响谓词读取的具体常量库地址"。
3. 建套件时的关键组合轴：真分支序列本身要不要再细分 memory-context（`ERRBAR`/`CGAERRBAR` 前后是否有其他访存）——目前只做了孤立指令校准，还没做 P0-1 式的上下文轴。

### `barrier.cluster.wait`（R，`DESIGNED`）

1. 已证 4 种拼写归并成 1 组，假分支退化为 `BAR.SYNC.DEFER_BLOCKING 0x0`——**与 `bar.sync 0` 逐位相同**。建套件时必须把这条交叉关系做成显式回归：套件应该同时编译 `barrier.cluster.wait;` 与 `bar.sync 0;` 两个 kernel，断言假分支片段与后者的目标指令逐位相同,而不是只在文档里陈述。
2. `barrier.cluster.arrive` 与 `barrier.cluster.wait` 通常成对出现（split-phase barrier 的两半），P0-3 式的序列组合矩阵应该以"arrive 变体 × wait 变体 × 中间插入的计算量"为轴，而不是把两者当独立指令各自研究——这是本族里最接近 tcgen05 `alloc`→`mma`→`commit`→`dealloc` 生命周期矩阵的地方。

### `bar.arrive`（A，`DESIGNED`）

1. 已证必须带两个操作数（缺 count 语法拒绝），与 `bar.sync`（单操作数合法）形成不对称——这是容易在生成器里写错的边界，必须在负向面显式覆盖。
2. 寄存器双操作数的打包指令（`SHF.L.U32`+`LOP3.LUT`）是否总是恰好 2 条、打包位域是否稳定，需要用多个不同 id/count 寄存器组合复测确认（目前只有 1 个组合样本）。

### `bar.sync`（A，`DESIGNED`）

1. 已证四种操作数形态（0 操作数不合法、1 立即数、2 立即数、1 寄存器、2 寄存器）里，1 立即数和 1 寄存器都合法（`count` 隐含全部参与线程），这一点需要在语法矩阵里显式区分"省略 count"和"count 显式等于全部线程数"两种 case，二者的 SASS 是否相同待测。
2. barrier id 越界（>15）和 count 非 warp-size 整数倍在编译期就被拒绝——这两条编译期检查的具体阈值（15、32）应作为负向面的核心断言,不能只写"非法输入被拒绝"这种模糊描述。
3. `BAR.SYNC.DEFER_BLOCKING` 与 `barrier.cluster.wait` 假分支产出的指令逐位相同，两个目录的套件应该互相引用对方的归属证据，不重复建账（同 `02_tma` 里 mbarrier lowering 规则"由 `03_mbarrier` 持有,不重复登记"的处理方式）。

## STATIC_ONLY 边界声明

全部结论为 `STATIC_ONLY`：编译通过 + 归属成功只证明"编译器为给定 PTX 组合选择了哪些 SASS 指令、是否合并/坍缩/生成运行时分支"，不证明：

- `MEMBAR`/`CCTL.IVALL`/`ERRBAR`/`FENCE.VIEW.ASYNC.*` 在实机上真正产生了声称的可见性或顺序效应；
- `fence.proxy.alias`/`barrier.cluster.*` 里运行时分支所依赖的常量库位在实际 launch 配置下取何值；
- `bar.sync`/`bar.arrive`/`barrier.cluster.wait` 的参与线程计数在实机上确实按声明到齐。

族 README（[`README.md`](README.md)）的完成门槛写明："编译差分只产生候选约束；涉及可见性和顺序的结论必须关联 litmus 或其他允许结果 oracle。" 本文与两个已建套件严格停在"候选约束"这一步：litmus test（或其他运行时 oracle）属于运行时验证范围，是本文与套件的显式边界外事项，不在 `FRAMEWORK_VALIDATED` 状态的证明范围内，也不是把族状态推进到族 README 所定义的 `VALIDATED` 的充分条件。跨版本重跑：两个套件都接受 `--ptxas`/`--nvdisasm` 路径参数，换 CUDA release 或换架构（如 `sm_100a`）只需重新指向对应工具链;跨版本/跨架构差分目前是待办事项,不是已交付证据。

# Quantization 族实验设计

> 适用范围：PTX ISA 9.0、NVIDIA Thor、`sm_110a`、CUDA 13.0（ptxas V13.0.88、nvdisasm V13.0.85）
> 本文性质：实验设计裁决 + 首轮校准记录。文中"实测"来自本机 scratchpad 校准探针（`dp4a`/`dp2a`/`cvt.pack`/`cvt.e4m3x2`/`cvt.e5m2x2` 各若干条，O0/O3 编译反汇编）与已建成套件（`dp4a/thor_ptx90/`，14 syntax + 26 expanded case，O0–O3 全量自检）的运行结果；规范阅读得出的预期与实测冲突之处一律标注为证伪记录，不采信规范推断。
> 设计基线：`01_tcgen05` 的静态实验分层（syntax/expanded/negative/O0–O3/归属/规则挖掘）与 `02_tma/实验设计.md` 的文档结构，逐条吸收 `01_tcgen05/对抗式审查_实验设计缺口.md` 的 P0/P1 结论；流程与检查单见 `00_shared/templates/建族套件指南.md`。

## 结论

Quantization 族 5 个 opcode 全部落在 tcgen05 分类法的 **A 类单指令直译**，且全部是纯 ALU/数据格式指令——没有 mbarrier、没有 scoreboard、没有异步完成协议，因此 TMA 族的 P0-1（调度控制位是全局资源）在本族**不成立**：`dp4a`/`dp2a` 的合法/负向探针中，guard 谓词从未让目标指令本身消失或改变编码，只在其后插入 `SEL`。本族真正的结构风险集中在 **P0-2（合法面未证伪）**：两处规范阅读的直觉预期被实测直接推翻（见下）。

一条形态学备注：`cvt.pack` 的 s8/u8 目的类型强制要求 4 操作数"链式"语法（`d, a, b, c`，`c` 是待合并的高两字节来源），FP8 pack 转换（`F2FP`）在 SASS 层同样带一个 PTX 语法未暴露的第三源操作数（`MERGE_C`，恒为 `RZ`）——两者形态上呼应但不是同一机制，未经进一步探针不应合并成一条规则（已在下文分别记录，不做归并声明）。

| 类别 | 指令 | PTX→SASS 结构 |
|---|---|---|
| A 单指令直译 | `dp4a`、`dp2a` | 1 条 PTX → 1 条 `IDP.4A`/`IDP.2A`，signedness 逐个进助记符后缀 |
| A 单指令直译（链式语法） | `cvt.pack.sat.{s8,u8}.s32.b32` | 1 条 PTX → 1 条 `I2IP`；PTX 语法本身是"两路 pack + 前序高字节合并"的链式形态，不是跨指令展开 |
| A 单指令直译（隐藏合并槽） | `cvt.{rn.satfinite,rn}[.relu].{e4m3x2,e5m2x2}.{f32,f16x2,f16}` | 1 条 PTX → 1 条 `F2FP`；SASS 恒有 3 个源操作数，PTX 未使用的合并槽自动填 `RZ` |

## 实测助记符总表

### `dp4a`（套件已建，`FRAMEWORK_VALIDATED`）

| PTX | SASS | O0 | O3 |
|---|---|---|---|
| `dp4a.u32.u32 d,a,b,c` | `IDP.4A.U8.U8 d,a,b,c` | 立即数物化进 GPR | 立即数 `b` 走 `UR`（`IDP.4A.U8.U8 R9,R2,UR6,R5`） |
| `dp4a.s32.s32 d,a,b,c` | `IDP.4A.S8.S8 d,a,b,c` | 同上 | 同上 |
| `dp4a.u32.s32 d,a,b,c` | `IDP.4A.U8.S8 d,a,b,c` | 同上 | 同上 |
| `dp4a.s32.u32 d,a,b,c` | `IDP.4A.S8.U8 d,a,b,c` | 同上 | 同上 |
| `c` 为立即数 | 同签名 `IDP.4A.*` | GPR | **仍是 GPR**（`IDP.4A.U8.U8 R9,R2,R5,R9`），与 `b` 槽的 `UR` 路由不对称 |
| `d == c`（目的/累加器重叠） | 合法，`IDP.4A.*` 直接复用同一目的寄存器 | — | — |
| 两条 `dp4a` 累加器串联 | 两条独立 `IDP.4A.*`，第二条的 `c` 操作数取第一条的 `d` | — | — |
| guard `@%p` | `IDP.4A.*` 本身**不带** `@P` 前缀；O0/O3 均无条件计算，用 `SEL` 事后按谓词选择结果 | `ISETP` + 无条件 `IDP.4A` + `SEL` | 同 O0 结构 |

PTX 级 `u32`/`s32` 描述的是"该 32 位寄存器内 4 个打包字节应按无符号/有符号解释"，不是寄存器宽度声明——`.reg .b32`/`.u32`/`.s32` 声明该操作数寄存器时 SASS 结果不变，只有位宽不匹配（16/64 位）才被拒绝。

### `dp2a`（`DESIGNED`，轴已校准）

| PTX | SASS |
|---|---|
| `dp2a.lo.u32.u32 d,a,b,c` | `IDP.2A.LO.U16.U8 d,a,b,c` |
| `dp2a.hi.u32.u32 d,a,b,c` | `IDP.2A.HI.U16.U8 d,a,b,c` |
| `dp2a.lo.s32.s32 d,a,b,c` | `IDP.2A.LO.S16.S8 d,a,b,c` |
| `dp2a.hi.s32.s32 d,a,b,c` | `IDP.2A.HI.S16.S8 d,a,b,c` |
| `dp2a.lo.u32.s32 d,a,b,c` | `IDP.2A.LO.U16.S8 d,a,b,c` |
| `dp2a.lo.s32.u32 d,a,b,c` | `IDP.2A.LO.S16.U8 d,a,b,c` |
| `b` 为立即数（`lo`/`hi` 均实测） | 合法，O3 同 `dp4a` 走 `UR`（`IDP.2A.LO.U16.U8 R9,R2,UR6,R5`） |

`atype`（16 位对操作数 `a` 的符号）进 `U16`/`S16` 后缀，`btype`（8 位打包操作数 `b` 的符号）进 `U8`/`S8` 后缀——与 `dp4a` 的两个后缀都描述同一操作数宽度不同，`dp2a` 的两个类型后缀分别描述**不同宽度**的两个操作数，是本族内不能跨指令套用同一后缀语义的证据。`.mode`（`.lo`/`.hi`）是强制修饰符，缺失被拒（`'.hi/.lo' modifier required for instruction 'dp2a'`）。

### `cvt.pack`（`DESIGNED`，轴已校准；含一条证伪记录）

| PTX | SASS |
|---|---|
| `cvt.pack.sat.s8.s32.b32 d,a,b,c` | `I2IP.S8.S32.SAT d,a,b,c` |
| `cvt.pack.sat.u8.s32.b32 d,a,b,c` | `I2IP.U8.S32.SAT d,a,b,c` |
| `c` 为立即数 `0` | 折叠为 `RZ`（`I2IP.S8.S32.SAT R0,R0,R2,RZ`） |
| 两条 `cvt.pack` 链式（第二条 `c` = 第一条 `d`） | 两条独立 `I2IP.*.SAT`，四路 8 位值分两步打包进同一 32 位寄存器 |

**证伪记录**：规范阅读预期 `cvt.pack` 应同时存在 `.s16`/`.u16` 目的类型的 2 操作数形态（`cvt.pack.sat.s16.s32.b32 d,a,b;`，只打包两路 16 位值，无需 `c`）。实测该形态在本工具链上**全部被拒**，且诊断固定为 `Unexpected instruction types specified for 'cvt.pack'`（与操作数个数无关——3 操作数或 4 操作数形式同样被拒，说明不是"缺 `c`"而是"目的类型组合本身不被识别"）。本族在此工具链版本上 `cvt.pack` 的合法目的类型面**只有 `{s8, u8}`**，且**只有 4 操作数链式语法**；`.s32` 是唯一合法源类型（`.u32` 源同样被拒，同一诊断）。这条证伪推翻了任务描述里"预计 I2IP/PRMT 序列"中的 `PRMT` 猜测——本族未观测到 `PRMT` 参与 `cvt.pack` lowering。`.sat` 强制（`'.sat' modifier required for instruction 'cvt.pack'`），且不接受任何舍入修饰符（`Illegal rounding modifier for instruction 'cvt.pack'`）。

### `cvt.e4m3x2` / `cvt.e5m2x2`（`DESIGNED`，轴已校准）

| PTX | SASS | 备注 |
|---|---|---|
| `cvt.rn.satfinite.e4m3x2.f32 d,a,b` | `F2FP.SATFINITE.E4M3.F32.PACK_AB_MERGE_C d,a,b,RZ` | 打包方向，两个标量 f32 → 一对 FP8 |
| `cvt.rn.satfinite.e5m2x2.f32 d,a,b` | `F2FP.SATFINITE.E5M2.F32.PACK_AB_MERGE_C d,a,b,RZ` | 同上 |
| `cvt.rn.satfinite.relu.e4m3x2.f32 d,a,b` | `F2FP.SATFINITE.RELU.E4M3.F32.PACK_AB_MERGE_C d,a,b,RZ` | `.relu` 合法（见下方发现） |
| `cvt.rn.satfinite.e4m3x2.f16x2 d,a` | `F2FP.SATFINITE.E4M3.F16.UNPACK_B_MERGE_C d,a,RZ` | 打包方向，源为已打包 f16x2 |
| `cvt.rn.satfinite.e5m2x2.f16x2 d,a` | `F2FP.SATFINITE.E5M2.F16.UNPACK_B_MERGE_C d,a,RZ` | 同上 |
| `cvt.rn.f16x2.e4m3x2 d,a` | `F2FP.F16.E4M3.UNPACK_B d,a` | 反向（解包），**无** `SATFINITE`、**无**合并槽后缀 |
| `cvt.rn.f16x2.e5m2x2 d,a` | `F2FP.F16.E5M2.UNPACK_B d,a` | 同上 |

FP8 转换的 SASS 家族统一是 `F2FP`，`.E4M3`/`.E5M2` 描述哪一种 8 位浮点格式，`.F32`/`.F16` 描述参与的另一侧类型，`PACK_AB`/`UNPACK_B` 描述这条 `F2FP` 是在"合成一对 FP8"还是"从打包源里取出一路"。

## 合法面实测（satfinite / rounding / 结构）

| 探针 | 结论 | 诊断（若拒绝） |
|---|---|---|
| `f32 → e4m3x2` 不带 `.satfinite` | **拒绝**，`.satfinite` 强制 | `'.satfinite' modifier required for instruction 'cvt' with destination type '.e4m3x2'` |
| `f32 → e5m2x2` 不带 `.satfinite` | **拒绝**，同上 | `'.satfinite' modifier required for instruction 'cvt' with destination type '.e5m2x2'` |
| `f16x2 → e4m3x2` 不带 `.satfinite` | **拒绝**，同上（打包方向恒强制，与源类型无关） | `'.satfinite' modifier required for instruction 'cvt' with destination type '.e4m3x2'` |
| `e4m3x2 → f16x2` 带 `.satfinite` | **拒绝**——解包方向不接受 `.satfinite`，二者互斥而非"解包方向可选" | `Unexpected instruction types specified for 'cvt'` |
| FP8 pack 不带 `.rn` | **拒绝**，舍入修饰符强制 | `Rounding modifier required for instruction 'cvt'` |
| FP8 pack 用 `.rz`/`.rp`/`.rm` | **拒绝**，本族舍入档位支持面**只有 `.rn`** | `Illegal rounding modifier for instruction 'cvt'` |
| FP8 pack 加 `.relu` | **接受**（发现，非任务预设猜测） | — |
| `dp4a` 加 `.sat` | **拒绝**，PTX 语法层无饱和开关 | `Illegal modifier '.sat' for instruction 'dp4a'` |
| `dp4a` 加 `.lo`（误用 `dp2a` 的修饰符） | **拒绝** | `Comparison qualifier is not allowed for instruction 'dp4a'` |
| `dp2a` 缺 `.lo`/`.hi` | **拒绝** | `'.hi/.lo' modifier required for instruction 'dp2a'` |
| `cvt.pack` 缺 `.sat` | **拒绝** | `'.sat' modifier required for instruction 'cvt.pack'` |
| `cvt.pack.sat.s16.s32.b32`（2 或 3 操作数） | **拒绝**——本工具链版本无 s16/u16 目的类型（证伪记录，见上） | `Unexpected instruction types specified for 'cvt.pack'` |
| `cvt.pack` 源类型 `.u32` | **拒绝**，唯一合法源类型是 `.s32` | `Unexpected instruction types specified for 'cvt.pack'` |
| `dp4a`/`dp2a` 的 `b` 操作数为立即数 | **接受**（全部签名实测），O3 走 `UR` | — |
| `dp4a` 的 `c`（累加器）为立即数 | **接受**，O3 仍走 GPR（与 `b` 槽不对称） | — |
| `dp4a` 混入 `.f32`/64 位/16 位操作数 | **拒绝** | `Arguments mismatch for instruction 'dp4a'` |
| `dp4a` 使用不存在的类型关键字（`u16`/`b32`/单类型） | **拒绝** | `Unexpected instruction types specified for 'dp4a'` |

**结论汇总**：`.satfinite` 在"打包成 FP8"方向对 `e4m3x2`/`e5m2x2`、对 `.f32`/`.f16x2` 源**全部强制**，在"从 FP8 展开"方向**全部非法**——不是"可选变宽松"，而是两个互斥的强制状态,按转换方向二值切换。舍入档位方面本族目前只观测到 `.rn` 一个合法档位；未发现 tie-breaking 的其它可选项，"rounding tie" 的具体舍入行为（是否 round-half-to-even）留给运行时数值 oracle 验证，静态编译层不可观测。

## 对抗式审查缺口在本族的落实

| tcgen05 缺口 | 本族对应设计 |
|---|---|
| P0-1 控制位是全局资源 | 已实测**不适用**于本族核心语义（无 scoreboard/mbarrier）；`dp4a` 套件仍按指南要求内置深度轴（`chain_depth_2`/`chain_depth_4`：累加器串联深度）与并行轴（`parallel_2`：两条独立指令经 `xor` 汇聚），把"控制位是全局资源"的精神换算成"累加器依赖链深度是否改变指令选择"——已实测不改变（`IDP.4A` 助记符与操作数结构在深度 2/4 下恒定），此为负向确认，已记录而非略过 |
| P0-2 合法面未证伪 | 本文两处证伪记录（`cvt.pack` 无 s16/u16 目的类型、FP8 解包方向禁止 `.satfinite`）均来自"预期合法却被拒绝"通道；`dp4a` 套件负向探针全部登记 `expected_diagnostic` 并实测匹配（10/10），其中 2 条为补集抽样（`extra_operand`、`double_dot_modifier`）而非核心签名/位宽假设的直接展开 |
| P0-3 组合不足 | `dp4a` 套件的 syntax 矩阵覆盖 `SF.atype`×`SF.btype`（4 种符号组合）× `SF.b_class`/`SF.c_source`（立即数轴），并显式登记两条 `b`+`c` 同时立即数的双修饰符组合（`dual_imm`）；expanded 追加 `combo_indirect_dual_imm`（双立即数 + 不可折叠 `a` producer 三因子叠加） |
| P1-1 模板未受控 | `dp4a` expanded 含 `template_wide`（参数签名加宽并插入 pad 参数），确认加宽签名不改变 `IDP.4A` 操作数结构，只改变 const-bank 偏移（未在套件里逐字段核对偏移值，只确认目标指令归属不受影响） |
| P1-2 重物化前提 | `dp4a` expanded 对 `a`/`b`/`c` 三个操作数分别提供不可折叠 producer（`a_indirect`/`b_indirect`/`c_indirect`：tid 派生 `xor`），确认三个操作数槽位对不可折叠来源的容忍度一致 |
| P2 边界 | 套件接受 `--ptxas`/`--nvdisasm` 路径参数（继承 `suite_runtime.py` 模板），跨版本重跑只需替换工具链路径；`.relu` 这类"超出任务预设猜测的合法修饰符"发现，说明版本差分时应对 FP8 转换族重新跑一遍修饰符枚举而非假定当前合法面稳定 |

## 每指令研究重点

### `dp4a`（套件已建，`FRAMEWORK_VALIDATED`）

1. 立即数在 `b`/`c` 两个槽位的编译器路由不对称（`UR` vs GPR）目前记为观测，未证明是 ISA 强制还是 ptxas 当前版本的寄存器分配策略——需要跨 release 差分才能升级为规则。
2. guard 谓词从 `IDP.4A` 上消失、改用 `SEL` 事后选择，与 `02_tma/实验设计.md` 记录的 `cp.async` guard 现象同构；本族进一步确认该模式在纯 ALU 指令上同样成立，两族证据互相加强但未合并成通用规则声明（各自归属各自文档）。
3. 四种签名（`u32.u32`/`s32.s32`/`u32.s32`/`s32.u32`）在 SASS 层各自独立编码（`U8.U8`/`S8.S8`/`U8.S8`/`S8.U8`），说明 `atype`/`btype` 是两个独立的每操作数符号位，不是一个整体"有符号/无符号"开关——逆向规则挖掘时必须按操作数对分别判定符号，不能从助记符猜测整条指令的符号语义。
4. 累加器链（`chain_depth_2`/`chain_depth_4`）尚未验证寄存器分配在更深链条（8、16 条）或跨基本块场景下是否仍保持"逐条独立 `IDP.4A`"的简单结构；深链与循环携带累加器是未覆盖的形态。

### `dp2a`（`DESIGNED`）

1. `.mode`（`.lo`/`.hi`）选择 `b` 操作数（4 路 8 位打包值）里参与运算的哪一对，`a` 操作数（2 路 16 位打包值）不受 `.mode` 影响——尚未通过套件对 `.mode` 与 `.atype`/`.btype` 的双修饰符组合做完整交叉验证。
2. 与 `dp4a` 共享的立即数路由问题（`b` 槽已验证 O3 走 `UR`）需要在完整套件里对 `.lo`/`.hi` 两态各自重新确认，不能从 `dp4a` 结果外推。
3. `dp2a` 与 `dp4a` 混合调度上下文（同一 kernel 内两族指令交替出现）下寄存器分配是否互相干扰，未探针。

### `cvt.pack`（`DESIGNED`，含证伪记录）

1. 本工具链版本上 `.s16`/`.u16` 目的类型全部不可用是否是 Thor/`sm_110a` 特有限制、还是 PTX 9.0 该指令本身的定义收窄，需要与旧架构（如 `sm_90a`）差分才能区分"ISA 事实"与"本版本实现选择"——按 `01_tcgen05` 审查 P2-1 的同款方法论处理，目前只记录观测,不下架构层结论。
2. 链式 pack（两条 `cvt.pack` 通过 `c` 串联）目前只验证了 2 深度；更长链条、以及链条与 `dp4a` 的操作数是否共享寄存器分配策略，未覆盖。
3. `d`/`a`/`b` 操作数重叠（`a == b`）尚未系统验证——只知道 `c` 立即数 `0` 会折叠为 `RZ`。

### `cvt.e4m3x2` / `cvt.e5m2x2`（`DESIGNED`）

1. `F2FP` 恒带的第三源操作数（`MERGE_C`，PTX 未暴露、恒为 `RZ`）提示底层硬件原语可能支持一种当前 PTX 语法未开放的"pack 并与已有值合并"操作——这是一个观察记录，不是已证明的可利用能力；在没有找到能让该槽位非 `RZ` 的 PTX 语法之前，不应假设它可控。
2. `.relu` 是本次校准中超出任务预设猜测的发现，其在打包两方向（`.f32` 源、`.f16x2` 源）都合法，但尚未验证是否对 `.rn`-only 的舍入约束、或对解包方向（`e4m3x2 → f16x2`）有交互；解包方向未测试 `.relu`。
3. e4m3x2 与 e5m2x2 之间是否存在直接互转（不经过 f16x2/f32 中转）未探测；若不存在，量化流水线的格式切换必须经过中间格式，这对流水线设计有直接影响。
4. 逐 lane 数值语义（哪个源操作数对应 SASS pack 结果的哪个字节位置、round-half-to-even 的具体行为、`satfinite` 的边界值钳位精确阈值）全部留给运行时 oracle，见下方 `STATIC_ONLY` 声明。

## STATIC_ONLY 边界声明

全部结论为 `STATIC_ONLY`：编译通过 + 归属成功不证明点积累加、pack 打包、FP8 舍入或饱和钳位的数值正确性。族 README 门槛要求"逐 lane oracle + saturation 两侧 + rounding tie"，这条门槛明确落在运行时验证范围，本文档与已建套件均不覆盖；以下把该门槛将来落地时需要的 lane 设计约束记录在案，供运行时 oracle 编写时直接复用套件坐标，而不必重新逆向：

- **`dp4a`/`dp2a` 的字节序**：`dp4a` 的 `a`/`b` 操作数各自打包 4 个 8 位值，`dp2a` 的 `a` 打包 2 个 16 位值、`b` 打包 4 个 8 位值（`.mode` 选其中一对）；哪个字节/半字对应点积的哪一路，套件坐标里没有编码这个断言，需要运行时 oracle 用已知边界值（如 `0x01, 0x02, 0x03, 0x04`）单独探测后再补充进坐标 `lane_order` 字段。
- **`dp4a` saturation 两侧**：`dp4a` 本身不带 `.sat`（已证伪），累加是否可能整型溢出（`u32`/`s32` 累加器）由调用者负责，不是指令语义的一部分——运行时 oracle 的"两侧"应理解为"累加器上溢/下溢的边界值"，不是指令自带的饱和钳位。
- **`cvt.pack` saturation 两侧**：`.sat` 是强制修饰符，目的类型 `s8`（`[-128,127]`）与 `u8`（`[0,255]`）的钳位边界必须各测上界与下界共 4 个点，外加链式 `c` 操作数携带的高两字节是否共享同一饱和判定（未知，需 oracle 验证）。
- **FP8 rounding tie**：静态编译只确认 `.rn` 是唯一合法舍入档位；round-half-to-even 的具体行为（尾数为 0.5 ULP 时向偶数舍入）、以及 `.satfinite` 钳位到 FP8 最大有限值而非 `Inf` 的精确阈值，需要运行时 oracle 用已知 tie 值（如恰好落在两个可表示 FP8 值中点的 f32 输入）逐 lane 验证；套件坐标应为每个 `context` 预留 `tie_case` 布尔字段以便后续扩展，当前套件未使用运行时数值，故未启用该字段。
- **`.relu` 与 saturation 的交互**：`.relu` 合法但语义未验证——是"先 relu 再 satfinite"还是"两者融合成单一钳位"决定了负数输入在边界附近的行为，纯负向静态测试无法区分，留给运行时 oracle。

tensormap/mbarrier 一类跨族状态在本族不涉及；`dp4a` 套件的 `full_instructions`（128-bit 编码）已按模板保留，供将来控制字差分复用，但本族核心语义不依赖控制字，此项主要是与其他族保持结构一致，不代表本族发现了控制字相关缺口。

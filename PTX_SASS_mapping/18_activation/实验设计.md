# Activation（`tanh` / `ex2` 低精度形态）实验设计

> 适用范围：PTX ISA 9.0、NVIDIA Thor、`sm_110a`、CUDA 13.0（ptxas V13.0.88、nvdisasm V13.0.85）
> 本文性质：实验设计裁决 + 首轮校准记录。文中"实测"来自本机会话 scratchpad 的 40+ 个校准探针
> （`.version 9.0` / `.target sm_110a`，`ptxas -O0/-O3` + `nvdisasm --print-code --print-instruction-encoding`）
> 以及已建成的 `tanh/thor_ptx90/` 套件（15 syntax + 25 expanded case，O0–O3 全量自检，10 负向探针）。
> 探针脚本未入库（按任务口径留在会话 scratchpad），套件本身可独立复现全部 tanh 结论；ex2 结论目前
> 仅有探针证据，尚无套件复现入口（见"路线图"）。
> 设计基线：`01_tcgen05` 的静态实验分层，`02_tma/实验设计.md` 的文档结构，并逐条吸收
> `01_tcgen05/对抗式审查_实验设计缺口.md` 的 P0/P1 结论。

## 结论

本族两个 opcode（`tanh`、`ex2` 的低精度形态）在结构上都不是"观察到的近似序列直接当可替换规则"
这种最容易踩空的情形——**每一个已校准合法 dtype 都落到真正的硬件超越函数单元
（`MUFU.TANH.*` / `MUFU.EX2.*`），没有任何 dtype 需要软件多项式展开**。差异只出现在
"一条 PTX 对一条 SASS"还是"一条 PTX 对两条 SASS（拆 lane）"：

| 结构类别 | 覆盖 dtype | PTX→SASS |
|---|---|---|
| A 单指令直译 | `tanh.approx.{f32,f16,bf16}`；`ex2.approx.f16`；`ex2.approx.ftz.bf16` | 1 条 PTX → 1 条 SASS，dtype 后缀直译（`.F16`/`.BF16`，f32 无后缀） |
| L 拆 lane 序列（1 条 PTX → 2 条 SASS + 打包指令，仍是稳定序列，非多项式） | `tanh.approx.{f16x2,bf16x2}`；`ex2.approx.f16x2` | 两条 `MUFU.{TANH,EX2}.{F16,BF16}` 分别处理高低 16 位 + `PRMT` 打包/解包；**O0 显式 `PRMT` 解包两次，O3 省掉解包（第二条 MUFU 直接读 `Rn.H1`）**，是否出现依赖两个 lane 的结果是否都被下游消费（见"结构分类"一节的 DCE 警告） |
| 越界对照（B 类，编译器合成协议，归 `06_cuda_core_fp` 持有） | `ex2.approx.f32`（不带 `.ftz`） | `FSETP` 判断范围 + 条件 `FMUL 0.5` + `MUFU.EX2` + 条件 `FMUL` 平方 + `FSEL` 选择——真正的编译器合成正确性协议，**只在 f32 且不带 `.ftz` 时出现**；`.ftz.f32` 与全部低精度 dtype 都不需要这层协议 |

这本身就是一条对抗式发现：任务简报预设的三种可能性（HMUFU 类 / 拆 lane MUFU 序列 / 整段多项式模拟）
里，"HMUFU"（假设存在的打包型超越函数单元指令）和"多项式模拟"在本机 CUDA 13.0 / `sm_110a` 上均未
出现；真实情况是标量走 `MUFU.{TANH,EX2}.F16`/`.BF16`（依然是硬件直译，只是带 dtype 后缀），
`x2` 走两次标量 `MUFU` 调用的稳定序列。**这一结论仅覆盖 `tanh`/`ex2` 低精度形态，不外推到本族之外
或未来 CUDA 版本**（P2-1 口径）。

## 探针校准表

### `tanh`

修饰符legality（对全部合法 dtype 一致，已逐个探针验证）：`.approx` **强制**（`tanh.f32` 直接被拒，
诊断 `.approx modifier required for instruction 'tanh'`）；`.rn`、`.ftz`、`.sat` 在**全部** dtype 上
都是非法修饰符（`Illegal rounding modifier for instruction 'tanh'` / `Illegal modifier '.ftz' for
instruction 'tanh'` / `Illegal modifier '.sat' for instruction 'tanh'`）；无 `.f64` 形态、无整型形态
（`Unexpected instruction types specified for 'tanh'`）。**`tanh` 没有全精度 `.rn` 形态**——不是"全
精度形态存在但 rounding 可选"，而是 rounding 修饰符本身不合法，全部合法形态都只有 `.approx` 一种舍入
契约。

| dtype | O0 SASS 结构 | O3 SASS 结构 | 归类 |
|---|---|---|---|
| `f32` | `MUFU.TANH Rd, Ra`（1:1） | `MUFU.TANH Rd, Ra`（1:1） | A 直译 |
| `f16` | `MUFU.TANH.F16 Rd, Ra`（1:1） | `MUFU.TANH.F16 Rd, Ra`（1:1） | A 直译 |
| `bf16` | `MUFU.TANH.BF16 Rd, Ra`（1:1） | `MUFU.TANH.BF16 Rd, Ra`（1:1） | A 直译 |
| `f16x2` | `PRMT`×2 解包 → `MUFU.TANH.F16`×2 → `PRMT` 重打包（5 条含 2 条目标） | `MUFU.TANH.F16 R0,R2` + `MUFU.TANH.F16 R7,R2.H1`（免解包）→ `PRMT` 重打包（3 条含 2 条目标） | L 拆 lane 序列 |
| `bf16x2` | 同 `f16x2` 结构，助记符换 `MUFU.TANH.BF16` | 同 `f16x2` 结构，助记符换 `MUFU.TANH.BF16` | L 拆 lane 序列 |

一个额外发现（P0-2 发现渠道）：`tanh.approx.f32 %d, 0f3f800000;`（源操作数为立即数字面量而非寄存器）
**编译通过**，直接编码为 `MUFU.TANH R0, 1`——`MUFU.TANH` 支持立即数源操作数，这不在最初假设的合法面
描述里，已作为 `CTX.immediate_source` 并入 expanded 套件（正向发现，非负向探针）。

### `ex2`（低精度形态；`f32`/`f64` 通用形态归 `06_cuda_core_fp`，此处仅作边界对照）

修饰符 legality 在 `ex2` 上按 dtype **不对称**——这是比 `tanh` 更强的一条"不能跨 dtype 泛化"证据：

| dtype | `.ftz` | O0/O3 SASS 结构 | 归类 |
|---|---|---|---|
| `f16` | **非法**（`Illegal modifier '.ftz' for instruction 'ex2'`） | `MUFU.EX2.F16 Rd, Ra`（1:1，O0=O3） | A 直译 |
| `f16x2` | 非法 | 拆 lane：结构与 `tanh.f16x2` 完全同构（`PRMT`+2×`MUFU.EX2.F16`+`PRMT`） | L 拆 lane 序列 |
| `bf16` | **强制**（不带 `.ftz` 拒绝，诊断 `.ftz modifier required for instruction 'ex2.bf16'`） | `MUFU.EX2.BF16 Rd, Ra`（1:1，O0=O3） | A 直译 |
| `bf16x2` | 强制 | 拆 lane：`PRMT`+2×`MUFU.EX2.BF16`+`PRMT`，同构 | L 拆 lane 序列 |
| `f64` | N/A | `ex2.approx.f64` 直接拒绝：`Unexpected instruction types specified for 'ex2'`（不是"支持但慢"，是完全不支持） | 越界，仅确认边界 |
| `f32`（不带 `.ftz`，越界对照） | 可选 | O0：`FSETP.LT.AND` + `FMUL ×0.5`(条件) + `MUFU.EX2` + `FMUL R,R`(条件平方) + `FSEL`；O3：`FSETP.GEU.AND` + `@!P0 FMUL ×0.5` + `MUFU.EX2` + `@!P0 FMUL R,R` | B 类编译器合成范围规约协议 |
| `f32.ftz`（越界对照） | 强制打开 | 裸 `MUFU.EX2 Rd, Ra`（1:1，无范围规约） | A 直译 |

`ex2.approx.rn.f16`（把 `.approx` 换成显式 `.rn`）被拒绝，诊断
`Rounding modifier or '.approx' modifier required for instruction 'ex2'`——与 `tanh` 的
"仅 `.approx` 合法、`.rn` 非法"不同，`ex2` 的诊断措辞暗示 `.rn` 是这条指令语法上可选的舍入位之一，只是
这个具体探针把两者都写错了；本文未进一步枚举 `ex2` 的合法舍入面，留给 `ex2` 套件建设时处理（见路线图）。
`.sat` 在 `f16` 上非法（`Illegal modifier '.sat' for instruction 'ex2'`）。

`f32`/`f64` 通用形态由 `06_cuda_core_fp` 持有，本文只记录到能画清边界为止，不重复建账；但
`f32`（无 `.ftz`）呈现的范围规约协议，与本族全部低精度形态（`f16`/`bf16`/`f16x2`/`bf16x2`，无论
`ex2` 还是 `tanh`）都不出现同类协议形成对照——**范围规约协议是 f32 精度特有的正确性补偿，不是
"approx 类超越函数"的通用特征**，这条边界结论本身就是防止"观察到的近似序列直接当可替换规则"的一个
具体反例。

## 与 epilogue 的组合（族 README 点名的组合轴）

全部探针使用 `tanh.approx.f32`/`.f16` 为代表，O0/O3 均已验证：

| 组合 | 实测 | 结论 |
|---|---|---|
| `tanh.f32` → `mul.f32`（乘常数/乘间接量） | `MUFU.TANH` 与 `FMUL` 相邻但**不融合**成单条指令 | 不融合，纯调度相邻 |
| `tanh.f32` → `add.f32` | `MUFU.TANH` 与 `FADD` 相邻不融合 | 不融合 |
| `tanh.f16` → `mul.f16` | `MUFU.TANH.F16` 后接 `HMUL2 Rd, Rs.H0_H0, Rs.H0_H0`（标量 `mul.f16` 在 SASS 层走打包 `HMUL2` 广播形式，不是标量乘法指令）；不融合 | 不融合；顺带发现"标量 f16 乘法在 SASS 层没有专用标量指令，统一走 `HMUL2` 广播" |
| `cvt.rn.f16.f32` → `tanh.approx.f16`（先转换再 tanh，对照直接 f16 tanh） | O0：`F2F.F16.F32` 后接 `MUFU.TANH.F16`；O3：`F2FP.F16.F32.PACK_AB`（打包转换形式，尽管只用一路）后接 `MUFU.TANH.F16`。**两种优化级别下 `cvt` 都不会被吸收进 `tanh`**，只是 `cvt` 自身的 SASS 选择随优化级别变化（O0 用标量转换指令，O3 用打包转换指令的单路形式） | 不融合；且 `cvt` 前驱指令本身的 SASS 形态是优化级别相关的独立变量，不能只按 O3 或只按 O0 归纳规则 |
| `tanh.f32` → `tanh.f32`（双 tanh 链） | 两条独立 `MUFU.TANH` 背靠背，无代数化简、无消除 | 不融合，链式保留 |
| guard 谓词 `@%p tanh.approx.f32 ...` / `@!%p mov ...` | **谓词不落在 `MUFU.TANH` 本身**：ptxas 无条件计算 `MUFU.TANH`，再用 `FSEL`（O3 是两条 `FSEL`）在两个分支值间选择 | 与 TMA 族的 `UTMALDG` 形成鲜明对照（TMA 的 guard 谓词落在指令上，`@!UPx UTMALDG`）；`MUFU` 类超越函数单元的 guard 走推测执行 + 选择，不是硬件谓词位 |

推论：本族的"融合"轴在当前 ptxas 上**全部是阴性结果**——没有发现任何 epilogue pattern 被吸收进
`tanh`/`ex2` 本身的编码。这本身是需要被记录的合法面事实（否则后续读者可能想当然认为存在 fused
activation 指令）。

## 结构分类

- **A 单指令直译**：`tanh.approx.{f32,f16,bf16}`、`ex2.approx.f16`、`ex2.approx.ftz.bf16`。1 PTX → 1
  SASS，dtype 后缀就是 mnemonic 后缀，无操作数形态变化。
- **L 拆 lane 序列**：`tanh.approx.{f16x2,bf16x2}`、`ex2.approx.{f16x2,ftz.bf16x2}`。1 PTX → 一个稳定
  的多指令序列（解包/免解包 + 两条标量 `MUFU` + 重打包）。**这不是"观察到的近似序列"意义上的模糊近似
  ——序列结构在全部已测 dtype × 优化级别 × 消费者组合下稳定复现，且套件的 `lane_asym` case 已验证：
  只要两个 lane 的结果都被下游消费，序列在 O0–O3 全程稳定**。
- **DCE 陷阱（不是独立类别，是对 L 类的适用范围警告）**：探针 `tanh_f16x2_asym_pack`
  （构造非对称打包输入、只消费一个 lane 的输出）显示 **O3 会把整个 x2 计算退化为一条标量
  `MUFU.TANH.F16`**——上游仍加载两个操作数并打包，但只有被消费的那个 lane 保留计算，另一个 `MUFU`
  调用连同其打包指令被消除。这意味着"x2 dtype ⇒ 恒定两条 MUFU"不是不变式，而是"两个 lane 都活跃"
  这个前提下的观测。套件的 `lane_asym` case 因此显式让两个 lane 都参与下游 `add.f32` 归约，避免被
  DCE 掩盖真实序列结构。
- **B 类范围规约协议（越界对照，不在本族计数内）**：仅 `ex2.approx.f32`（无 `.ftz`）出现，由
  `06_cuda_core_fp` 持有。
- **未观测到的类别**：本族全部已校准合法 dtype 都未出现"整段多项式模拟"（一串 `FMUL`/`FMA` 展开近似
  多项式、不含任何 `MUFU` 指令的序列）。这是一个需要留痕的阴性结果：任务简报预设的三种可能之一被
  实测排除，不是"未检查"。

## 已校准合法面

- **dtype 全集**（本族范围内）：`tanh` 合法 `{f32, f16, f16x2, bf16, bf16x2}`，五者齐全；`ex2` 低精度
  合法 `{f16, f16x2, bf16(.ftz 强制), bf16x2(.ftz 强制)}`。
- **`tanh` 无全精度 `.rn` 形态**：`.rn`/`.ftz`/`.sat` 在全部 dtype 上都是非法修饰符，`tanh` 只有
  `.approx` 一条合法舍入契约，没有"精确 tanh"这回事。
- **bf16 的 `ex2` 合法性以 `.ftz` 为前提**：`ex2.approx.bf16`（不带 `.ftz`）直接拒绝，`bf16` 家族的
  `ex2` 合法面是 `ex2.approx.ftz.bf16`/`ex2.approx.ftz.bf16x2`，这是 dtype 与 `.ftz` 的联合约束，不能
  拆成两条独立轴登记（同 TMA 审查里 op×type 后缀不能拆轴的教训）。
- **P0-2 四象限**（复用 tcgen05 审查方法论）：

  | 象限 | 实例 |
  |---|---|
  | 预期合法且接受 | `tanh.approx.{f32,f16,bf16,f16x2,bf16x2}`；`ex2.approx.{f16,f16x2}`；`ex2.approx.ftz.{bf16,bf16x2}` |
  | 预期非法且拒绝 | `tanh.f32`（缺 `.approx`）、`tanh.approx.f64`、`tanh.approx.s32`、`tanh.approx.rn.f32`、`tanh.approx.sat.f32`、目标操作数宽度不匹配、操作数个数不匹配 |
  | **预期非法但接受**（合法面画小了） | `tanh.approx.f32 %d, <immediate>;`——立即数源操作数；未在最初的"寄存器操作数"假设里 |
  | **预期合法但拒绝**（合法面画大了，跨 opcode 泛化的陷阱） | 按 `ex2`/`rsqrt`/`rcp` 等兄弟 `.approx` 指令普遍支持 `.ftz` 类推，`tanh.approx.ftz.f32` 应当合法——**实测在全部 dtype 上都被拒绝**。这是本文最重要的一条 P0-2 教训：**同族内不同 opcode 的修饰符合法面不能相互类推，哪怕它们共享 `.approx` 语义** |

  第二条"预期非法但接受"补充：`ex2` 的 `.ftz` 合法性按 dtype 反向（`f16` 禁、`bf16` 强制），如果只按
  `tanh` 的经验（全 dtype 一致禁用 `.ftz`）类推到 `ex2`，会在 `bf16` 上判断失误——这是**同一 opcode
  家族内跨 dtype 类推也不安全**的证据，比跨 opcode 类推更容易被忽视。

## 审查缺口对应设计

| tcgen05 缺口 | 本族对应设计 |
|---|---|
| P0-1 控制位是全局资源 | `tanh` 套件 expanded 含 `inflight_depth_2`/`inflight_depth_4`（独立 `tanh` 调用条数）与 `double_chain`（消费距离为 0 的背靠背链）；探针 `tanh_f32_inflight_2_immediate` vs `_delayed` 实测：即使 `MUFU.TANH` 是定长延迟功能单元而非异步引擎，其相邻指令的 word 1 stall/barrier 位仍随在飞条数与消费距离变化（如 `0x004e24`→`0x004fe2`/`0x008e64`），`full_instructions` 已保留供后续控制字差分，不需要重跑实验 |
| P0-2 合法面未证伪 | 10 条负向探针全部登记 `expected_diagnostic` 子串；另设 2 条补集抽样（`extra_operand_complement`、`f16x2_scalar_args_complement`，均为算子个数/宽度类而非 dtype/修饰符类约束）；`.ftz` 跨 opcode/跨 dtype 泛化失败已记入"预期合法但拒绝"象限 |
| P0-3 组合不足 | expanded 覆盖 dtype×consumer 全factorial（15）+ 9 个 CTX 组合（indirect producer、cvt 前驱、双链、拆 lane 双活跃、guard、模板宽度、双档在飞深度、立即数源），不是单因素扫描 |
| P1-1 模板未受控 | `template_wide` case 验证参数签名加宽后常量 bank 偏移变化（`0x380`→`0x388`→`0x398`），`MUFU.TANH` 本身不变 |
| P1-2 重物化前提 | `producer_indirect` case 让源操作数来自 `%tid.x` 派生值 + 内存偏置的加法，不可折叠为立即数；`lane_asym` case 让 `f16x2`/`bf16x2` 的两个 lane 分别来自独立 `ld.global`，而非单条 32 位打包加载 |
| P2 边界 | 套件 `check_cases.py`/`check_negative_probes.py` 接受 `--ptxas/--nvdisasm` 路径参数，跨版本重跑只需换工具链；数值语义边界见下方"边界声明" |

## 每指令研究重点

### `tanh`（套件已建，`FRAMEWORK_VALIDATED`）

1. 立即数源操作数（`MUFU.TANH Rd, <imm>`）是否对全部 dtype 都合法，还是仅 `f32`——当前只在 `f32`
   上验证，`f16`/`bf16`/`x2` 形态的立即数支持待补。
2. `ex2.approx.rn.f16` 诊断文本暗示 `ex2` 存在显式 `.rn` 舍入位，而 `tanh` 完全没有——`tanh` 为什么在
   ISA 设计上比 `ex2` 少一种舍入契约，需要 PTX ISA 手册交叉核对（本文只记录实测边界，不猜测设计动机）。
3. `HMUL2`/`HFMA2` 出现在标量 `f16`/`bf16` `mul` 消费者的 SASS 里（`mul.bf16` → `HMUL2.BF16_V2`，
   `mul.f16x2`/`mul.bf16x2` → `HFMA2`/`HFMA2.BF16_V2` 而非 `HMUL2`——O3 把乘法折成 FMA 形式带
   `-RZ` 第三操作数），说明本族的"consumer"轴天然会牵出 `06_cuda_core_fp` 的半精度算术 lowering
   规则，两族在 epilogue 组合处有交叉验证价值但规则归属仍在 `06`，本目录不重复登记。
4. `cvt.f32.bf16`（升精度，无需舍入）在 SASS 层走 `SHF.L.U32`（纯移位，因为 bf16 就是 f32 高 16
   位，升精度=左移 16 位补零）而非任何 `F2F`/`MUFU` 指令；`cvt.rn.bf16.f32`（降精度）走
   `F2F.BF16.F32`（O0）/`F2FP.BF16.F32.PACK_AB`（O3）。这与 `f16` 的 `cvt.f32.f16`/`cvt.rn.f16.f32`
   非移位路径不同，是 bf16 位布局特有的编译器优化，值得在 `06_cuda_core_fp` 交叉记录（本文只作为
   epilogue 组合的背景观测）。

### `ex2`（低精度形态，`DESIGNED`，尚未建套件）

1. `.ftz` 按 dtype 反向合法（`f16` 禁、`bf16` 强制）的机制原因待查——初步猜测与 bf16 的指数范围/
   subnormal 行为有关，但这是解释性假设，不是实测结论，需要更多探针（如 `ex2.approx.f16x2` 与
   `.ftz` 的交互、`bf16` 不同指数区间输入的运行时行为——后者已越出 `STATIC_ONLY`）。
2. `ex2` 的合法舍入面（`.approx` vs 显式 `.rn` 等）未系统枚举，诊断文本
   `Rounding modifier or '.approx' modifier required` 暗示存在替代舍入修饰符集合，建套件时需要先做
   语法候选全集枚举（P0-2 方法论）再定合法面，不能只按 `.approx` 一条分支设计。
3. `f32`（无 `.ftz`）的范围规约协议与 `06_cuda_core_fp` 的既有结论是否一致，需要交叉核对而非本目录
   重新建账；本文的 `f32` 记录仅为"低精度形态不需要该协议"提供对照证据。
4. 尚未验证 epilogue 组合（mul/cvt/双链/guard）在 `ex2` 上是否与 `tanh` 同构——`tanh`/`ex2` 的
   `f16x2` 拆 lane 序列已证同构（`PRMT`+2×`MUFU`+`PRMT`），但组合轴（consumer/producer/guard）尚未
   对 `ex2` 逐条重测，是建 `ex2` 套件时的第一步工作，不能假定"结构同构 ⇒ 组合行为也同构"。

## 边界声明（`STATIC_ONLY`）

全部结论为 `STATIC_ONLY`：编译通过 + SASS 归属成功不证明 `MUFU.TANH`/`MUFU.EX2` 的数值近似精度、
特殊值（`±0`/`Inf`/`NaN`/subnormal）行为、或范围规约协议（`ex2.approx.f32`）在边界输入下的正确性。
族 README 明确要求"数值 oracle 必须声明误差度量、输入域和特殊值策略"——本文与本套件都**不提供**这三
项：没有做过任何 `MUFU.TANH`/`MUFU.EX2` 输出与参考实现的数值比对，没有定义 ULP/相对误差度量，没有
枚举特殊值输入域。任何要把本文的"结构分类"或"校准表"当作数值可替换规则使用的下游消费者，必须先补齐
误差度量、输入域和特殊值策略这三项，否则不满足族 README 的完成门槛。`.ftz` 相关的 subnormal 行为
（尤其是 `ex2.approx.ftz.bf16` 为什么强制 `.ftz`）在本文中只有编译期合法性证据，运行时数值行为完全
未验证。

# mbarrier 族实验设计

> 适用范围：PTX ISA 9.0、NVIDIA Thor、`sm_110a`、CUDA 13.0（ptxas V13.0.88、nvdisasm V13.0.85）
> 本文性质：实验设计裁决 + 首轮校准记录。文中"实测"来自本机 47 个校准探针（scratchpad，`t01_init.ptx`…`t47_init_cluster_scope_neg.ptx`，编号即探针引用，可按文中给出的 PTX 片段逐条重放）的 O0/O3 编译反汇编，以及旗舰套件 `mbarrier.arrive/thor_ptx90/` 的 O0–O3 全量自检。所有 mbarrier 对象声明遵循 `.shared .align 8 .b64 mbar;`（8 字节对齐是 `.b64` 操作数的硬约束，未测试更宽/更窄对齐）。
> 设计基线：`01_tcgen05` 的静态实验分层（syntax/expanded/negative/O0–O3/归属/规则挖掘）与结构分类法（A/B/C/D，见 `01_tcgen05/各指令_映射规则研究重点.md`），逐条吸收 `01_tcgen05/对抗式审查_实验设计缺口.md` 的 P0/P1 结论；表格与叙述口径对齐 `02_tma/实验设计.md`。

## 结论

mbarrier 族 9 个 opcode 全部落在 A 类（单指令直译），**没有独立的 B/C/D 类**，但族内出现两种此前在 TMA/tcgen05 都未见过的"类内变体"，必须在文档里单独标注，否则会把它们错误地并入普通 A 类：

1. **modifier 组合决定指令组大小（1→5 条）**：`mbarrier.arrive`/`arrive_drop` 在 `.release` 语义 **且** `.cluster` 作用域同时成立时，会在核心 `SYNCS.ARRIVE.TRANS64...` 之前插入固定的四指令前导序列（`MEMBAR.ALL.CTA` + `MEMBAR.ALL.GPU` + `ERRBAR` + `CGAERRBAR`）；`.relaxed` 语义即使配 `.cluster` 作用域也不触发该前导序列。这不是"是否跨 CTA"决定的（跨 CTA 与否由地址是 `.shared::cta` 还是 `.shared::cluster` 决定，与该前导序列正交），而是纯粹由 `sem × scope` 这一对修饰符组合决定——是 P0-1（控制位是全局资源）在 mbarrier 族的直接对应证据。
2. **hint 操作数触发单次编译器合成重试**：`mbarrier.try_wait` 补上可选的 `suspendTimeHint` 操作数后，即使 PTX 里没有写任何循环，ptxas 也会自动展开成"首次 `PHASECHK.TRYWAIT`→失败则 `NANOSLEEP`→二次 `PHASECHK`（无 `.TRYWAIT` 后缀）"的三指令序列。这是 tcgen05 B 类（编译器合成协议）在本族的一个轻量子形态：不是自旋循环+影子状态+trap 那种完整协议，但确实是"一条 PTX 内部隐含了控制流"，需要与普通 A 类分开建轴。

| 类别 | 指令 | PTX→SASS 结构 |
|---|---|---|
| A 单指令直译 | `mbarrier.init`、`mbarrier.inval`、`mbarrier.arrive.expect_tx`、`mbarrier.expect_tx`、`mbarrier.complete_tx`、`mbarrier.test_wait`（含 `.parity`） | 1 条 PTX → 1 条 SASS，qualifier 逐个对应修饰符或不进编码 |
| A 单指令直译（modifier 决定组大小 1→5） | `mbarrier.arrive`、`mbarrier.arrive_drop` | `sem=release ∧ scope=cluster` 时前置 4 条 `MEMBAR`/`ERRBAR`/`CGAERRBAR`，核心 `SYNCS.ARRIVE.TRANS64...` 恒为 1 条；`.shared::cluster`（remote）地址额外触发 `.RED` 后缀，与前导序列正交独立 |
| A 单指令直译（hint 触发单次合成重试） | `mbarrier.try_wait`（含 `.parity`） | 无 `suspendTimeHint` 时 1 条 `SYNCS.PHASECHK.TRANS64.TRYWAIT`；有 hint 操作数时自动展开为 3 条（首查 + `NANOSLEEP.SYNCS` + 二次查，二次查不带 `.TRYWAIT`） |

没有 tcgen05/TMA 意义上的 C 类完成节点（mbarrier 没有 `commit_group`/`wait_group` 式的批量完成标记指令——`arrive`/`complete_tx` 本身就是完成信号的载体），也没有 D 类零指令调度约束（9 个 opcode 都会产生至少一条真实指令；不存在类似 `tcgen05.fence` 那种纯调度边）。

## 实测助记符总表

### 生命周期骨架（`init` / `inval`）

| PTX | SASS（O0/O3 一致） | 备注 |
|---|---|---|
| `mbarrier.init.shared::cta.b64 [addr], count;` | `SYNCS.EXCH.64 URZ, [UR], UR_count` | `count` 为寄存器或立即数时形态相同；`.shared`（无 `::cta`）与 `.shared::cta` 拼写同 SASS（`t20`） |
| `mbarrier.init.shared::cta.b64 [addr], 0;`（**寄存器来源**，`t41`）或 `mbarrier.init...[addr], %reg_holding_0;` | 同上，正常发射 | **合法但语义可疑**：ptxas 不做运行时值检查 |
| `mbarrier.init.global.b64 ...`（`t46`） | 拒绝 | `State space incorrect for instruction 'mbarrier.init'` |
| `mbarrier.init.release.cluster...`（`t47`） | 拒绝 | `Illegal modifier '.cluster'`/`'.release'` for `mbarrier.init`——**`init` 不接受任何 sem/scope 修饰符**，是与 `arrive` 家族的结构性差异 |
| `mbarrier.inval.shared::cta.b64 [addr];` | `SYNCS.CCTL.IV [UR]` | 单指令，无操作数变体 |
| `mbarrier.inval.global.b64 ...`（`t42`） | 拒绝 | `State space incorrect for instruction 'mbarrier.inval'` |

### arrive 家族（`arrive` / `arrive_drop` / `arrive.expect_tx`）

三者共享同一条底层指令 `SYNCS.ARRIVE.TRANS64`，靠后缀区分角色；`sem`/`scope`/地址空间三个轴对三者的作用一致（已用 `arrive`/`arrive_drop` 双向校准）：

| 后缀形态 | 触发条件 | 探针 |
|---|---|---|
| `.A1T0` | 无显式 count 操作数（隐含到达数 1） | `t02`（默认）、`t11`（显式 `.release.cta`）、`t12`（`.relaxed.cta`，SASS 与 release 完全相同）、`t20`（`.shared` 拼写）、`t45`（无状态空间限定符，真正的 64 位 generic 地址） |
| `.ART0` | 显式 count 操作数（立即数或寄存器，SASS 相同） | `t15`（立即数 2）、`t16`（寄存器）、`t44`（寄存器值运行时为 0，**照样接受**） |
| `.TMASK.ART0` | `.noComplete`（要求显式 count） | `t18` |
| `.OPTOUT.A1T0` / `.OPTOUT.ART0` | `arrive_drop`，count 缺省/显式 | `t04` / `t26` |
| `.RED.A1T0` / `.RED.OPTOUT.A1T0` | 地址空间为 `.shared::cluster`（跨 CTA，经 `mapa` 取得），`arrive`/`arrive_drop` | `t19`、`t34`（`.cta` 作用域配 remote 地址，仍合法）、`t37`（`arrive_drop` remote） |
| 无后缀（裸 `SYNCS.ARRIVE.TRANS64`） | `arrive.expect_tx`（tx count 走第三操作数，立即数/寄存器同形） | `t03`（寄存器）、`t24`（立即数） |

前导序列（P0-1 核心证据）：

| sem | scope | 前导指令 | 探针 |
|---|---|---|---|
| `.release` | `.cta`（默认） | 无 | `t02`/`t11` |
| `.relaxed` | `.cta` | 无 | `t12` |
| `.release` | `.cluster` | `MEMBAR.ALL.CTA` + `MEMBAR.ALL.GPU` + `ERRBAR` + `CGAERRBAR`（4 条，恒定顺序） | `t13`（本地地址）、`t36`（`arrive_drop`）、`t19`/`t37`（remote 地址，`.RED` 与前导序列同时出现） |
| `.relaxed` | `.cluster` | 无 | `t21`（本地地址）、`t33`（remote 地址：`.RED` 后缀出现但前导序列不出现，证明 `.RED` 与前导序列是两个独立触发条件） |

`arrive.expect_tx` 的 remote 形态有独立约束：`.shared::cluster` 目标必须用 sink `_` 接收结果，写入真实寄存器会被拒绝（`t25`，见下表）。

### 计数簿记（`expect_tx` / `complete_tx`）

| PTX | SASS | 探针 |
|---|---|---|
| `mbarrier.expect_tx.shared::cta.b64 [addr], txCount;` | `SYNCS.ARRIVE.TRANS64.RED.A0TR RZ, [UR], R_tx` | `t05` |
| `mbarrier.complete_tx.shared::cta.b64 [addr], txCount;` | `SYNCS.ARRIVE.TRANS64.RED.A0TX RZ, [UR], R_tx` | `t06` |

两者只差 `.A0TR` 与 `.A0TX` 一个后缀，且**本地地址**（`.shared::cta`，非 remote）也带 `.RED`——这与 `arrive`/`arrive_drop` 里"`.RED` 只在 remote 地址出现"的规律不一致。结论：`.RED` 后缀的语义在不同 opcode 上被复用为不同含义（对 `arrive` 是"remote 到达"，对 `expect_tx`/`complete_tx` 可能是"仅计数、不消耗到达名额"的编译器内部记号），**不应跨 opcode 假设同一后缀同一语义**——这是描述符/后缀不透明性（TMA 文档 P0-2 教训）在本族的又一实例，本文只记录文本观测，不做跨指令的语义外推。

### wait 家族（`test_wait` / `try_wait`）

| PTX | SASS | 探针 |
|---|---|---|
| `mbarrier.test_wait.shared::cta.b64 p, [addr], state;` | `SYNCS.PHASECHK.TRANS64 Pd, [UR], R_state` | `t07` |
| `mbarrier.test_wait.parity.shared::cta.b64 p, [addr], parity;` | `SYNCS.PHASECHK.TRANS64 Pd, [UR], R_parity`（**与非 parity 形态文本相同**） | `t38` |
| `mbarrier.try_wait.shared::cta.b64 p, [addr], state;` | `SYNCS.PHASECHK.TRANS64.TRYWAIT Pd, [UR], R_state` | `t08` |
| 用户写自旋循环 `SPIN: try_wait; @!p bra SPIN;` | O3 下先出一条不带分支的 `PHASECHK.TRANS64.TRYWAIT`（首查），循环体内再出一条完全相同的 `PHASECHK.TRANS64.TRYWAIT`（peel 首次迭代） | `t39` |
| `mbarrier.try_wait...b64 p, [addr], state, hint;`（无用户循环） | `SYNCS.PHASECHK.TRANS64.TRYWAIT P0,...` → `@!P0 NANOSLEEP.SYNCS <hint>` → `@!P0 SYNCS.PHASECHK.TRANS64 P0,...`（**二次查无 `.TRYWAIT` 后缀**） | `t40` |

`test_wait`/`try_wait` 的 `.parity` 变体在助记符文本层面与 state 变体**不可区分**——差异（如果存在）只能落在编码字（`encoding_words`）里，本文不做字段级解码（同 tcgen05 审查对 word 1 高位的裁决：留给 `full_instructions` 原始编码，不在文档层断言字段布局）。

| `t22` | `mbarrier.arrive.global.b64 ...` | 拒绝 | `State space incorrect for instruction 'mbarrier.arrive'` |
| `t46` | `mbarrier.init.global.b64 ...` | 拒绝 | `State space incorrect for instruction 'mbarrier.init'` |
| `t42` | `mbarrier.inval.global.b64 ...` | 拒绝 | `State space incorrect for instruction 'mbarrier.inval'` |

| `t35` | `mbarrier.arrive...b64 %tok32, [addr];` 其中 `%tok32` 声明为 `.b32` | 拒绝 | `Arguments mismatch for instruction 'mbarrier.arrive'` |
| `t34`（补集抽样） | `mbarrier.arrive.release.cta.shared::cluster.b64 _, [remaddr];`（作用域 `.cta` 配 remote 地址，看似矛盾组合） | **接受**，`SYNCS.ARRIVE.TRANS64.RED.A1T0`，无前导 MEMBAR 序列 | 无诊断——见下方"发现" |
| `t30`（补集抽样） | `cvta.shared.u64 %gen, %addr32;`（32 位源配 `.u64` 目标类型） | 拒绝 | `Arguments mismatch for instruction 'cvta'`（探针自身操作数宽度错误，非 mbarrier 指令本身的边界，已用 `t45` 的正确写法补测生成地址） |

### 三处"预期非法却接受"的发现（P0-2 缺口对应）

1. **计数为 0 的静态检查只覆盖 PTX 文本里的字面立即数，不覆盖寄存器来源的运行时值**：`mbarrier.arrive` 对**字面量** `0`（`t31`）有专门诊断（`value '0' expected to be a non-zero positive`），但对**寄存器**里在编译期已知为 0 的值（`t44`，来自 `mov.u32 %n, 0;`）完全放行，生成正常的 `SYNCS.ARRIVE.TRANS64.ART0`。这不是"运行时才能确定"的场景——`t44` 里的 0 在 PTX 文本里就是常量，只是形式上经过了一次寄存器搬运,ptxas 也没有做常量传播后回查。这与 tcgen05 审查 P0-2"文本级检查可被寄存器中转绕过"是同一类缺口。
2. **`mbarrier.init` 完全没有非零检查**：`arrive` 的非零检查不是族内统一策略——`init` 对字面量 `0`（`t41`/`t43`）和寄存器来源的 `0` 都不拒绝，正常发射 `SYNCS.EXCH.64`。一个 expected-count 为 0 的 barrier 语义上永远不会完成（或立即完成，取决于运行时约定），属于典型的"合法语法但可疑语义"，静态层不拦截。
3. **`.cta` 作用域配 `.shared::cluster`（remote）地址是合法组合**（`t34`）：直觉上"用 CTA 可见性写跨 CTA 的远程 barrier"像是自相矛盾的组合，容易在设计矩阵里被主观排除；实测 ptxas 接受并正常降为 `.RED.A1T0`（不带前导 MEMBAR 序列，因为触发前导序列的是 `scope=cluster`，与该探针的 `scope=cta` 无关）。这是本文按规范阅读会漏掉、必须靠穷举才能发现的合法面实例（对应 TMA 文档里 `tile::gather4` 之于 prefetch 的同类教训）。

## 对抗式审查缺口在本族的落实

| tcgen05 缺口 | 本族对应设计 |
|---|---|
| P0-1 控制位是全局资源 | `sem × scope` 的四指令前导序列（`t13` vs `t21`）证明控制位由修饰符**组合**而非单个修饰符决定；旗舰套件把 `sem × scope` 做满因子而非各自单因素抽查；runtime 保留全函数 128-bit 编码（`full_instructions`），前导序列的控制字差分不需要重跑实验 |
| P0-2 合法面未证伪 | 负向探针登记 `expected_diagnostic` 子串；`t44`/`t41`/`t34` 三个"预期拒绝却接受"的发现已写入正向矩阵并在负向目录里保留对照（`t31` 立即数 0 仍按预期拒绝，凸显立即数/寄存器的不对称）；套件另设 ≥2 条合法面补集抽样（remote+cta scope、count 寄存器为 0） |
| P0-3 组合/序列不足 | 旗舰套件的核心轴本身就是 `sem × scope × state_space × count_form × token_use × noComplete` 六维组合矩阵，而非孤立轴抽查；expanded 追加在飞多 barrier（`t28`）与 guard（`t27`）序列上下文 |
| P1-1 模板未受控 | expanded 含 `template_wide`（加宽/打乱参数签名）case；已记录一个**结构性边界**：`t29` 显示模板加宽对本指令没有可观测扰动，因为 mbarrier 地址来自编译期固定的 `.shared` 符号而非参数——这是"P1-1 轴存在但该指令对它不敏感"的合法结论，不是漏做 |
| P1-2 重物化前提 | `mbar` 地址、`count`/`tx` 数值、token 各有 indirect producer case（`add.u32` 派生地址、`tid` 派生坐标、寄存器搬运的数值） |
| P2-1 单版本 | 套件与 TMA/tcgen05 相同接受 `--ptxas/--nvdisasm` 路径参数，跨版本差分只需换工具链重跑 |

## 每指令研究重点

### `mbarrier.init`（A，`DESIGNED`；作为旗舰套件 `mbarrier.arrive/thor_ptx90/` 的必需前置指令已被 O0–O3 反复编译验证，但尚无独立以 `SYNCS.EXCH.64` 为目标 pattern 的 `suite_spec.py`）

1. 完全没有 sem/scope 轴（`t47`），是族内最简单的指令；独立套件的轴应聚焦 state space 拼写等价性（`.shared` vs `.shared::cta`，已证同形）与 count 来源（立即数/寄存器/间接）。
2. `count=0` 不被拦截（`t41`/`t43`）：需要在文档与生成器里明确标注这是"合法但语义可疑"的构造，不能进候选实现集合（对应族 README 完成门槛）。
3. `.align` 要求（`.shared .align 8 .b64`）是否有更细粒度的合法/非法边界（如 `.align 4`），本轮未测，列入路线图。

### `mbarrier.arrive`（A，旗舰套件已建，`FRAMEWORK_VALIDATED`）

1. `sem × scope` 前导序列已确认（`t02`/`t11`/`t12`/`t13`/`t21`），是本套件的第一轴。
2. `.shared::cluster`（remote）地址的 `.RED` 后缀与前导序列相互独立（`t19`/`t33`/`t34`），套件需要把"地址空间"和"scope"当成两条正交轴，不能合并成一条"是否跨 CTA"的轴。
3. count 操作数形态（缺省/立即数/寄存器）只影响 `.A1T0`/`.ART0` 二选一，立即数与寄存器彼此 SASS 相同（`t15`/`t16`）——已证的"重物化前提"（P1-2）。
4. token 消费方式（落地 `st.global` vs `_` 丢弃）都不消除指令本身（`t02` vs `t17`），因为 arrive 是副作用指令；但目的寄存器从 `R2` 变 `RZ`，是本套件的一个观测轴而非归属判据。
5. `count=0` 的立即数/寄存器不对称（`t31` vs `t44`）是本套件负向 + 补集抽样的核心案例。
6. guard 谓词：O0 走分支+`BSYNC.RECONVERGENT`，O3 收敛为 `@!P0` 前缀（`t27`），与 TMA/tcgen05 已确立的"谓词落到 uniform predicate"规律一致。
7. 待补：`.noComplete` 与 remote 地址（`.shared::cluster`）的组合是否合法，本轮未测；`sem × scope × noComplete` 三维交叉暂未穷举，留路线图。

### `mbarrier.arrive.expect_tx`（A，`DESIGNED`）

1. 底层与 `arrive` 共享 `SYNCS.ARRIVE.TRANS64`，但没有 `.A1T0`/`.ART0` 后缀——tx count 走真实第三操作数（`t03`/`t24`），需要单独的归属 pattern（`SYNCS.ARRIVE.TRANS64` 精确匹配且第三操作数非 `RZ`，否则会与裸 `arrive` 误命中同一 target_pattern）。
2. remote 形态强制 sink 目的操作数（`t25`），是需要在生成器里对 `.shared::cluster` case 特殊处理 token 字段的硬约束。
3. `.noComplete` 非法组合（`t32`）已校准，直接进负向目录。
4. sem/scope 前导序列是否对本指令同样成立（本轮只测了本地默认形态），需要补 `.release.cluster` 探针。

### `mbarrier.arrive_drop`（A，`DESIGNED`）

1. `.OPTOUT` 后缀恒定叠加在 `arrive` 的后缀体系之上（`.A1T0`→`.OPTOUT.A1T0`，`.ART0`→`.OPTOUT.ART0`，remote 时 `.RED.OPTOUT.A1T0`），三个后缀正交组合已用 `t04`/`t26`/`t36`/`t37` 四点交叉确认，足以支撑"后缀独立叠加"的假设，但严格覆盖需要把 count×remote×sem/scope 做满因子，留路线图。
2. arrive_drop 用于"提前退出的线程减少后续 phase 期望计数"（README 口径），静态层无法验证这与普通 arrive 在运行时计数簿记上的差异——STATIC_ONLY 边界的典型案例。

### `mbarrier.expect_tx`（A，`DESIGNED`）

1. 独立于 arrive 的纯计数操作，`.RED.A0TR` 后缀在本地地址下就出现（`t05`），与 `arrive` 家族"`.RED` 仅 remote 触发"的规律不一致，是"后缀跨指令不同义"的证据来源之一，需要在规则挖掘阶段把 `expect_tx`/`complete_tx`/`arrive`/`arrive_drop` 的归属分开建表，不能共用同一张后缀语义表。
2. sem/scope 对本指令的前导序列触发条件未测，留路线图（预期与 arrive 家族一致，但"预期"不能代替实测，按 P0-2 口径必须补测才能写进合法面）。

### `mbarrier.complete_tx`（A，`DESIGNED`）

1. 与 `expect_tx` 唯一差异是 `.A0TX` 对 `.A0TR`（`t06` vs `t05`），一字之差,必须用精确子串匹配（`target_patterns` 里不能只写 `SYNCS.ARRIVE.TRANS64.RED`，否则 `A0TR`/`A0TX` 会被合并统计）。
2. transaction byte 计数的运行时正确性（与 TMA 的 `mbarrier::complete_tx::bytes` 完成机制配对）不在静态范围内；本目录只持有指令选择结论，运行时字节记账语义由 `02_tma` 与本族共同的运行时边界声明覆盖。

### `mbarrier.test_wait`（A，`DESIGNED`）

1. state 与 `.parity` 变体助记符文本相同（`t07` vs `t38`），归属层面无法靠反汇编文本区分——这是需要在文档里显式承认的观测局限，不能声称"已验证 parity 有独立编码"。
2. sem（`.acquire`/`.relaxed`）与 scope 轴未系统测试（本轮只用了默认形态），留路线图；`arrive` 系已证 `.acquire` 是被拒绝的（`t23`)，`test_wait`/`try_wait` 预期恰好相反（只接受 `.acquire`/`.relaxed`，不接受 `.release`）——这是一个"规范阅读得出的预期"，按 P0-2 要求必须补探针证伪或证实才能写进合法面，本轮未做，明确标注为待验证假设。

### `mbarrier.try_wait`（A / 轻量 B 混合，`DESIGNED`）

1. 无 hint 时单指令 `.TRYWAIT`（`t08`），有 hint 时编译器合成三指令重试序列（`t40`），是本族里对"1 条 PTX 是否等于 1 条 SASS"这一假设最直接的证伪，套件设计必须把"是否带 hint 操作数"当作独立轴，而不是普通修饰符。
2. 用户手写自旋循环会在 O3 下产生"首查 + 循环体内重复查询"的 peel 结构（`t39`），与 hint 触发的编译器合成重试是两种不同机制（前者循环结构来自用户 PTX 的 `bra`，后者来自 ptxas 内部展开），文档与生成器都需要分开记录，不能混为一谈。
3. `.parity` 变体同 `test_wait`，文本不可区分。

### `mbarrier.inval`（A，`DESIGNED`）

1. 单指令 `SYNCS.CCTL.IV`，唯一已测非法边界是 `.global` 状态空间（`t42`）。sem/scope 轴预期不存在（`inval` 与 `init` 同属生命周期骨架，`init` 已证无 sem/scope），需要一条负向探针证实（未测，留路线图）。
2. `inval` 前后的顺序约束（README"关闭前后的顺序约束"）属于运行时/序列语义，STATIC_ONLY 范围之外，静态层只能确认指令本身能否独立编译。

## 边界声明

全部结论为 `STATIC_ONLY`：编译通过 + 归属成功不证明 barrier 到达计数、transaction byte 记账、phase/parity 翻转或跨 CTA 可见性的运行时语义。未初始化 barrier、错误参与数、非法 phase 等运行时约束只能作为负向 corpus 的候选来源（若能被 ptxas 静态拒绝则登记诊断），不能作为候选实现集合的正向 case——这与族 README"本族完成门槛"的表述一致。`count=0`（`t41`/`t43`/`t44`）与"`.cta` 作用域配 remote 地址"（`t34`）虽然静态合法，但运行时语义（是否立即完成、是否触发未定义行为）不在本文与套件的验证范围内，只记录"静态接受"这一事实。`test_wait`/`try_wait` 的 `.parity` 变体因反汇编文本与 state 变体不可区分，任何依赖"能从 SASS 文本反推 parity/state 语义"的下游假设都超出本文档证据范围。

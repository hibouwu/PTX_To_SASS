# PTX→SASS 实验设计详细规范

> 本文是 [实验设计](实验设计.md) 的可执行规范。
> 设计语义以主文档为准；数据对象、字段、ID、约束、状态、成本和覆盖公式以本文为准。
>
> 阅读约定：正文以中文术语为主；代码块和反引号中的英文保留为稳定字段名、枚举值或检索关键词。代码块旁的中文说明用于解释含义，不替代这些机器可读名称。

## 实验目的

本实验的目标不是建立一张静态的“PTX 操作码 → SASS 操作码”对照表，而是在固定编译环境和版本化测试模型下，系统发现并分类受上下文影响的 PTX→SASS 目标代码落地（lowering）变体。需要观察的结果包括核心指令变化、操作数折叠、融合、消除、寄存器类别转换，以及操作数、谓词、线程参与和完成确认等准备或协议序列。

实验产物是带有上下文条件和证据的**候选目标代码落地记录**：

```text
PTX 语义模式
+
已测试的上下文条件
+
源码覆盖信息
→
已观测的 SASS 效应图
+
映射拓扑与多标签语义角色
+
相互独立的证据、实现与验证状态
+
区分执行路径和统计作用域的成本记录
```

在尚未形式化并穷举一个有限输入全集之前，结果只能称为：

> 在所声明测试空间和固定编译环境下观测到的候选 SASS 目标代码落地变体集合。

本实验本身不证明目标架构上的绝对完整性，不单独证明候选的语义正确性，也不证明候选是最优实现。语义正确性需要通过独立的规范推理、差分执行或专门的正确性判定器（oracle）验证；最优性则需要后续的成本模型和选择算法验证。

## 研究对象与结果口径

优化编译后的 PTX 与 SASS 不是一对一关系。一条 PTX 指令可能被删除、展开为多条 SASS、与其他 PTX 融合、被复制或移动；一条 SASS 也可能服务于多个 PTX 指令实例（occurrence）。因此，主要记录单位是**从源码模式组（source pattern group）到 SASS 效应图的目标代码落地实例**，同时保留组内每个目标指令实例的对应关系，而不是强行给每个实例复制一份互斥的效应切片。

最低限度需要记录以下数据关系：

```text
source_member(
    pattern_group_id,
    occurrence_id,
    source_role
)

effect_node(
    lowering_instance_id,
    node_id,
    function_id,
    basic_block_id,
    address,
    opcode,
    path_condition
)

effect_edge(
    lowering_instance_id,
    source_node,
    destination_node,
    relation_type
)

attribution(
    lowering_instance_id,
    pattern_group_id,
    occurrence_id,
    node_id,
    slice_membership,
    role_tags,
    relation_tags,
    evidence_ids
)
```

`effect_node` 的主键是 `(lowering_instance_id, node_id)`；边（edge）和归属关系（attribution）中的节点外键，也都在同一个目标代码落地实例内解析。`lowering_instance_id` 已绑定代码产物与 `E_analysis_id`，因此不同分析版本不会共用节点地址命名空间，也不会跨实例误连节点。`relation_type` 至少覆盖数据、守卫、控制、内存序、线程参与和完成确认等边。共享的 SASS 节点在同一个目标代码落地实例内只存一次；成本统计以目标代码落地实例、可达路径或内核为作用域，不能在多个 PTX 指令实例之间直接重复相加。

SASS 效应图中的节点和边允许同时使用多个角色标签：

```text
CORE_OPERATION
OPERAND_PREPARATION
PREDICATE_PREPARATION
PATH_DISPATCH_FALLBACK
PARTICIPATION_PROTOCOL
ORDERING_VISIBILITY_PROTOCOL
COMPLETION_PROTOCOL
RESULT_RECONSTRUCTION
CALL_ABI_PROTOCOL
RESOURCE_MANAGEMENT_PROTOCOL
ROLE_UNRESOLVED
```

`slice_membership` 独立记录 `IN_SLICE`、`CONTEXT_ONLY` 或 `AMBIGUOUS`。对于 `tcgen05`、TMA、mbarrier、barrier 和集合操作（collective）等复杂指令，线程参与、顺序保证、路径分派或完成确认序列可能属于语义实现本体，不能仅凭操作码名称就把它们排除为无关的辅助代码。

每个目标代码落地实例分别生成以下结果投影和版本化结果指纹（fingerprint）。这些投影代表不同观测视角，不假定彼此形成严格的包含关系：

```text
mapping_topology:
    源码模式、核心操作/完整切片的数量关系、备选执行路径，
    eliminated / absorbed / fused / expanded / shared /
    replicated / moved / unknown 等关系

effect_graph:
    SASS 节点、基本块、路径条件，以及 data/guard/control/
    memory-order/participation/completion 等类型的边

lowering:
    对地址、标签和无关编号规范化后的操作码、修饰符、
    操作数形式、定义—使用关系和 CFG 形态

allocation:
    在 lowering 投影上保留 GPR/UR、P/UP、寄存器对/元组、
    与寄存器组冲突有关的相等关系、谓词极性和路由/转换，
    但允许对物理编号作同构重命名

schedule_control:
    指令发射顺序、reuse、等待/读/写屏障、yield、stall
    和显式 DEPBAR；同时记录解码器来源与解码状态

exact:
    原始 cubin/段字节、逐指令编码、物理寄存器编号、
    地址、符号、重定位信息和原始反汇编
```

控制字段的原始字节是基础证据；若可读的复用、屏障、让出和停顿字段来自社区逆向解码器，必须记录解码器名称、版本、哈希和架构适用范围。无法解码时保留 `RAW_ONLY`，不能仅凭原始编码就宣称已经理解控制字段。

删除、吸收、融合、展开、共享、移动、无法归属，以及未实现预期实验处理条件等情况，都必须显式记录。当核心操作近似为 `1:1`、但完整 SASS 效应图为 `1:N`，或不同路径具有不同数量关系时，应并列报告，不能压缩成单个数字。源代码行号或 `.loc` 信息只能作为辅助证据，不能单独充当 PTX→SASS 因果归属规则。

## 对象层级与变量角色

实验数据结构必须区分以下六个层级。每个字段都需要唯一的 `field_id` 和 `field_role`，不能因为它同时出现在生成器、适用性判断和结果报告中而重复计数。

1. **环境分层**：架构能力、PTX 源码契约、编译流水线、观测工具，以及动态实验所用的 GPU、驱动程序和测量工具。每个完整的环境元组分别形成一个结果集合。
2. **目标身份**：指令族、精确语义形态，以及目标在模式中的逻辑角色。改变语义形态意味着改变研究对象，而不是改变同一实验种子的上下文。
3. **可操纵的静态程序上下文**：操作数实例化、数据流、控制流图（CFG）与守卫、内存关系、协议生命周期、资源压力构造，以及函数与应用二进制接口（ABI）上下文。
4. **测试骨架与测量设计**：基线测试骨架、结果观测点、空白/阳性/阴性对照和重复编译。它们属于测量干预或区组变量，不是目标程序天然具有的语义属性。
5. **运行负载与运行时实现事实**：输入分布、启动与线程簇配置、预期路径，以及实际的一致性、活动线程掩码、动态别名/对齐和执行路径。静态 `ptxas` 目标代码落地不会响应仅在运行时成立、但在编译期不可证明的事实；这类字段主要用于语义正确性判定和动态成本测量。
6. **编译后的中介变量与响应结果**：最终的 GPR/UR/P/UP 类别、立即数编码或物化方式、实际使用拓扑与存活区间、溢出、融合、调度，以及完整的 SASS 效应图。

对于第 3 类变量，生成器声明的是预期实验处理；只有相应的处理实现检查结果为 `REALIZED` 时，该实验用例才能用于估计这一因素的条件效应。第 5 类运行时事实不得反过来冒充静态输入。第 6 类只能作为结果或中介变量，不能作为可直接指定的 PTX 因素。

### 原维度划分的裁决摘要

原清单的覆盖面基本合理，但存在三类结构性冗余：同一数据流关系被生产者、定义—使用关系、相邻指令关系和控制流/存活性重复描述；GPR/UR/P/UP、溢出和物化等结果被当作输入；环境、测试骨架和运行时实现事实被混入同一个“上下文”层。规范化后的唯一归属如下：

| 原维度或字段组 | 裁决 | 唯一归属 |
|---|---|---|
| 指令自身的数据类型、限定符链、形状、内存序/作用域等 | 保留，但不是上下文因素 | `SF.*` / `semantic_form_id` |
| 普通操作数、取值、修饰符和身份关系 | 保留；地址操作数单独拆分 | `CTX.operand/value.*` |
| 生产者、定义—使用、消费者、相邻模式和局部存活性 | 合并；具体短模式降为组合方案 | `CTX.dataflow.*` + `CTX.cfg.*` |
| 谓词、守卫和线程参与关系 | 保留静态构造；实际活动线程集合拆到运行时 | `CTX.guard/participation.*` + 运行时试验事实 |
| GPR/UR/P/UP、转换、立即数编码、寄存器溢出、最终存活区间 | 从因素表移除 | `OBS.*` 中介变量/结果 |
| 内存语义形态、地址、别名和相邻访问 | 拆成目标固有语义、地址构造和访问关系 | `SF.*` + `CTX.address/memory.*` |
| 异步、张量和屏障操作 | 拆成目标语义形态、周边协议状态和结果序列 | `SF.*` + `CTX.protocol.*` + `OBS.*` |
| 控制流图边界与资源压力 | 保留；目标边与辅助压力代码分开 | `CTX.dataflow/cfg.*` + `CTX.resource.*` |
| ABI、链接、源码指示符与 RDC/LTO | 源码上下文与编译流水线分离 | `CTX.function/abi/directive.*` + `E_codegen` |
| 编译器、观测工具和硬件/运行时 | 拆为三个环境对象 | `E_codegen` / `E_analysis` / `E_runtime` |
| 测试骨架、结果观测点、对照和运行时输入 | 不进入实验种子；分别形成测量区组和运行负载 | `FX.*` / `runtime_workload_id` |

## 实验空间组织

实验空间不采用“所有指令依次经历同一组上下文层级”的统一阶梯，也不把所有候选因素平铺成一个全局笛卡尔积。实验按**环境分层 + 语义实验种子 + 生成器归属 + 适用的原子因素 + 测试骨架/测量区组**组织。

### 环境分层

静态代码生成环境元组定义如下：

```text
E_codegen = {
    codegen_environment_schema_version,
    architecture_contract: {
        target_sm,
        target_feature_set
    },
    source_contract: {
        ptx_isa,
        ptx_target,
        address_size
    },
    compiler_pipeline: {
        pipeline_stage,
        toolkit_label,
        ptxas_version,
        ptxas_binary_hash,
        device_linker_version_and_hash,
        driver_jit_version,
        optimization_level,
        codegen_options,
        debug_line_instrumentation_mode,
        relevant_environment_variables,
        rdc_lto_mode,
        register_limit
    }
}

E_analysis = {
    analysis_environment_schema_version,
    E_codegen_id,
    observer: {
        disassembler_name_version_binary_hash_and_canonical_argv,
        parser_schema_version_implementation_hash_and_config,
        attribution_schema_version_implementation_hash_and_config,
        fingerprint_schema_versions_implementation_hash_and_config,
        control_decoder_name_version_binary_hash_config_and_arch_support
    }
}
```

`toolkit_label` 用于记录发布包来源；真正用于结果归因的是当前阶段实际使用的工具二进制文件及其哈希。`toolkit_label`、`ptxas_version` 和 `ptxas_binary_hash` 可以同时记录，但不能视为三个彼此独立、可自由组合的因素。`codegen_options` 使用规范化后的命令行参数，即移除输出路径、临时文件名等不影响语义的参数；完整的原始命令行仍作为证据保存。离线 `ptxas`、设备链接后的 cubin，以及驱动程序即时编译（JIT），分别属于不同的 `pipeline_stage`。

`target_sm`、`ptx_target`、PTX ISA 和目标特性之间存在合法性约束，因此还需要维护版本化的环境兼容矩阵。跨 SM 的差异同时包含架构能力变化和面向目标架构的代码生成变化；只有在架构与源码契约保持不变、仅改变编译器或编译选项时，才适合近似解释为编译器策略变化。

每个完整的 `E_codegen` 分别生成一套代码生成产物；每个 `E_analysis` 形成一套可复现的分析结果。只改变观测工具或解析器时可以复用 cubin，但必须生成新的分析身份。`O0` 与 `O3` 属于两个不同的 `E_codegen`，而不是同一环境内的两份输出；编译次数、反汇编文件数和分析文件数，也必须与实验用例数、代码生成次数和 cubin 数量分开统计。

只要报告动态语义或性能，还必须另外固定运行时元组：

```text
E_runtime = {
    runtime_environment_schema_version,
    gpu_sku_and_revision,
    driver_version,
    clock_power_thermal_policy,
    runtime_library_versions,
    profiler_and_metric_versions
}
```

`target_sm` 不能替代实际 GPU 和真实运行条件。纯静态目标代码落地实验可以不生成 `E_runtime`，但此时成本只能通过静态代理指标报告，不能报告实测延迟或吞吐量。

三个环境对象分别使用 `E_codegen_id = H(E_codegen)`、`E_analysis_id = H(E_analysis)` 和 `E_runtime_id = H(E_runtime)`；各自的数据结构版本已经包含在参与哈希的对象中。`H` 是后文定义的规范化内容哈希。不得使用一个含义不明确的通用 `environment_id` 混合这三类环境。

### 目标身份与实验用例身份

正式研究单位不是 PTX 文件，测试骨架也不纳入目标的语义身份。标识分为以下五层：

```text
instruction_family_id
    = H(instruction_family_schema_version,
        canonical opcode family)

semantic_form_id
    = H(semantic_form_schema_version,
        instruction_family_id,
        {
            opcode / sub-op,
            完整合法 qualifier chain,
            operand and result role/shape,
            instruction-specific semantic control / side operand
        })

seed_id
    = H(seed_schema_version,
        semantic_form_id,
        logical target role)

logical_case_id
    = E_codegen_id
    + seed_id
    + canonical complete static context assignment
    + fixture_id
    + sink_id
    + observability_track

case_id
    = logical_case_id
    + source_variant_id
    + codegen_replicate_id
```

逻辑目标角色（`logical target role`）用于区分同一语义形态在指令模式中作为生产者、中心目标、消费者或协议节点时的不同研究角色。改变指令固有的语义形态会产生新的 `semantic_form_id`；若要研究数据类型、状态空间、舍入模式或形状的差异，应在同一个 `instruction_family_id` 下进行跨语义形态配对，而不能把这种差异解释为同一实验种子的上下文效应。

这里的“指令专属语义控制”是指会改变操作模式的字段；普通算术字面量、地址偏移、守卫、生产者和消费者都进入上下文赋值，不进入 `semantic_form_id`。

每个实际生成的 PTX 目标指令实例都有独立的 `occurrence_id` 和稳定定位信息。一个 PTX 文件可以包含多个指令实例，一个测试骨架也可以被多个实验种子和实验用例复用；因此文件数、实验种子数、实验用例数和指令实例数不能相互替代。

重复运行分析工具和开展运行时试验时，使用以下独立标识：

```text
occurrence_id =
    H(occurrence_identity_schema_version,
      logical_case_id, target_slot,
      semantic_form_id, normalized_source_AST_path)

pattern_group_id =
    H(pattern_group_schema_version,
      logical_case_id, ordered source occurrence IDs, source roles)

codegen_unit_id =
    H(codegen_unit_schema_version,
      E_codegen_id, packaging_manifest,
      ordered case_ids)

source_variant_id =
    H(source_variant_schema_version,
      logical_case_id,
      exact_generated_source_hash)

source_variant_metadata(
    source_variant_id,
    source_variant_kind,
    canonical_transformation_spec,
    source_variant_matching_key,
    transformation_provenance
)

codegen_unit_member(
    codegen_unit_id,
    case_id,
    member_ordinal
)

analysis_execution_id =
    H(analysis_execution_schema_version,
      code_artifact_hash, E_analysis_id, analysis_replicate_id)

analysis_result_id =
    H(analysis_result_schema_version,
      case_id, code_artifact_hash, E_analysis_id,
      normalized_analysis_output_hash)

analysis_execution_result(
    analysis_execution_id,
    case_id,
    analysis_result_id
)

lowering_instance_id =
    H(lowering_instance_schema_version,
      pattern_group_id, analysis_result_id)

runtime_trial_id =
    H(runtime_trial_schema_version,
      case_id, code_artifact_hash, E_runtime_id,
      runtime_workload_id, runtime_replicate_id)
```

`normalized_analysis_output_hash` 根据解析器和归属分析产生的规范化数据计算，并明确排除 `analysis_result_id`、`lowering_instance_id` 以及其他由该哈希派生的标识，避免循环定义。对同一产物和同一配置执行多次分析时，如果所得数据完全相同，可以关联到同一个 `analysis_result_id`；但分析执行次数与唯一分析结果数仍需分别统计。

这样，改变解析器不会伪装成新的代码生成实验用例，改变运行输入或硬件测量条件也不会增加静态上下文覆盖率。

### 测试骨架、结果观测点与公共基础设施

所有生成器都共享以下基础设施，但不要求使用同一套具体测试骨架：

```text
规范合法性检查
可观测性保障
目标指令实例识别
归属分析对照
数据来源与结果观测点控制
原始产物留存
```

```text
fixture_id = H({
    fixture_schema_version,
    normalized_source_template_hash,
    target_slot,
    source_control_contract
})

fixture_family_id = H({
    fixture_family_schema_version,
    semantic_matching_contract,
    allowed_fixture_ids,
    blocking_and_balance_policy
})

sink_id = H({
    sink_schema_version,
    normalized_sink_template,
    visibility_contract
})

source_coverage_id = H({
    source_coverage_schema_version,
    declared_source_and_fixture_family_manifest,
    denominator_definition,
    sampling_or_holdout_policy
})

measurement_block_id = H({
    measurement_block_schema_version,
    fixture_family_id,
    ordered_fixture_ids,
    ordered_sink_ids,
    observability_tracks,
    required_control_classes
})
```

只有会改变所生成 PTX 或静态可观察性契约的字段，才进入 `fixture_id` 或 `sink_id`。生成器名称和版本、归属分析的实现与控制信息、分析配置，以及纯判定器实现，都作为分析或运行时来源信息保存；如果某种归属标记或伪处理对照确实改变了源码，这一变化必须已经反映在规范化源码模板哈希中。测试骨架清单不包含具体因素赋值、环境、结果观测点或重复编号。同一个模板包含多个目标位置时，必须使用不同的 `target_slot` 加以区分。

`fixture_id`、`sink_id` 和 `observability_track` 都属于测量设计。更换配对基线或结果观测点不会改变 `seed_id`，而是在同一实验种子下产生新的实验用例，从而用于估计观测方式本身造成的影响。测量区组至少记录：

```text
fixture_id
fixture_family_id
sink_id
measurement_block_id
observability_track: preserved | optimization
control_class:
    none | blank | sham | positive |
    normalization_negative | interaction_fault | protocol_fault
source_coverage_id
source_variant_id
codegen_replicate_id
```

`source_variant_id` 用于区分同一逻辑设计的不同源码变体（source variant），例如字母重命名、标签名称变化、等价常量写法变化或规范化阴性对照。计算 `exact_generated_source_hash` 时，可以移除已声明仅用于传输的临时路径和换行差异，但必须保留所有有意测试的词法单元或拼写变化。`source_variant_matching_key = H(source_variant_matching_schema_version, source_variant_kind, canonical_transformation_spec)` 不包含环境、逻辑实验用例或精确源码哈希，用于跨语义形态或跨环境的一对一配对。源码变体不会增加逻辑实验用例数或静态因素覆盖率。`codegen_replicate_id` 只表示同一精确源码变体的重复代码生成，不进入 `fixture_id` 或 `logical_case_id`。一次实际编译对应一个 `codegen_unit_id`；如果多个实验用例被打包进同一次编译，则使用 `codegen_unit_member` 记录成员。它们共享同一次编译调用，统计独立性时必须按代码生成单元聚类，不能视为多次独立编译。运行时重复另用 `runtime_replicate_id`，这三类标识不得复用。

所有配对对照都使用显式关联，不能依靠名称推断：

```text
control_link(
    control_source_variant_id,
    treatment_source_variant_id,
    control_class,
    matched_coordinate_ids,
    intended_difference
)
```

空白对照、伪处理对照等对照用例，可以携带实验处理的静态上下文投影作为匹配键，但不会增加因素水平覆盖率或因素组合覆盖率。对于在对照中按设计被删除的目标字段，不执行“源码是否实现实验处理”的判定。

### 生成器归属与适用性标签

原有分类只保留为工程实现中的唯一生成器归属，不作为科学因素、互斥语义分类或因果结论的聚合轴：

```text
A：寄存器局部的算术、逻辑、转换与数据移动目标
M：普通内存访问、原子与归约目标
C：谓词、分支、控制流与 warp 集合操作目标
P：张量、异步搬运、屏障与协议目标
F：调用、返回与 ABI 专属目标
```

类别 `P` 继续按生成基础设施细分为：

```text
P-Tensor
P-AsyncMove
P-Barrier
P-Collective
```

RDC、设备链接和链接时优化（LTO）不属于 `F`，而属于 `E_codegen.compiler_pipeline`。普通算术指令即使位于设备函数中、被其他函数调用或跨越 LTO 边界，仍由 `A` 生成，只额外增加函数/ABI 适用性标签。`C` 中的 `vote`、`shuffle`、`redux` 等指令本身以集合操作为目标语义；`P-Collective` 只表示为其他复杂目标提供线程参与或选举支持的生成器。

必须维护版本化的 `semantic_form_id → generator_owner` 全覆盖路由表，并明确覆盖纹理/表面、互连结构、栈操作、特殊寄存器、视频和其他杂项指令族。任何无法唯一分配生成器的语义形态，都必须进入“未解决路由项”清单，不能因为不适合 A/M/C/P/F 的命名体系而被静默漏测。

科学分析中的适用性使用彼此独立、允许多标签的 `semantic_family` 和 `implementation_domain_tags`：

```text
canonical factor-group tags:
    operand_instantiation
    dataflow_topology
    guard_cfg_participation
    memory_relation
    protocol_lifecycle
    resource_construction
    function_abi_context

observed-domain tags:
    operand_routing
    predicate_routing
    allocation
    scheduling_control
    dispatch_fallback
    ordering_visibility
    completion
```

前一组决定哪些输入因素适用于当前目标；后一组只决定结果如何投影和标注。寄存器路由、溢出和完成确认序列等编译后现象，不得反过来作为输入叠加条件。

例如：

```text
add.u32:
    generator_owner = A
    factor_groups = operand_instantiation,
                    dataflow_topology,
                    guard_cfg_participation,
                    resource_construction

ld.global:
    generator_owner = M
    factor_groups = operand_instantiation,
                    dataflow_topology,
                    guard_cfg_participation,
                    memory_relation

atom.global:
    generator_owner = M
    factor_groups = dataflow_topology,
                    guard_cfg_participation,
                    memory_relation

tcgen05.mma:
    generator_owner = P-Tensor
    factor_groups = operand_instantiation,
                    dataflow_topology,
                    guard_cfg_participation,
                    protocol_lifecycle,
                    resource_construction

TMA load:
    generator_owner = P-AsyncMove
    factor_groups = operand_instantiation,
                    memory_relation,
                    guard_cfg_participation,
                    protocol_lifecycle

call:
    generator_owner = F
    factor_groups = dataflow_topology,
                    guard_cfg_participation,
                    resource_construction,
                    function_abi_context
```

普通 `add` 不需要遍历内存作用域；TMA 也不能因为归属于协议类生成器，就遗漏地址、对齐、状态空间和代理关系等因素。

### 稳定标识与规范化

所有按内容寻址的稳定 ID 均使用：

```text

```

`canonical_json` 必须对字段名排序，对无序集合排序并去重，统一枚举值和单位，显式写出默认值，同时排除绝对路径、时间戳、随机临时名称和说明文字。任何会改变语义或结果指纹的数据结构修改，都必须提升对应的 `schema_version`。

完整的原始命令行参数、环境变量、标准输出/错误输出、产物绝对路径和时间戳，仍作为来源信息保存，但不进入逻辑实验用例身份。生成后的 PTX、cubin 和转储文件哈希属于产物身份，也不能替代实验设计身份。

```text
logical_case_id =
    H(case_schema_version,
      E_codegen_id,
      seed_id,
      complete_static_context_assignment,
      fixture_id,
      sink_id,
      observability_track)

case_id =
    H(case_realization_schema_version,
      logical_case_id, source_variant_id, codegen_replicate_id)
```

`complete_static_context_assignment` 必须为适用性矩阵当前行中的每个适用 `CTX.*` 因素给出唯一、规范化的水平取值；`UNBOUND` 不得进入实验用例，不适用状态也不能伪装成普通因素水平。该赋值不包含 `SF.*`、`FX.*`、`RUN.*`、`ENV.*` 或 `OBS.*`：这些字段分别由实验种子、测量区组、运行负载、环境对象和结果对象承载。`logical_case_key` 是上述 `logical_case_id` 哈希输入元组经过规范化、但尚未哈希的表示。

## 规范化因素模型

以下内容用于定义原子因素注册表（atomic factor registry），并不要求每条指令遍历同一套测试全集。一个因素只有同时具备唯一的 `factor_id`、有限的 `level_schema`、合法性与适用性约束，以及处理实现检查，才可以进入实验用例生成器。环境字段、语义形态字段、编译后结果和由其他因素推导出的组合方案，不计入上下文因素数量。

字段按下列命名空间组织：

```text
SF.*:
    语义形态字段（semantic form fields）

CTX.*:
    可操纵的静态程序上下文

FX.*:
    测试骨架、结果观测点与测量控制

RUN.*:
    运行时实现情况与判定负载

ENV.*:
    代码生成或运行环境分层

OBS.*:
    实际产生的中介结果与观测结果
```

其中，`SF.*` 表示语义形态，`CTX.*` 表示可操纵的静态程序上下文，`FX.*` 表示测试骨架、结果观测点和测量控制，`RUN.*` 表示运行负载及实际运行事实，`ENV.*` 表示代码生成或运行环境，`OBS.*` 表示编译过程中实际产生的中介结果和最终观测结果。

下文代码块中的短名是规范化因素后缀（canonical factor suffix）；写入注册表时必须加上对应前缀。每个实验用例应同时保存精确值和带版本的水平标签。例如，立即数既要保存完整位模式，也可以附带 `zero` 或 `encoding_boundary_v1` 标签，但不能只保存标签。

### 语义形态模式：研究对象自身，不是上下文

每个操作码族都必须依据目标 PTX ISA 的语法、限定符合法组合矩阵和目标说明，建立专属模式。通用字段至少包括：

```text
操作码与子操作（opcode / sub-op）
精确的标量、打包、替代格式或张量类型链
位宽，以及有符号、无符号或位模式解释
状态空间与子空间
舍入模式
sat / ftz / approx / wide / hi / lo 等行为限定符
缓存、逐出与预取限定符
内存语义类别、内存序与作用域
代理类别与 from/to 方向
sync / aligned / uni 等执行限定符
标量、向量或元组形式的操作数与结果形状
多目标结果及每个目标的角色
指令专属的旁路操作数与立即数控制字段
```

最后一项是指会改变指令操作模式或协议角色的专属控制字段，包括但不限于比较条件、布尔组合模式、洗牌（`shuffle`）模式、原子子操作、线程块/线程束组（CTA/warpgroup）粒度、矩阵形状、完整的源/目标类型链、描述符模式、布局重排（`swizzle`）、稀疏元数据、块缩放和完成模式。普通数据字面量、地址偏移，以及可作为上下文变化的掩码、标识和数量，应进入操作数、内存或协议因素赋值；如果规范把某个专属立即数定义为指令固有的操作模式，则应将它归入语义形态。每个操作码模式都必须显式声明字段归属，不能仅凭“是否为立即数”统一判断。

这些字段只能组合规范明确允许、且当前 `E_codegen.source_contract` 与架构约束支持的形态。`.b32`、`.u32` 和 `.s32` 即使位宽相同，也不能默认合并；亚字宽、打包类型、FP8/FP6/FP4 和张量类型链，也不能拆成不受约束的全局笛卡尔积。

为研究同一核心操作在带谓词守卫与不带谓词守卫时的目标代码落地（lowering），目标守卫被有意排除在 `semantic_form_id` 之外，统一归入 `CTX.guard.*`。这是为了便于实验身份拆分，并不表示守卫不属于 PTX 语义。

`ptxas` 接受某段 PTX，只能说明该代码通过了当前工具的检查；这并不能自动证明它符合规范，也不能证明整个程序的语义有定义。跨语义形态比较必须使用 `instruction_family_id` 和显式的配对比较 ID。

### 操作数实例化

操作数因素按每个源槽位和结果槽位分别定义，因为不同槽位不一定支持相同的立即数、常量、修饰符或操作数折叠能力：

```text
operand.representation[slot]:
    virtual register
    immediate
    named symbol
    other grammar-allowed surface substitute under the same fixed slot shape

operand.source_identity_partition:
    source virtual operands 的等价类划分

operand.destination_source_overlap[result_slot, source_slot]:
    disjoint / exact overlap / legal partial tuple overlap

operand.reaching_definition_relation[slot_pair]:
    same definition
    distinct definitions proven equal
    distinct definitions with unknown equality
    definitions proven different

value.knownness[subject]:
    compile-time literal
    compile-time symbolic constant
    runtime unknown

value.exact_bits[subject]:
    type-specific exact bit pattern

operand.modifier[slot]:
    none / neg / abs / not / instruction-legal combinations

value.static_uniformity_evidence[subject]:
    no proof
    uniform by semantic definition
    derived from compiler-visible uniform source
    fixture-specific proof construction
```

整数水平的分区至少要考虑 0、±1、最小值、最大值，以及编码或优化边界；浮点分区至少要区分 +0、-0、正规数、次正规数、无穷大、不同 NaN 位型和舍入边界。带版本的值类别是从 `value.exact_bits` 推导出的覆盖标签，不是第二个因素；记录中必须保留精确位模式，不能只保存人类可读的类别。

`RZ`/`URZ`、直接立即数编码、常量存储区折叠和常量物化，都是 SASS 结果。只有在编码规则已被独立建立并完成版本化时，才可以根据精确位模式推导 `encodable_under_rule_version`；即使如此，该字段仍然只是派生标签，而不是源码输入。

标量、向量或元组的数量，以及操作数和结果的形状，均由 `semantic_form_id` 固定。`operand.representation` 只能在同一合法槽位形状下改变可互换的表面写法，不能借此改变语义形态。

地址表达式、对象空间、指针来源和对齐信息统一归入内存因素组。特殊寄存器属于值来源；最终是否通过 `S2R`、`S2UR` 或其他路径读取，则属于观测结果。

### 数据流拓扑

原有的定义—使用关系、生产者、相邻模式和部分活跃性内容，统一整理为以下原子因素：

```text
dataflow.producer_form[slot]:
    external input class or producer semantic_form_id

dataflow.producer_result_component[slot]:
    exact producer destination / tuple / predicate component

dataflow.consumer_edge_count[result_component]:
    exact generated use-edge count

dataflow.consumer_edge[result_component, edge_id].form:
    consumer semantic_form_id

dataflow.consumer_edge[result_component, edge_id].operand_slot:
    exact consumer operand slot

dataflow.consumer_edge[result_component, edge_id].distance:
    exact intervening occurrence count plus versioned distance class

dataflow.consumer_edge[result_component, edge_id].region_relation:
    same basic block
    dominating cross-basic-block
    branch arm / merge-carried
    loop-carried

dataflow.consumer_edge[result_component, edge_id].boundary_kind
dataflow.consumer_edge[result_component, edge_id].boundary_side
dataflow.consumer_edge[result_component, edge_id].crosses_boundary

dataflow.consumer_edge[result_component, edge_id].guard_relation:
    no guard / same / opposite / unrelated
```

`edge_id` 是在一个结果分量内，按规范化源码位置和消费者操作数槽位排序后得到的稳定序号。当 `consumer_edge_count=n` 时，只激活 `0..n-1` 对应的边主体路径；每个带索引的叶字段都要单独注册并赋予唯一水平。未激活的边不能伪装成普通的 `NOT_APPLICABLE` 水平。消费者槽位角色由精确的消费者语义形态和操作数槽位推导；`producer_kind` 与 `consumer_kind` 由所引用的语义形态或外部输入类别推导。这些字段只用于查询和分层，不再注册为并列因素。

精确使用次数由 `consumer_edge_count` 给出，并且必须等于生成后的边数。重复槽位、同类或混合扇出，以及全部结果存活、部分结果存活或结果均不存活等分类，都从边集合推导，不再另行注册并列因素。编译后的实际使用拓扑和活跃区间仍然属于 `OBS.*`。

`boundary_kind` 可以表示普通 ALU、加载/存储、原子/归约、栅栏（`fence`）、屏障（`barrier`/`mbarrier`）、异步操作、分支、调用/返回、退出或陷阱（`trap`）等边界。它描述数据流边所跨越的区域，不再作为另一套“相邻上下文”重复计数。

`mul + add`、`shift + logic`、`compare + branch`、`address-add + load/store`、`convert + arithmetic`、`load + arithmetic`、`arithmetic + store`、`neg/abs + arithmetic`、`min/max/select`、位域/打包/宽窄转换，以及原子或集合操作消费者等组合，全部改为交互组合方案：

```text
pattern recipe
    = producer_form
    + target and indexed consumer_edge fields
    + identity/value constraints
```

短连续窗口只是一种组合方案，不代表编译器依赖分析范围的上限。长依赖图、跨基本块分析、代码尺寸和资源阈值的探索上限，都必须写入覆盖清单和结论边界。

“结果无人使用”与“通过结果观测点保活”属于不同的 `observability_track`。目标被删除是一种合法的指令实例结果；加入 store、return 或其他结果观测点会改变消费者、活跃区间和融合机会，因此必须使用匹配的测试骨架，并安排结果观测点敏感性实验块。

### 谓词守卫、控制流图与执行参与关系

谓词守卫、谓词来源、编译器可证明性、控制流图和执行参与拓扑必须使用不同字段：

```text
guard.target_form:
    absent / positive / negative

guard.producer_target_relation[source_slot]:
    no guard / same / opposite / unrelated

cfg.topology:
    straight-line / conditional branch / both arms / merge
    loop body / loop-carried / indirect control / reconvergence region

cfg.control_dependence:
    same controlling predicate / nested / sibling / unrelated

participation.issuer_construction:
    source construction intends all / elected leader / one per warp
    one per CTA / other legal issuer subset

participation.group_construction:
    compiler-visible single warp / multi-warp / warpgroup
    CTA / multi-CTA cluster construction

participation.explicit_mask_guard_relation:
    same / complement / independent relative to target guard

participation.convergence_evidence:
    statically required convergence
    compiler-visible convergent construction
    divergent or runtime-dependent construction
```

目标指令要求的发射或参与粒度属于 `SF.*`；上述 `CTX.*` 字段只描述源码意图中的构造方式和编译器可见的保证。实际活动集合、发射者集合、实际组映射、mask 相对活动集合的相等/超集/子集关系，以及最终收敛状态，都记录在 `runtime_trial_id` 下，不能回填为静态因素。显式 mask 的精确位模式、派生值类别标签和生产者，分别复用 `CTX.value.exact_bits`、其覆盖分区和 `CTX.dataflow.producer_form`。

谓词的生产者、消费者边集合与数量、已知性或真值，以及编译器可见的一致性，分别复用 `CTX.dataflow.producer_form`、`CTX.dataflow.consumer_edge*`、`CTX.value.knownness/value.exact_bits` 和 `CTX.value.static_uniformity_evidence`，其中主体指向谓词值。守卫因素组不得再次注册同义因素。

运行时实际一致或分歧、实际活动 mask，以及编译器可证明的一致性，是三个不同概念。最终分配到 `P`/`UP`、目标 SASS 守卫极性，以及生成的选举或集合操作序列，都属于结果。编译期恒真或恒假的守卫被规范化或删除，也属于观测结果。

当目标本身是 `setp`、`selp`、分支、`vote`、`shuffle` 等操作时，上述字段是该语义指令族的核心模型；当其他目标只是被守卫或控制流包围时，应复用相同的规范化因素 ID 作为跨指令上下文，不能复制出另一套专属因素。

### 内存语义、地址、别名与代理

必须分开记录三类内容：

1. **目标固有的内存语义**：属于 `semantic_form_id`。
2. **地址和对象的静态构造**：属于可操纵上下文。
3. **目标与其他内存效应的关系**：属于关系型上下文。

目标固有的内存模式至少要正交记录：

```text
operation_class:
    ordinary load/store / atomic / reduction / fence / async

access_preservation_class:
    ordinary / volatile / MMIO where legal

strength_or_order:
    weak / relaxed / acquire / release / acq_rel / sc where legal

scope:
    cta / cluster / gpu / sys where legal

state_space_and_subspace
cache_eviction_prefetch_policy
proxy_kind_and_direction:
    generic / async / alias / tensormap / fabric / other ISA-defined proxy
```

`volatile`/MMIO 的访问保持类别、普通/原子/归约操作类别，以及 weak/relaxed/acquire 等内存序，是不同的轴；`.sc` 只出现在规范允许的指令上。`.param` 是 ABI 参数传递抽象：它可以作为目标固有的状态空间，但不能自动加入普通内存别名、内存序和作用域的笛卡尔积。

地址构造因素至少包括：

```text
address.expression_form:
    named symbol / immediate address / register address
    base + immediate offset / descriptor-based / instruction-specific

address.pointer_provenance:
    generic / explicit state-space pointer / cvta chain / parameter .ptr

address.declared_state_space
address.declared_subspace
address.object_attribute_set:
    managed / unified / other applicable declaration attributes

address.alignment_proof_source:
    declaration / instruction constraint / derived construction / none

address.guaranteed_alignment_bytes:
    exact statically guaranteed bytes or unknown
```

基址生产者、偏移量的精确位模式与已知性，以及描述符生产者，分别复用规范化的数据流和值因素；地址因素组只登记表达式、指针或对象来源，以及对齐保证。

实际运行时对齐与编译器可证明的对齐必须分开。通用地址、对象声明空间、指针来源和 `cvta` 链，也不能压缩成一个 `state_space` 字段。

内存关系因素至少包括：

```text
memory.neighbor_edge_count
memory.neighbor[edge_id].semantic_form_id
memory.neighbor[edge_id].side
memory.neighbor[edge_id].exact_gap
memory.neighbor[edge_id].object_relation:
    proven distinct object / may alias / same abstract object
memory.neighbor[edge_id].byte_range_relation:
    exact same bytes / partial overlap / containment / disjoint / unknown
memory.neighbor[edge_id].actor_relation_construction:
    same-thread program order / distinct-thread-or-CTA actor scaffold
memory.neighbor[edge_id].intervening_fence_semantic_form_id
```

`memory.neighbor_edge_count=n` 时只激活 `0..n-1`；各边按规范化源码位置和访问角色排序。最大序列长度、可达元组和截断原因必须写入组合方案与覆盖清单。目标和每个相邻节点的操作类别、状态空间、宽度、内存序、作用域和代理端点，都从各自的 `semantic_form_id` 读取。同宽或异宽、同代理或跨代理、代理的 `from/to` 方向，以及写后读/读后写/写后写/读后读（`RAW/WAR/WAW/RAR`）关系，都是按边推导的标签，不再注册为重复因素。

执行者关系构造只描述源码或测试骨架中的执行者框架；实际执行者、地址重合和先后事实进入运行时试验记录。普通指针别名与 PTX `alias` 代理是不同概念。跨代理的通用、异步、张量映射和互连结构（`generic/async/tensormap/fabric`）访问，必须显式建模方向和所需栅栏（`fence`）。是否满足足够强的内存关系（`morally strong`）、释放/获取（`release/acquire`）或其他并发关系，需要通过规范约束和独立的并发小测试（`litmus test`）或运行时判定程序验证，不能只凭静态 SASS 判定。

### 异步、屏障与张量协议生命周期

复杂协议不能只用“某条指令前后存在 async/mbarrier”来表示。对于适用的语义种子，至少要考虑以下因素：

```text
protocol.neighbor_edge_count

protocol.neighbor[edge_id].semantic_form_id:
    exact predecessor/successor protocol occurrence form

protocol.neighbor[edge_id].side:
    before / after / enclosing
protocol.neighbor[edge_id].group_relation
protocol.neighbor[edge_id].resource_relation
protocol.neighbor[edge_id].phase_relation

protocol.symbolic_inflight_operation_count
protocol.symbolic_outstanding_group_count
protocol.commit_group_relation
protocol.wait_depth

protocol.pipeline_stage_count
protocol.buffer_relation:
    same / alternating / overlapping / disjoint
protocol.overlap_work_kind:
    none / independent / dependent / mixed

protocol.barrier_phase_or_parity
protocol.generated_arrival_operation_count
protocol.expected_arrival_count
protocol.expected_transaction_bytes

protocol.resource_state_before
protocol.resource_state_at_target
protocol.resource_state_after

protocol.resource_region_relation:
    same / partially overlapping / disjoint region
protocol.resource_owner_group_relation

protocol.dispatch_config_knownness:
    compile-time fixed / runtime value available to generated code
protocol.compatibility_regime:
    compatible / requires legal alternative path
```

`protocol.neighbor_edge_count=n` 时只激活 `0..n-1`。`edge_id` 按规范化源码位置和协议角色排序，所有带索引的叶字段都要单独赋值；最大协议序列长度和截断理由写入组合方案与覆盖清单。是否存在完成观测节点及其边集合，都从相邻节点的语义形态、角色和关系推导，不再注册单值选择器。目标指令实例的操作角色、屏障种类和固有完成模式，已由目标或相邻节点的 `semantic_form_id + logical target role` 固定；本组只记录相邻协议节点、状态和边关系。线程通道（lane）、线程束（warp）、线程束组（warpgroup）、线程块（CTA）或线程块簇（cluster）的静态参与构造由规范化的参与因素描述，运行时实际参与集合则写入试验事实，两者都不得在协议因素组中重复定义。

这里的数量、阶段、资源状态和缓冲区关系，是从源码协议图推导出的预期状态或符号状态。实际完成时刻、到达次数、实际阶段、缓冲区别名关系和未完成深度，属于 `runtime_trial_id` 下的运行时事实，不能用于增加静态因素覆盖率。

张量/TMA 指令的形状、源/目标类型链、分片与布局、描述符模式、步长与越界行为、布局重排（`swizzle`）、稀疏元数据、块缩放、CTA 组和发射粒度，都属于语义形态。描述符的来源、已知性和地址构造应复用规范化的数据流、值和地址因素；只有生命周期、资源区域和完成关系由协议因素组新增。

最终是否生成运行时分派、备用路径，以及各条路径对应的 SASS，属于 `OBS.mapping_topology/effect_graph`，不能作为输入水平。

实验只生成规范允许的协议状态转换。非法生命周期可以组成单独的负向验证语料集，但不能进入合法的目标代码落地（lowering）候选集合。

### 资源压力构造

资源构造输入、编译器限制和编译后的实际结果必须分别记录：

```text
resource.source_live_occurrence_span
resource.source_live_block_span

resource.crossed_region_or_boundary_set

resource.interference_shape:
    independent values / tied uses / constrained consumers

resource.local_DAG_node_count
resource.block_instruction_count
resource.loop_body_instruction_count
resource.independent_chain_count
resource.dependence_depth

resource.live_value_count[type_or_width_class]:
    exact count for each 32/64-bit, tuple/vector and predicate class

resource.static_shared_bytes
resource.static_local_bytes
resource.explicit_stack_bytes
resource.static_memory_layout_id
```

这些资源因素的主体，是为制造资源压力或指令级并行度而构造的辅助值集合。同时存活的总值数由各个 `resource.live_value_count[...]` 求和得到，不另行注册因素。目标指令实例自身的生产者、消费者边、距离、区域和边界，只在规范化的数据流因素中记录，不在此重复。

源码跨度的短/中/长，以及“低/中/高压力”，只能作为根据精确构造字段推导出的报告标签，不能取代原始生成参数。命令行中的 `register_limit` 属于 `E_codegen`；函数 `.maxnreg` 等源码指示符属于函数/源码指示符上下文；最终寄存器数、GPR/UR 分配、本地或共享内存溢出、重计算和调度，则属于结果。

每个实验用例都要先在生成后的规范化 PTX/AST 上检查预期的存活值数量、使用位置、跨越边界和源码规模，以确认源码实验处理是否已实现。最终资源统计、寄存器数、溢出和实际活跃区间是编译后的中介结果或观测结果。即使优化器消除了压力构造，这也只是编译响应，不能据此把已正确生成的源码实验处理改记为 `NOT_REALIZED`。

    entry kernel / device function

    no call / direct / indirect

### 测试骨架、结果观测点与控制因素

测试骨架和结果观测点不属于自然程序上下文，但它们带来的观测工具效应，必须通过实验区组设计和少量配对实验进行量化：

```text
fixture_id / fixture_family_id
sink_id
measurement_block_id
observability_track
control_class
source_variant_id
codegen_replicate_id
```

至少保留多种合法的结果观测点，例如匹配的 store、return、调用/参数传递，或指令族专属的观测方式。结果观测点的每次使用都应形成一条带索引的 `dataflow.consumer_edge`，并同步记录消费者形态和槽位、距离、守卫、区域与边界关系；槽位角色和 `consumer_kind` 均作为派生标签，不重复入表。

空白对照删除目标后，会改变数据流、活跃性和布局，因此主要用于检查错误归属。实验还需要设置尽量保持控制流图、ABI 和数据流外形不变的伪处理对照。只改变虚拟寄存器名、标签名、等价常量写法或无关源码拼写的实验用例，属于规范化阴性对照：它使用新的 `source_variant_id`，但沿用同一 `logical_case_id`，也不能冒充 `codegen_replicate_id`。

### 运行时验证与性能负载

动态实验需要单独定义运行负载身份。它描述“如何执行已经生成的代码产物”，不并入静态 `logical_case_id`，也不与硬件或驱动环境 `E_runtime` 混合：

```text
runtime_workload_id = H({
    runtime_workload_schema_version,
    launch_geometry,
    cluster_configuration,
    dynamic_shared_memory_bytes,
    input_dataset_id,
    address_map_id,
    concurrency_topology,
    expected_participation_and_path,
    oracle_id,
    measurement_mode,
    warmup_and_repetition_policy
})
```

实际的值一致性或分歧、谓词值与活动掩码、发射者集合、实际组映射、掩码与活动集合的关系、地址别名与对齐、线程块簇配置和实际选择的路径，都是 `runtime_trial_id` 下的动态事实或运行时处理实现证据。它们不参与静态因素覆盖率；只有当相应值在 PTX 中被显式读取并生成运行时分派时，才会影响静态程序结构。输入值分布、启动几何等执行意图只属于运行负载清单；如果实测值与预期不一致，两者都要保留。

同一属性在报告中按“语义保证 → 编译器可见证明 → 实际 SASS 表示 → 运行时事实”四层记录。一致性、对齐、别名和执行参与关系都遵守这一规则。动态指标必须同时绑定 `E_runtime_id` 与 `runtime_workload_id`：更换 GPU 或驱动不能伪装成新的运行负载，更换输入或启动配置也不能伪装成新的静态上下文。

静态成本只包括代码字节数、每条控制流路径的指令或协议操作计数、寄存器/栈/溢出、SASS 效应图属性，以及调度与控制元数据。动态延迟、吞吐率、占用率、内存流量和实际执行路径，必须绑定完整的 `E_runtime`、测量方法、置信区间和原始计数器证据。

### 必测交互组合方案

高风险组合使用带约束的组合方案表达，不重新创造因素。单个语义种子内部的 `within_seed_recipe` 只组合 `CTX.*`：

```text
每个源槽位的表示 × 精确值分区 × 操作数修饰符
生产者 × 消费边数量 × 带索引的边字段
CFG 拓扑 × 跨越边界 × 活跃性构造
地址构造 × 带索引的相邻内存边 × 静态对齐
守卫构造 × 掩码构造 × 协议状态
带索引的相邻协议边 × 描述符来源 × 生命周期
资源构造
函数容器 × 调用直接性/尾调用属性 × ABI × 源码指示符
```

以下变化属于跨语义形态配对，而不是单个语义种子内部的组合方案：

```text
内存状态空间 / 宽度 / 内存序 / 作用域 / 代理
要求的发射或参与粒度
张量形状 / 类型链 / 描述符或完成模式
其他目标固有限定符或指令专属控制字段
```

每个组合方案或语义形态配对比较，都必须声明合法性约束、覆盖模式、元组分母、预算上限和未覆盖原因。跨编译流水线、SM 或 PTX 源码约束的研究，应使用配对环境比较清单，在共有的语义形态和上下文投影上比较，不能把环境坐标塞入单环境组合方案。除已知规则驱动的组合方案外，还要保留基于语法的变异、边界变异和独立留出集，避免实验只重复发现预期中的目标代码落地（lowering）。

## 实验有效性要求

### 可观察性

不存在适用于所有指令族、且完全中性的“最小可观测基线”。实验至少要区分以下两条观测路线：

1. **保活的目标代码落地（lowering）**：使用运行时未知输入和匹配的结果观测点，使目标效应可见，并检查结果观测点是否引入融合或额外协议。
2. **优化后的结果**：允许死代码删除、常量折叠、复制传播和融合发生；目标消失或不再具有独立 SASS 时，将其记录为结果类别。

同一结论应尽可能得到多个匹配基线或不同结果观测点的支持。除目标实验处理外，测试骨架中的参数 ABI、符号布局和无关代码应尽量保持一致；无法保持一致的变化，必须作为伴随因素记录。

### 处理实现检查

每个实验用例不仅要记录生成器声明，还必须在生成目标代码之前，验证生成出的规范化 PTX/AST 是否真正包含预期的源码实验处理。编译后的变化要另记为中介结果或观测结果，不能反过来决定实验处理是否存在。例如：

```text
声明 single-use      → 在 source AST 检查一次 use；最终 use 拓扑记 OBS
声明跨 N 条指令      → 检查 source occurrence 距离；最终调度距离记 OBS
声明 uniform proof   → 检查证明构造；最终 UR/UP 路由记 OBS
声明压力构造         → 检查 live-value/use 构造；寄存器数与 spill 记 OBS
声明相同 predicate   → 检查 source guard identity；最终 SASS guard 记 OBS
```

源码处理实现检查按 `source_variant_id × applicable manipulated-static factor_id` 分别记录，不能只为整个实验用例给出一个状态。测量控制与运行负载，分别通过控制项/测试骨架验证和试验级实现证据检查：

```text
REALIZED:
    生成后的 canonical PTX/AST 实现了预期 source/control 条件

NOT_REALIZED:
    生成器输出没有实现预期 source/control 条件

AMBIGUOUS:
    无法可靠确认或归因

NOT_APPLICABLE:
    该因素不适用于当前 case
```

同一个源码变体可能实现了预期的使用边数量，却没有实现预期的证明构造或守卫关系。只有相关实验处理因素为 `REALIZED` 的源码变体和实验用例，才能用于估计该因素的条件效应。对于 `NOT_REALIZED` 或 `AMBIGUOUS`，不能把“输出没有变化”解释为“该因素没有影响”。编译后的使用拓扑、证明传播、守卫、分配和溢出应进入独立的中介结果或结果记录，不参与上述准入判定，以避免实验处理后的选择偏差。可以根据逐因素状态派生 `DESIGN_NOT_REALIZED` 摘要，但不能覆盖原始状态。

### 对照与证伪

实验框架至少需要以下对照与证伪机制：

```text
空白对照：
    删除目标 PTX pattern，检查提取器是否错误归属周围 SASS

阳性对照：
    使用已知会改变 lowering 的 pattern，检查框架能否发现差异

规范化阴性对照：
    仅改变虚拟寄存器名、标签名等预期无关信息，
    检查规范化后 fingerprint 是否稳定

交互故障注入：
    构造只在二阶或更高阶组合下出现的结果，
    检查组合生成和分析流程不会因缺少主效应而漏报

重复性检查：
    相同输入和环境在独立进程中重复编译，
    确认目标代码与规范化结果是否确定
```

### 证据与状态轴

成功汇编、符合规范、目标已生成、能够归属、可以运行和语义正确，是彼此独立的判断，不能压缩成单一互斥枚举或“最高证据等级”。每种状态都必须绑定明确的记录主体：

```text
spec_status[source_variant_id]:
    LEGAL | ILLEGAL | UNKNOWN

support_status[logical_case_id]:
    SUPPORTED | UNSUPPORTED | NOT_APPLICABLE | UNKNOWN

manipulation_status[source_variant_id, factor_id]:
    REALIZED | NOT_REALIZED | AMBIGUOUS | NOT_APPLICABLE

build_status[codegen_unit_id]:
    NOT_RUN | SUCCEEDED | REJECTED | TOOL_ERROR

parse_status[analysis_execution_id, case_id]:
    NOT_RUN | COMPLETE | PARTIAL | UNSUPPORTED | FAILED

raw_encoding_status[code_artifact_hash]:
    CAPTURED | MISSING

control_decode_status[analysis_execution_id, case_id]:
    NOT_REQUESTED | RAW_ONLY | PARTIAL | DECODED |
    CROSSCHECKED | UNSUPPORTED | FAILED

target_realization[analysis_result_id, occurrence_or_expected_slot]:
    PRESENT_INDEPENDENT
    ABSORBED_SHARED_EFFECT
    ELIMINATED_NO_RESIDUAL_EFFECT
    NOT_PRESENT_BY_DESIGN
    UNKNOWN

attribution_status[lowering_instance_id, occurrence_id]:
    ATTRIBUTED | SHARED | PARTIAL | UNKNOWN

runtime_status[runtime_trial_id]:
    NOT_RUN | PASS | FAIL | CRASH | TIMEOUT | UNAVAILABLE

semantic_status[runtime_trial_id]:
    NOT_RUN | PASS | FAIL | INCONCLUSIVE |
    NO_ORACLE | UNDEFINED_PROGRAM

repeatability_status[source_variant_id, compared_codegen_unit_ids]:
    NOT_CHECKED | DETERMINISTIC | NONDETERMINISTIC | INCONCLUSIVE
```

当一个模式组包含多个指令实例时，应逐实例记录目标实现状态，不能生成一个会掩盖混合状态的组级值；组级摘要只能作为派生聚合。空白对照通过 `control_link` 指向实验处理的源码变体，其预期目标槽位记为 `NOT_PRESENT_BY_DESIGN`，不能误记为编译器执行了 `ELIMINATED_NO_RESIDUAL_EFFECT`。

`ELIMINATED_NO_RESIDUAL_EFFECT` 是非空白目标指令实例的一种合法目标代码落地（lowering）结果，不是失败状态。如果语义形态合法、实验处理已实现、编译与解析成功，并且匹配的反事实对照支持将消除归因于该处理，就可以把它纳入已观测优化候选。目标被立即数折叠、融合或复制传播吸收到共享 SASS 节点时，应使用 `ABSORBED_SHARED_EFFECT`，不能误报为无残余删除。

可以从这些状态轴派生 `observed_candidate`、`semantic_validated`、`unresolved` 或 `excluded`，但派生状态不能覆盖原始状态轴。无法运行、无法解码控制字段，或尚未建立判定程序的候选，可以保留相应静态证据，但不能升级为已经验证的选择规则。

控制码证据还应记录：

```text
control_decoder:
    name / version / binary hash / supported architecture range

control_decode_evidence:
    COMMUNITY_DECODE
    REENCODE_BYTE_MATCH
    INDEPENDENT_DECODER_AGREEMENT
    DYNAMIC_CORRELATION
```

社区解码器与原始字节一致，只能说明该逆向模型获得了交叉验证，并不等于 NVIDIA 官方公开的 ISA 事实。

### 成本记录

成本是带有作用域和路径条件的向量，不能预先压缩成单一分数：

```text
kernel_artifact_id =
    H(kernel_artifact_schema_version,
      code_artifact_hash, canonical_function_locator)

cost_record = {
    cost_record_schema_version,
    cost_record_id,
    analysis_result_id,
    scope_type:
        CORE_ONLY | FULL_EFFECT_GRAPH |
        SOURCE_PATTERN_GROUP | KERNEL,
    scope_id:
        lowering_instance_id | kernel_artifact_id,
    path_condition,
    static_observed,
    static_estimated: {
        architecture_model_id,
        calibration_id,
        confidence
    },
    dynamic_measured: {
        runtime_trial_ids,
        matched_control_runtime_trial_ids,
        aggregation_schema_version,
        estimator_and_uncertainty
    }
}
```

`CORE_ONLY`、`FULL_EFFECT_GRAPH` 和 `SOURCE_PATTERN_GROUP` 都使用 `lowering_instance_id`；该 ID 已绑定模式组、代码产物和分析结果。`KERNEL` 使用 `kernel_artifact_id`，并同样显式绑定产生该投影的 `analysis_result_id`。`cost_record_id = H(cost_record_schema_version, analysis_result_id, scope_type, scope_id, path_condition, canonical_cost_payload_hash)`，其中载荷哈希不包含 `cost_record_id` 本身。任何成本记录都不能只包含枚举值，或未绑定环境与结果的函数/模式 ID。`static_observed` 至少可以记录代码字节数、SASS 并集计数与逐路径计数、各角色的指令数、基本块/分支/路径数、内存/栅栏/屏障/集合操作/调用次数、寄存器/栈/溢出统计，以及具有解码证据的调度与控制字段。当互斥的运行时分派路径和备用路径同时存在时，必须同时报告并集大小和各路径的执行计数，不能把所有路径相加后当作一次动态执行。

`static_estimated` 可以包含发射槽位、关键路径、吞吐率/占用率代理，或内存事务代理，但每一项都必须绑定带版本的架构模型。`stall_count` 的求和不等于实测延迟，等待屏障也不能直接换算为周期。

只有 `dynamic_measured` 可以记录实测周期数或耗时、稳态吞吐率、实际执行指令数、内存/缓存计数器、分歧、占用率、停顿原因或能耗。每个 `runtime_trial_id` 已绑定完整的 `E_runtime_id`、`runtime_workload_id` 和重复编号。聚合记录必须列出试验集合、估计器、样本分布和置信区间；只有运行状态与语义有效性通过后，才可以使用匹配的 A/B 对照试验报告结果。不同的运行环境或运行负载不得合并，除非聚合模式明确进行了分层。内核级差值不能在缺乏依据时分摊给共享 SASS 节点或单个 PTX 指令实例。

## 枚举与交互策略

具体的因素水平、测试上限和交互阶数，需要在实验范围确定后再冻结。本节只规定基本原则，避免筛选逻辑造成系统性漏报。

1. 分别建立不可变的 `E_codegen` 与 `E_analysis` 清单。前者固定源码与架构约束、编译工具链、命令和流水线阶段；后者固定反汇编器、解析器、归属算法、结果指纹和控制码解码器的模式、实现哈希及规范化配置/参数。两者都要说明原始产物的保存方式。
2. 为每个 `seed_id × E_codegen_id` 冻结一条适用性记录。有限测试模型由相应生成器按归属关系实现，并由规范化因素 ID、合法水平、约束和组合方案共同定义。必须明确区分：规范非法、目标不支持、因素不适用、程序语义未定义、生成器不支持，以及超出声明范围。
3. 使用多个匹配的测试骨架、结果观测点和伪处理对照进行单因素配对差分，以理解局部条件效应并校验观测工具效应。某个因素在单因素实验中没有造成差异，不能成为永久淘汰该因素的理由。
4. 操作数、数据流、控制流图、内存、协议、资源和 ABI 是因素组织组，不是分阶段的准入门槛。后续组合测试不能以前一个因素组已经观测到主效应为前提。
5. 测试空间分成两部分：

   ```text
   必测覆盖（mandatory coverage）：
       根据语义、目标约束和已知高风险交互预先声明的必测组合

   发现性扩展（discovery expansion）：
       根据新观测到的目标代码落地变化扩展邻近组合
   ```

   发现曲线只能用于衡量继续扩展测试空间的边际收益，不能取消已列入强制覆盖的交互组合。
6. 组合测试必须覆盖适用性记录中纳入的所有因素，而不能只组合已经观测到主效应的因素。两两覆盖或其他 t 阶覆盖，只能证明相应阶数的可达元组已经覆盖，不能据此推断不存在更高阶交互。
7. 对“必测交互组合方案”中声明的高风险因素簇，执行带约束的穷举、t 阶覆盖或精选元组测试。涉及 `SF.*` 的变化，应采用语义形态配对比较。每个组合方案或比较都要同时报告必需元组、已生成元组、不可达元组和未覆盖元组。
8. 使用不依赖已知目标代码落地（lowering）规则的语法变异、边界变异和独立留出集，降低实验只验证既有认知的偏差。
9. 对新候选执行最小见证用例提取，并通过反向修改、移除单个前提或构造邻近反例，尝试证伪其成立条件。差分观测首先只能形成候选规则；只有经过规范推理、语义判定程序和反例验证后，才能升级为选择规则。
10. 保存原始 PTX、完整命令参数与环境、标准输出与错误输出、编译及链接产物、原始 cubin/编码、反汇编、资源统计、归属证据，以及映射拓扑、SASS 效应图、目标代码落地（lowering）、分配、调度控制和精确结果等投影的版本化结果指纹。规范化结果不能替代原始证据。

## 实验规模口径

对于 `E_codegen` 下的一条适用性记录 \(r\)，不同生成路径会产生一个允许重复元素的候选集合：

\[
G(r)=
C_{\mathrm{baseline}}(r)
\uplus C_{\mathrm{single}}(r)
\uplus C_{\mathrm{recipe}}(r)
\uplus C_{\mathrm{discovery}}(r)
\]

首先按完整的 `logical_case_key` 去重：

\[
C(r)=\operatorname{unique}_{\mathrm{logical\_case\_key}}G(r)
\]

如果同一个逻辑实验用例同时由基线、单因素、多个组合方案或发现性扩展路径生成，只保留一条逻辑设计记录，但保留全部 `coverage_origins`。这条记录还可以实例化为多个源码变体。令 \(e\) 表示一个确定的 `E_codegen_id`，则正式的逻辑实验用例集合为：

\[
C(e)=
\operatorname{unique}_{\mathrm{logical\_case\_key}}
\left(
\biguplus_{r:\,r.E_{\mathrm{codegen}}\_id=e}C(r)
\right)
\]

\[
N_{\mathrm{logical\_testcase}}(e)=|C(e)|
\]

对于 \(c\in C(e)\)，令 \(V(c)\) 表示其中互不相同的 `source_variant_id` 集合。对于 \(v\in V(c)\)，令 \(R(c,v)\) 表示通过 `codegen_unit_member` 实际关联到某次编译调用，并且属于该逻辑实验用例和源码变体的 `case_id` 集合，则：

\[
N_{\mathrm{source\_variant}}(e)
=\sum_{c\in C(e)}|V(c)|
\]

\[
N_{\mathrm{case\_realization}}(e)
=\sum_{c\in C(e)}\sum_{v\in V(c)}|R(c,v)|
\]

增加源码拼写变体只会增加 `source_variant_id`，重复编译同一源码变体只会增加 `case_id`；两者都不会增加上下文覆盖率。生成器归属、因素组或组合方案的小计可以作为覆盖来源报告，但不能把这些小计相加后当成实验用例总数。

不能使用“PTX 文件数 × 每文件统一上下文数”作为正式规模公式，因为文件、目标指令实例、指令固有形态和测试骨架之间不是一一对应关系。

数量报告必须始终区分：

```text
指令族数量（instruction family）
语义形态数量（semantic form）
语义种子数量（semantic seed）
测试骨架/结果观测点数量（fixture / sink）
逻辑实验用例数量（logical testcase）
精确源码变体数量（exact source variant）
实验用例实现/重复代码生成数量（case realization / codegen replicate）
目标指令实例数量（target occurrence）
编译调用数量（`codegen_unit_id`）
唯一代码产物/cubin 哈希数量
分析执行数量（`analysis_execution_id`）
唯一分析结果数量（`analysis_result_id`）
运行时试验数量（`runtime_trial_id`）
各类投影的唯一结果指纹数量
目标代码落地实例/未解决归属数量
```

`N_compilation_invocation(e)` 是该环境下互不相同的 `codegen_unit_id` 数；`N_code_artifact(e)` 是这些编译调用产出的不同代码产物哈希数。`N_analysis_execution(a)` 是某个 `E_analysis_id=a` 下互不相同的 `analysis_execution_id` 数，`N_analysis_result(a)` 是与这些分析执行关联的不同 `analysis_result_id` 数；失败的分析执行可以增加前者，却不会增加后者。`N_runtime_trial` 直接按不同的 `runtime_trial_id` 计数。一个 cubin 可以包含多个实验用例，也可以被多个观测工具/解析器版本或分析重复处理，因此这些计数都不能默认等于逻辑实验用例数。

`optimization_level` 属于 `E_codegen`，因此不同优化级别应分别统计：

```text
一个完整环境元组 E_codegen_O0：
    N_logical_testcase(E_codegen_O0) 个逻辑实验用例
    N_source_variant(E_codegen_O0) 个精确源码变体
    N_case_realization(E_codegen_O0) 个实验用例实现

另一个完整环境元组 E_codegen_O3：
    N_logical_testcase(E_codegen_O3) 个逻辑实验用例
    N_source_variant(E_codegen_O3) 个精确源码变体
    N_case_realization(E_codegen_O3) 个实验用例实现
```

只有当两个环境的适用性记录、测量区组和逻辑实验用例基数相同时，才可以直接比较数量。跨 SM、PTX ISA 或目标特性的环境往往具有不同的合法空间。跨环境配对必须按照 `paired_environment_comparison.matched_key`，也就是 `shared_seed_key + projected shared context + matched fixture/sink/track + selected source-variant key`，报告双方共有的交集；不能使用单侧完整赋值、源码变体笛卡尔积，也不能把覆盖差异解释为目标代码落地（lowering）差异。

在因素注册表、组合方案、语义种子清单、测量区组和适用性矩阵尚未冻结前，“每个完整环境元组约 1.1–1.3 万个逻辑实验用例”只能作为早期工程预算，不能视为理论基数或精确预测。最终的源码变体数、实验用例实现数、编译调用数、代码产物数、分析执行与结果数、运行时试验数，以及各投影的唯一结果指纹数，只能根据冻结后的清单和实际产物统计。

### 覆盖率口径

覆盖率必须同时声明带版本的分母，至少区分以下口径：

```text
semantic_form_coverage:
    已覆盖语义形态 / 声明范围内合法且受支持的语义形态

factor_level_coverage:
    已实现的合法水平 / 适用性记录中可达的合法水平

reachable_t_tuple_coverage:
    已实现元组 / 约束求解得到的可达 t 元组

mandatory_recipe_coverage:
    已满足的必需元组 / 组合方案声明的必需元组

paired_form_coverage:
    已完成且变体键唯一的匹配对 /
    比较实例声明的必需匹配对

paired_environment_coverage:
    已完成且变体键唯一的共有投影匹配对 /
    配对环境比较声明的必需匹配对

fixture_source_coverage:
    已覆盖测试骨架/源码族 / 预先声明的测试骨架/源码族

observer_sensitivity_coverage:
    已完成的匹配结果观测点/测试骨架区组 / 预先声明的区组

runtime_workload_coverage:
    已完成且状态有效的运行负载 / 动态结论所声明的运行负载清单

resolution_rates:
    manipulation_status=NOT_REALIZED
    target_realization=UNKNOWN
    parse_status=PARTIAL
    attribution_status=UNKNOWN
    semantic_status=NO_ORACLE
    control_decode_status=RAW_ONLY
    分别按各自状态主体和冻结分母报告比例

holdout_discovery_rate
repeatability_rate
```

源码覆盖率的分母，是冻结清单中声明的独立源码族、测试骨架族或留出语料集，而不是 PTX 文件数。如果不同环境的合法语义形态分母不同，应分别报告覆盖率，并另行报告共有配对交集。

因素水平或元组覆盖的分子，只有在至少一个源码变体的相关处理实现状态为 `REALIZED` 时才增加。同一逻辑实验用例的多个拼写变体和重复代码生成，不得重复增加分子。

## 完成条件与结论强度

完成条件必须与实验声明匹配：

- 如果穷举了形式化定义的有限上下文空间，所有可达逻辑实验用例都具有完整且可审计的状态向量，并且未解决项集合为空，才可以声称“相对于该版本化测试空间完整”。
- 如果只完成了 t 阶组合覆盖，只能声称“所有可达的 t 元组均已覆盖”。
- 如果采用规则驱动或随机探索，只能报告已观测候选、覆盖指标、独立留出集结果和未解决空间；连续若干轮没有发现新变体，并不能证明实验空间已经完整。

如果存在以下情况，都必须保留为相应的未解决项，不能静默跳过，也不能计入完整集合：可达组合尚未覆盖、输出不确定、相关实验处理未实现、目标实现状态未知、目标无法归属、程序语义未定义、观测工具或解析器无法识别新的 SASS，或者实验声明要求的控制字段无法解码。规范非法、目标不支持和明确超出范围的区域可以排除，但必须同时给出原因代码、分母口径和证据。

## 预期产物

在上述证据边界内，实验可以产生：

1. 每个 PTX 语义模式组对应的已观测目标代码落地实例、SASS 效应图、最小见证用例和邻近反例。
2. 上下文原子因素及组合方案对映射拓扑、核心/准备/分派/排序/参与/完成、资源分配和调度控制的观测影响矩阵。
3. 在固定 `E_analysis`、测试空间及投影/结果指纹定义下成立的各类投影**观测等价类**。
4. 已获得证据支持的相关属性候选集。未观测到影响的属性，不能直接从语义中间表示或目标中间表示中删除。
5. 一个候选数据库，其中保存源码/水平/元组覆盖率、成立条件、完整状态向量、归属证据和分作用域成本记录，可作为后续固定顺序指令选择原型的输入语料。
6. 未解决项集合，包括未覆盖元组、未实现的实验处理、未知目标实现状态、部分解析或归属、缺少语义判定程序、控制字段只有原始字节等。

该数据库足以支持后续选择器原型和独立语义验证的启动工作。但是，如果规则成立条件尚未经过证伪尝试、SASS 效应图尚未可靠归属，或语义判定程序尚未通过，就不能把它当成可以直接采用的正确规则库。

观测到 `ptxas` 生成某种 SASS，并不能证明保持源码顺序的选择器也能实现同样变换，因为 `ptxas` 本身可能使用指令重排、跨基本块分析或全局资源决策。固定顺序指令选择的能力边界，需要由后续受约束原型或独立证明来建立；本实验只能提供候选和反例。

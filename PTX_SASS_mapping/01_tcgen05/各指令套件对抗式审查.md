# tcgen05 各指令套件的逐个对抗式审查

> 适用范围：PTX ISA 9.0、NVIDIA Thor、`sm_110a`、CUDA 13.0（ptxas V13.0.88）
> 方法：逐套件读取其声称的因子轴与阴性边界，构造套件之外的探针试图证伪。
> 所有"实测"来自本次编译反汇编，探针在会话 scratchpad，未入仓库。
> `tcgen05.mma` 的审查已单独成文（[对抗式审查_实验设计缺口.md](对抗式审查_实验设计缺口.md)），此处不重复。
> `wait`/`fence`/`relinquish` 三个套件已在本轮按对照设计重建，此处只记录残余风险。

## 结果总览

| 套件 | 判定 | 最重要的发现 |
|---|---|---|
| `alloc` | 有实质缺口 | ncols 寄存器形态合法且 lowering 不同，轴缺失 |
| `dealloc` | 有实质缺口 | 合法面与 alloc 不对称（32 倍数 vs 2 的幂），轴测不出 |
| `cp` | 基本扎实 | 非法组合诊断同族，阴性覆盖足够 |
| `ld` | 有发现 | `red` 变体映射到未记录的 `LDTM.STAT` 修饰符族 |
| `st` | 小缺口 | 立即数 offset 的文法边界不在阴性集 |
| `commit` | 有重要发现 | generic 与 `shared::cluster` 编码逐位相同 |
| `shift` | 基本扎实 | 缺 `.cta_group` 省略的阴性探针 |
| `wait` | 已重建 | `ld`/`st` 不对称已断言，12/12 成立 |
| `fence` | 已重建 | 排序效应仍不可观测，限制已写入 spec |
| `relinquish` | 已重建 | `UVIRTCOUNT` 归属 16/16 成立 |

## alloc 与 dealloc：合法面不对称，两套阴性探针都测不出来

两个套件的阴性用例给出了不同的拒绝理由：alloc 写"nCols must be a power of two in [32, 512]"，dealloc 写"multiple of 32"。两者不能同时都是完整约束。用交集之外的值裁决：

| 探针 | 结果 | ptxas 诊断 |
|---|---|---|
| alloc ncols=96 | 拒绝 | value must be power of 2 |
| alloc ncols=160 | 拒绝 | value must be power of 2 |
| dealloc ncols=96（alloc 128 合法前序） | **接受** | — |
| dealloc ncols=48 | 拒绝 | expected to be multiple of 32 |
| alloc 32 + dealloc 64（数量不匹配） | 接受 | — |

结论：

1. 约束不对称是真实的。alloc 要求 2 的幂，dealloc 只要求 32 的倍数，`dealloc ncols=96` 是合法程序。两个套件的阴性值（16、48）恰好都落在两条约束的交集里，无论跑多少遍都无法区分这两条规则。dealloc 的 `SF.ncols` 轴缺少 96、160 这类只对 dealloc 合法的档位。
2. alloc 与 dealloc 的 ncols 不匹配（32 对 64）静态接受。静态合法面比语义合法面宽，这类错误由 lowering 中的运行时 guardrail trap 承接，与 `STATIC_ONLY` 口径一致，但应在套件文档中写明。

### alloc 的第二个缺口：ncols 的操作数形态轴缺失

套件所有 case 的 ncols 都是立即数。实测寄存器形态被 ptxas 接受，且 lowering 实质不同：

```
立即数 32:  掩码在编译期展开，IMAD.SHL.U32 R0, R0, 0x20
寄存器:     运行时求列数  SHF.R.S32.HI R0, RZ, 0x5, R0   (ncols/32)
            运行时建掩码  SHF.L.U32 R2, R3, R0, RZ
```

这不是同一 semantic form 的重编号，是不同的代码路径。`SF.ncols_operand_form ∈ {immediate, register}` 应当成为一条轴。dealloc 同理。

### 归属方式：目前正确，但依赖脆弱的巧合

三条指令的 kernel 互相包含（alloc 的 case 里有 dealloc 和 relinquish，反之亦然），归属能分开完全依赖三个 target pattern 是互不包含的子串：

| 套件 | pattern | 同 kernel 中的干扰源 |
|---|---|---|
| alloc | `FIND_AND_SET` | dealloc 的 `UTCATOMSWS.AND` 不含该子串 |
| dealloc | `UTCATOMSWS.AND` | alloc 的 `FIND_AND_SET.ALIGN` 不含该子串 |
| relinquish | `UVIRTCOUNT` | 另两者都不产生 |

当前成立，但任何一方的 lowering 改一个修饰符就会静默串味。另外一条 alloc 因自旋重试产生两条 `FIND_AND_SET`（主路径加 NANOSLEEP 重试路径），是结构性的一对多，规则挖掘的 signature 里会出现两个条目，文档必须写明这不是两次 alloc。

## cp：阴性覆盖足够，无实质缺口

套件阴性集测了缺 multicast（64x128b、32x128b 裸用）和多 multicast（128x256b.warpx4）。补测其余组合：

| 探针 | 结果 |
|---|---|
| `128x128b.warpx2::01_23` | 拒绝，Modifier .warptype not allowed for shape |
| `4x256b.warpx4` | 拒绝，同上 |
| `128x256b.warpx2::02_13` | 拒绝，同上 |
| `4x256b.b8x16.b6x16_p32` | 接受 → `UTCCP.T.S.4dp256bit.U6x16P32` |

所有 shape×multicast 非法组合走同一条诊断，属同一约束族，套件取样已足以代表。format 轴与 shape 正交的判断也再次成立。唯一备注：cp 的 case 全部没有 completion（无 commit），静态归属无碍，但这些 kernel 在语义上是不完整程序，套件文档应写明。

## ld：`red` 变体映射到未记录的修饰符族

套件 expanded 集含 4 个 `ld.red` case（u32/s32 × min/max，仅 32x32b.x2）。实测其 SASS：

```
tcgen05.ld.red.sync.aligned.32x32b.x2.u32.min  ->  LDTM.STAT.x2.MIN
```

`.STAT` 是一个此前任何文档都没记录的修饰符族：reduction 不是 LDTM 的操作数变化，而是独立的 `LDTM.STAT` 形态加 `.MIN`/`.MAX` 后缀。[各指令_映射规则研究重点.md](各指令_映射规则研究重点.md) 此前称 red 轴"未覆盖"是错的——expanded 集覆盖了，但只有一个 shape，且映射结果没有被归纳成规则。待补：red × 其他 shape、u32 与 s32 是否区分编码（助记符相同，需查 word0）。

新发现的非法组合，不在套件阴性集：

| 探针 | 结果 |
|---|---|
| `ld.red` + `.pack::16b` | 拒绝，Illegal modifier '.pack::16b' for 'tcgen05.ld.red' |

## st：文法边界缺一针

`16x32bx2` 形态的第二操作数（半列偏移）实测只接受立即数：

| 探针 | 结果 |
|---|---|
| `st 16x32bx2 [%taddr], %off_reg, {...}` | 拒绝，Arguments mismatch |

该边界不在套件阴性集（现有阴性只有 shape 8x32b 一针）。ld 侧同理。另外 `16x32bx2` 一条 PTX 产生两条 STTM/LDTM（`t0_t15` 与 `t16_t31`）的一对多事实已在映射研究重点中记录，套件的 signature 机制能容纳，但 `target_occurrence_count=1` 与 SASS 两条的关系需要在文档里写死，避免后续把它当成计数错误。

## commit：state space 在核心编码中被完全擦除

这是本轮最重要的单条发现。O3 下对比：

| 形态 | SASS | word0 | word1 |
|---|---|---|---|
| generic `[%mbar]`（参数地址） | `UTCBAR [UR4], URZ` | `0x000000ff040073e9` | `0x0001d800080000ff` |
| `.shared::cluster [mb]`（共享变量） | `UTCBAR [UR4], URZ` | `0x000000ff040073e9` | `0x0001d800080000ff` |

两条指令**逐位相同**。`.shared::cluster` 限定符在核心指令的助记符、操作数、编码里全部消失，唯一差别在 UR4 的生产方式（LDCU 参数装载 vs 共享地址计算）。此前 mma 综合报告中"看不到一对一的同名修饰符不表示信息被丢弃"的谨慎表述，对 commit 的 state space 可以收紧为：核心编码确实不携带该信息，逆向映射此维度必然返回候选集合。也因此，generic 形态传入非 shared 地址是静态不可检测的错误，属运行时语义范畴。

multicast 的操作数契约实测：

| 形态 | SASS |
|---|---|
| 无 multicast | `UTCBAR [UR4], URZ`（mask 槽位恒为 URZ） |
| `.multicast::cluster ... , %mask` | `UTCBAR.MULTICAST [UR4], URZ, UR6`（word1 低位 `0x00ff`→`0x0806`） |

mask 是第三操作数槽位，不用时以 URZ 占位。三个文法边界均拒绝但都不在套件阴性集（现有阴性只有 cta_group::3）：

- `.multicast::cluster` 不带 mask → 拒绝
- 带 mask 不带 `.multicast::cluster` → 拒绝
- 省略 `.cta_group` → 拒绝（.cta_group modifier required）

## shift：结构扎实，补一针即可

guarded shift 的降级实测与 mma 的外围控制流路径一致：guard 变成跳过 ELECT 块的分支，核心 `UTCSHIFT.DOWN tmem[UR4]` 自身不带谓词，等待 taddr 的 SB0。无异常。

缺口仅一处：省略 `.cta_group` 被拒绝（.cta_group modifier required），不在套件阴性集（现有阴性只有 direction=up 一针）。

## wait / fence / relinquish：本轮已重建，残余风险

三套件已改为对照差分设计并全量通过（fence 26、wait 26、relinquish 16 case）。残余：

1. fence 的排序效应仍不可观测。现有差分只显示 fence 位置多一条空 wait 的 NOP。要观测真实的排序作用，需要在异步操作与同步点之间放入编译器有动机跨同步点搬移的独立工作，该轴尚未构造，限制已写入 spec docstring。
2. wait 的 `ld`/`st` 不对称（零指令 vs `FENCE.VIEW.ASYNC.T`）在 12/12 组合上成立并已入断言，但 `FENCE.VIEW.ASYNC.T` 相对后续覆盖源寄存器指令的位置约束（它保护的窗口边界）还没有被差分刻画。
3. relinquish 的 guard 形态走外围分支，`UVIRTCOUNT` 自身无谓词；若未来出现谓词化形态，现有 16/16 断言不会报警，因为它只查存在性不查谓词。

## 跨套件的共性问题

1. 所有 factors.json 的 `constraints` 与 `high_risk_interactions` 均为空数组。本轮发现的 alloc/dealloc 合法面不对称、red×pack 非法、multicast×mask 配对，都属于应登记在 `constraints` 里的跨轴约束。字段存在但从未被使用。
2. 阴性探针普遍每套件 1 至 3 针，且集中在"显然非法"的值上。本轮每个套件都能在 15 分钟内找到不在阴性集里的可拒绝形态，说明阴性面取样密度整体不足。与 mma 审查中"合法面从未被证伪"（P0-2）是同一问题的两面。
3. 操作数形态（立即数 vs 寄存器）在多个套件里是被固定而非被控制的变量：alloc/dealloc 的 ncols、st/ld 的半列偏移。凡是文法同时接受两种形态的位置，都应当有一条轴或一条阴性边界，二者必居其一。

## 建议的修复顺序

| 优先级 | 套件 | 动作 |
|---|---|---|
| 高 | dealloc | ncols 轴加 96/160；阴性理由改为"32 的倍数"并与 alloc 的"2 的幂"分开登记 |
| 高 | alloc/dealloc | 增加 `ncols_operand_form` 轴（立即数/寄存器） |
| 高 | commit | 阴性集补 multicast/mask 三针；文档写明 state space 零编码差 |
| 中 | ld | red 映射（`LDTM.STAT`）入规则文档；阴性集补 red×pack |
| 中 | st/ld | 阴性集补寄存器 offset 一针 |
| 中 | shift | 阴性集补省略 cta_group 一针 |
| 低 | cp | 文档写明 case 无 completion 属静态不完整程序 |
| 低 | 全部 | factors.json 的 `constraints` 开始实际使用 |

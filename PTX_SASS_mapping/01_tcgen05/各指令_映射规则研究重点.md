# tcgen05 其余 10 条指令的映射规则研究重点

> 适用范围：PTX ISA 9.0、NVIDIA Thor 架构、编译目标 `sm_110a`
> 工具环境：CUDA 13.0、ptxas V13.0.88、nvdisasm V13.0.85
> 本文性质：研究范围裁决。表中"实测 SASS"来自对各目录 `thor_ptx90/generated/*.ptx` 的 O3 编译反汇编，"要关注的规则"是尚未成文的研究任务，不是已冻结结论。

## 结论

这 10 条指令与 `tcgen05.mma` 不共享一套规则模型。按 PTX 指令与 SASS 的结构关系，它们分成四类，每类的观测量和研究方法都不同：

| 类别 | 指令 | PTX→SASS 结构 | 与 mma 的关系 |
|---|---|---|---|
| A 单指令直译 | `cp`、`ld`、`st`、`shift` | 1 条 PTX → 1 条（或固定 2 条）SASS，qualifier 逐个对应 modifier | 同构，可直接复用 mma 的方法 |
| B 编译器合成协议 | `alloc`、`dealloc`、`relinquish_alloc_permit` | 1 条 PTX → 一整段含自旋循环、影子状态和 trap stub 的序列 | 不同构，mma 的"核心指令 + 外围"模型不适用 |
| C 完成节点 | `commit` | 1 条 PTX → 1 条 `UTCBAR`，但 state space 不进入助记符 | 部分同构，需要区分"进入助记符"与"进入操作数/编码" |
| D 零指令调度约束 | `wait`、`fence` | 1 条 PTX → 0 条 SASS，效应只在指令控制位 | 完全不同构，必须换观测量 |

把这四类套用同一份"opcode + qualifier → 助记符 + 修饰符"模板会在 B 类和 D 类上得到空结论。

## A 类：单指令直译

### `tcgen05.ld` / `tcgen05.st`

PTX 轴：`shape`（5 档）× `num`（x1/x2/x4/x8）× `pack::16b`/`unpack::16b` × `.red` 变体 × 归约操作。

实测 SASS 映射（40 + 40 个 case，全部 O3）：

| PTX 字段 | SASS 结果 |
|---|---|
| `.32x32b` | `LDTM` / `STTM`（无 shape 后缀，即默认形态） |
| `.16x64b` | `.16dp64bit` |
| `.16x128b` | `.16dp128bit` |
| `.16x256b` | `.16dp256bit` |
| `.16x32bx2` | 拆成两条：`.16dp32bit_t0_t15` + `.16dp32bit_t16_t31` |
| `.x1` | 无后缀 |
| `.x2` / `.x4` / `.x8` | `.x2` / `.x4` / `.x8` |
| `.pack::16b` | `.PACK16BIT` |
| `.unpack::16b` | `.EXPAND16BIT` |

要关注的规则：

1. `.16x32bx2` 是唯一的一对多形态。归属逻辑必须允许 1 条 PTX occurrence 配对 2 条 SASS，否则计数会错。这与 mma 的严格 1:1 归属假设冲突。
2. `shape × num` 决定目标寄存器个数和寄存器对齐要求，需要单独记录寄存器向量宽度，而不是只记录助记符。
3. `.red` 变体由 expanded 集覆盖（4 个 case，u32/s32 × min/max，仅 32x32b.x2）。实测映射为独立修饰符族：`tcgen05.ld.red...u32.min` → `LDTM.STAT.x2.MIN`。待补：red × 其他 shape，u32 与 s32 是否在 word0 区分（助记符相同），以及 `red × pack::16b` 为非法组合（ptxas 拒绝）应入阴性集。
4. `taddr` 来源（direct / identity_derived / nonidentity_derived）对 `tmem[UR]` 槽位的影响，方法可直接复用 mma 的 producer 分析。

### `tcgen05.cp`

PTX 轴：`cta_group` × `shape`（5 档）× `multicast`（4 档）× `format`（3 档）。

实测 SASS 映射（36 个 case，全部 O3，基础助记符恒为 `UTCCP.T.S`）：

| PTX 字段 | SASS 结果 |
|---|---|
| `.cta_group::2` | `.2CTA` |
| `.128x256b` | 无 shape 后缀（默认形态） |
| `.128x128b` | `.128dp128bit` |
| `.4x256b` | `.4dp256bit` |
| `.32x128b.warpx4` | `.4x32dp128bit` |
| `.64x128b.warpx2::02_13` | `.2x64dp128bit_lw02_lw13` |
| `.64x128b.warpx2::01_23` | `.2x64dp128bit_lw01_lw23` |
| `.b8x16.b6x16_p32` | `.U6x16P32` |
| `.b8x16.b4x16_p64` | `.U4x16P64` |

要关注的规则：

1. `.T.S` 是恒定后缀，表示 TMEM 目的、SMEM 源。需要验证是否存在改变这两个字母的合法形态；若不存在，应记为该指令的固定操作数契约而非可变轴。
2. shape 与 multicast 在 SASS 中融合成单个后缀（`32x128b.warpx4` → `4x32dp128bit`），不是两个独立字段。规则必须按"组合 → 后缀"登记，不能拆成两条独立规则。
3. `.128x256b` 的默认形态没有后缀，逆向时 `UTCCP.T.S` 必须映射回 `128x256b`，不能返回"未知 shape"。
4. `format` 与 shape 正交，36 个 case 中未见冲突，需要确认是否存在非法组合。

### `tcgen05.shift`

PTX 轴：`cta_group` × `direction`（PTX 9.0 只有 `.down`）。

实测：`tcgen05.shift.cta_group::1.down` → `UTCSHIFT.DOWN`；`cta_group::2` → `UTCSHIFT.2CTA.DOWN`。

要关注的规则：

1. 轴少，2 个 case 已穷举当前语法面。研究重点转向 taddr 来源和 guard 的外围 lowering。
2. 必须与 mma 的 `.ashift` 明确分离：`UTCSHIFT` 是独立指令，`.ASHIFT` 是 mma 的操作数修饰符，两者不是同一机制。这一点在顶层 README 已声明，需要在规则文档中给出 SASS 层面的证据。

## B 类：编译器合成协议

这是与 mma 差异最大的一类。`tcgen05.alloc` 在 O3 下展开成约 20 条指令的完整软件协议，PTX 中没有任何对应文本。

实测 `tcgen05.alloc.cta_group::1.sync.aligned.b32 [slot], 32` 的 O3 lowering 结构：

| 阶段 | SASS | 作用 |
|---|---|---|
| 簿记地址计算 | `S2UR SR_CgaCtaId`、`UMOV 0xc0/0x400`、`ULEA ...,0x18` | 按 CTA id 定位 SMEM 影子状态区 |
| 相位校验 | `LDS.U8 [base+0x1c]`、`ISETP.NE`、`@P0 BRA` | 非零则跳 trap |
| 单线程选举 | `ELECT P0, URZ, PT` | 选出执行分配的线程 |
| 硬件分配自旋 | `DEPBAR.LE SB0`、`UTCATOMSWS.FIND_AND_SET.ALIGN UP0, UR4, UR4`、`NANOSLEEP 0x64`、`BRA.U !UP0` | 失败则休眠重试 |
| 影子记账 | `SHF.L`、`ATOMS.OR [base+0x14]`、`ATOMS.OR [base+0x18]` | 在 SMEM 位图记录已分配列 |
| 结果发布 | `STS [slot]` | 写回 TMEM 地址 |
| 失败路径 | `CALL.REL.NOINC`、`BPT.TRAP 0x1` | `guardrail_trap_phase_invalid_during_alloc` |

`tcgen05.dealloc` 的实测结构：`WARPSYNC.ALL` → 重算簿记地址 → 从影子位图取列号并两次校验（失败进 `guardrail_trap_col_being_dealloced_not_returned_by_alloc` 与 `guardrail_trap_unallocated_columns_being_dealloced`）→ `VOTEU.ANY` + `UFLO.U32` + `REDUX` + `UTCATOMSWS.AND URZ, UR4` → `ATOMS.AND` 清账。

`tcgen05.relinquish_alloc_permit` 的实测结构：`ELECT` → `UVIRTCOUNT.DEALLOC.SMPOOL 0x80` → `STS.U8 [base+0x1c], 1` 置相位字节。

要关注的规则：

1. 三条指令共享 `UTCATOMSWS` 家族，靠子修饰符区分：alloc 用 `.FIND_AND_SET.ALIGN`，dealloc 用 `.AND`，relinquish 根本不用 `UTCATOMSWS` 而用 `UVIRTCOUNT.DEALLOC.SMPOOL`。按助记符做归属会把三者混为一谈。
2. 生成的每个 kernel 都同时包含 alloc、dealloc、relinquish 三条 PTX（后两条是 alloc 的资源配平），所以归属必须按序列结构切分，不能按助记符出现次数计数。这是当前 10 个套件里最容易出错的一处。
3. 研究对象应当是"序列模板"而不是"指令选择"：SMEM 影子状态的偏移布局（`+0x14`、`+0x18`、`+0x1c`）、自旋重试的退避常量（`NANOSLEEP 0x64`）、trap stub 的符号名和触发条件，都是编译器 lowering 的固定资产，需要单独建表。
4. `ncols`（32/64/128/256/512）与 `cta_group` 是否改变序列结构（而不只是改立即数），需要按序列模板做差分。
5. `state_space`（generic 与 `shared::cta`）是否改变结果发布路径（`STS` 与其他形式），需要单独验证。
6. trap stub 属于静态可见的合法性护栏，是本族独有的证据类型，应当与 mma 的阴性探针分开记账：mma 的非法组合由 ptxas 拒绝，这里的非法状态由运行时 trap 承接。

## C 类：完成节点

### `tcgen05.commit`

PTX 轴：`cta_group` × `state_space`（generic / `shared::cluster`）× `multicast`。

实测 SASS 映射（8 个 case 全覆盖）：

| PTX | SASS |
|---|---|
| `cta_group::1` + 无 multicast | `UTCBAR` |
| `cta_group::1` + `.multicast::cluster` | `UTCBAR.MULTICAST` |
| `cta_group::2` + 无 multicast | `UTCBAR.2CTA` |
| `cta_group::2` + `.multicast::cluster` | `UTCBAR.2CTA.MULTICAST` |
| `.shared::cluster` 与 generic | 助记符与修饰符完全相同 |

要关注的规则：

1. `state_space` 不进入核心编码（已裁决）。O3 下 generic 与 `.shared::cluster` 的 `UTCBAR` 逐位相同（word0 `0x000000ff040073e9`、word1 `0x0001d800080000ff`），差异只在地址操作数的生产序列（LDCU 参数装载 vs 共享地址计算）。逆向映射此维度必然返回候选集合；generic 形态传入非 shared 地址属静态不可检测的运行时错误。见[各指令套件对抗式审查.md](各指令套件对抗式审查.md)。
2. `.multicast::cluster` 需要一个 cluster mask 操作数，需要确认该 mask 走哪个槽位、由什么指令产生。
3. `CTX.prior_operation`（none / cp / shift）决定 commit 提交的是哪一批异步操作。要验证前序操作是否改变 `UTCBAR` 的编码或其控制位依赖，这是把 commit 与 mma 协议层打通的接口。
4. 与 mma 的 `tcgen05.mma` 完成协议对接：mma 目录的 `memory_consistency.md` 已有协议矩阵，本目录的规则必须与之交叉核对，不能各写一份。

## D 类：零指令调度约束

### `tcgen05.wait` / `tcgen05.fence`

`tcgen05.fence` 不是内存 fence，只是名字相同。它约束的是编译器对 tcgen05 异步操作的调度，不是硬件缓存。对照实测：

| PTX | SASS |
|---|---|
| `membar.cta` | `MEMBAR.SC.CTA` |
| `membar.gl` | `CCTL.IVALL` + `ERRBAR` + `MEMBAR.SC.GPU` |
| `membar.sys` | `CCTL.IVALL` + `ERRBAR` + `MEMBAR.SC.SYS` |
| `fence.sc.cluster` | `CCTL.IVALL` + `ERRBAR` + `MEMBAR.SC.GPU` |
| `fence.acq_rel.gpu` | `CCTL.IVALL` + `ERRBAR` + `MEMBAR.ALL.GPU` |
| `fence.proxy.async.shared::cta` | `FENCE.VIEW.ASYNC.S` + `MEMBAR.ALL.CTA` |
| `tcgen05.fence::before_thread_sync` | 无 |

真正的内存 fence 会产生缓存失效（`CCTL.IVALL`）与内存屏障（`MEMBAR`）指令。`tcgen05.fence` 一条都不产生：tcgen05 的完成状态由每 warp 的记分牌跟踪，跨线程同步点移动这些操作会破坏记分牌配对，因此该 fence 的全部作用是在调度图上钉一条边。

实测：在 `cp` → `tcgen05.fence::before_thread_sync` → `bar.sync` → `cp` 的序列中，加入 fence 只多出一条 `NOP`（调度分隔，`wait` 掩码为空），核心序列不变。

`tcgen05.wait::ld` 同样不产生指令，其效应体现在相邻指令的控制位上。

生成器必须区别对待：`membar`/`fence.*` 漏发射是内存一致性错误；`tcgen05.fence` 不该发射任何指令，但必须作为调度约束保留，漏掉不会报错，只会在某次重排后变成竞态。

补充探针（手写，`LDTM` 后有无 `wait::ld` 的单因素对照）结果：两版 SASS 指令序列相同，差异只出现在前一条指令的控制字段，`LDCU.64` 的第二个字从 `0x000e640008000a00` 变为 `0x000e620008000a00`。

要关注的规则：

1. 观测量必须换成指令控制位（word 1 高位的 scoreboard / 依赖屏障字段），不能用"是否出现某条 SASS 指令"。沿用 A 类方法会得到"该指令无 SASS 映射"的空结论。
2. 当前 syntax 集各只有 2 个 case，且 `CTX.prior_queue` 的 single/double 档位没有生成，正好缺少能让 wait 产生可观测效应的上下文。这两个套件必须先补生成，才能开始规则归纳。
3. `fence::before_thread_sync` 与 `fence::after_thread_sync` 的方向差异，需要在跨线程同步相邻的上下文里才可能显现，孤立 case 无法区分。
4. 需要明确一条边界：静态编译能证明的是"编译器插入了何种依赖约束"，不能证明运行时的可见性语义。这与 mma 目录已确立的 `STATIC_ONLY` 口径一致。

## 当前套件的三处缺口

| 缺口 | 影响 | 建议 |
|---|---|---|
| `wait`、`fence`、`shift`、`relinquish` 各只有 2 个 case，`prior_queue`、`adjacent` 等上下文档位未生成 | D 类无法产生任何可观测差异 | 先补上下文生成，再谈规则 |
| 10 个套件均只有 syntax 模式，无 expanded 上下文矩阵 | 无法做 mma 那样的配对差分 | A 类和 C 类可直接复用 mma 的上下文 profile 设计 |
| `results/` 是被 Git 忽略的运行时产物，本地已不存在 | `validation/*.json` 里的 forward rule 数只有计数和 SHA，规则本体不可读 | 重跑 `check_all.sh` 后再引用，引用前核对 SHA-256 |

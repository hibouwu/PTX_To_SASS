# PTX→SASS 实验设计：哪些上下文会改变 SASS 实现

> 本文面向需要理解或评审实验方案的读者，只说明研究问题、维度划分和实验方法。
> 字段、ID、枚举、约束、状态轴、成本与覆盖公式见
> [实验设计详细规范](实验设计_详细规范.md)。

## 先说结论

原有实验维度的覆盖面基本合理，但把六类不同角色混在了一起：实验环境、目标指令自身的语义、可操纵的源码上下文、测量条件、运行时事实和编译结果；生产者、消费者、定义—使用关系和相邻模式之间也存在重复。

整理后的核心结论是：

- 只有可操纵的静态源码上下文 `CTX` 才是实验因素，并计入静态因素覆盖率。
- 目标指令固有的类型、限定符、形状和内存语义属于 `SF`；改变它们意味着更换研究对象。
- 生产者、消费者、定义—使用关系、相邻模式和目标值自身的局部存活/使用关系统一归入“数据流拓扑”，不再重复建维度。
- 寄存器类别、立即数编码、值物化、融合、寄存器溢出和调度属于 `OBS`，只能作为编译结果。
- 测试骨架和结果观测点属于 `FX`，实际输入和动态执行事实属于 `RUN`，代码生成、分析和运行环境属于 `ENV`。

因此，实验真正要回答的是：

> 在代码生成环境、分析环境以及目标 PTX 语义形态保持不变时，改变某个静态源码上下文，SASS 效应图是否变化、如何变化，这种效应在什么条件下成立？

最终产物不是一张“PTX 操作码 → SASS 操作码”对照表，而是一组带适用条件、证据、反例和未解决项的候选目标代码落地规律。

## 一眼看懂六类变量

六类变量在实验中并不是同等级的“六个维度”，而是六种不同角色：

```text
ENV + SF：限定在哪个环境中、研究哪一种 PTX 语义形态
    ↓
主动改变适用的 CTX
    ↓
用匹配的 FX 生成可编译、可观测的实验用例
    ↓
编译和分析，记录 OBS
    └─ 必要时按 RUN 执行，验证语义或测量性能
```

| 角色 | 人类读法 | 它回答的问题 | 在实验中的用法 |
|---|---|---|---|
| `ENV` | 实验环境 | 代码在什么架构、编译器、分析工具和硬件条件下生成、观测或运行？ | 固定后单独报告，或做跨环境配对 |
| `SF` | 研究对象 | 当前研究的是哪一种 PTX 指令语义形态？ | 定义目标身份；改变它表示换了研究对象 |
| `CTX` | 静态上下文 | 哪些编译前可见的源码条件被主动改变？ | 唯一计入静态因素覆盖的实验因素 |
| `FX` | 测量方式 | 怎样让目标可编译、可观测，并检查测量本身的影响？ | 作为匹配的测量区组，不计入静态因素覆盖 |
| `RUN` | 运行条件与事实 | 已生成的代码用什么输入和启动配置执行，实际走了哪条路径？ | 用于动态正确性与性能验证，不增加静态覆盖 |
| `OBS` | 观测结果 | 编译器最终生成了什么，运行后表现如何？ | 作为响应变量记录，不能反向充当输入因素 |

容易放错的内容可以用下面这张表快速判断：

| 容易误当成 `CTX` 的内容 | 正确归属 |
|---|---|
| 目标指令的类型、限定符、状态空间、内存序、作用域和形状 | `SF` |
| 测试骨架、结果观测点、对照和等价源码写法 | `FX` |
| 实际输入、活动线程集合、动态地址关系和实际执行路径 | `RUN` |
| GPR/UR/P/UP 分配、立即数编码、融合、溢出、活跃区间和调度 | `OBS` |
| 编译器版本、目标 SM、分析工具、GPU 和驱动 | `ENV` |

## 真正需要扫描的七组静态因素

`CTX` 内部保留七组互补的静态因素：

| 因素组 | 它研究什么 | 典型例子 |
|---|---|---|
| 操作数与值实例化 | 每个源码操作数以什么形式和值出现 | 立即数或寄存器、精确位模式、编译期已知性、修饰符、操作数是否同一 |
| 数据流拓扑 | 目标值从哪里来、被谁使用以及跨越什么区域 | 生产者、消费者、使用次数、距离、基本块、循环或调用边界 |
| 谓词、控制流与参与性 | 目标位于怎样的静态控制条件和参与构造中 | 谓词守卫、控制依赖、CFG 位置、收敛或参与方式 |
| 内存、地址与访问关系 | 地址如何形成，目标与周边访存有什么关系 | 指针来源、静态对齐、偏移、别名、相邻访问和栅栏 |
| 异步、屏障与张量协议 | 目标处于怎样的协议生命周期中 | 组状态、等待深度、屏障阶段、流水线和资源生命周期 |
| 资源压力构造 | 源码怎样制造寄存器、指令级并行或代码规模压力 | 活跃值、干涉关系、独立链、代码规模和显式内存占用 |
| 函数、ABI 与源码指示符 | 目标处于怎样的函数和接口上下文 | 调用、参数与返回、可见性、链接属性和源码策略 |

不是每个语义形态都适用全部七组因素。例如，普通整数加法通常不需要协议生命周期因素，TMA 指令则同时涉及地址、参与性和协议因素。实验只组合当前语义形态适用且合法的因素，不构造“所有指令 × 所有因素”的全局笛卡尔积。

## 用一个最小例子理解这套划分

假设研究一条 `add.u32`：

1. 固定目标 SM、`ptxas` 版本、编译选项以及分析工具和配置，这是 `ENV`；若进行动态比较，还要固定运行环境。
2. 固定操作码、类型、结果形状和限定符，这是 `SF`。
3. 只改变一个源操作数是立即数还是 PTX 虚拟寄存器操作数（其值在编译期未知），这是 `CTX` 中的“操作数与值实例化”。
4. 保持数据流、控制流、资源构造和函数/ABI 等其他适用 `CTX` 相同，并使用匹配的测试骨架和结果观测点；生成后检查规范化 PTX/AST，确认预期的立即数/寄存器变化确实实现。
5. 比较两份产物中的 SASS 操作、立即数处理、寄存器路由、融合和调度差异，这些都是 `OBS`。
6. 如果还要验证结果正确性或实测性能，再为两份产物配置匹配的有效操作数值和启动参数，这是 `RUN`。

这个例子也说明了两条边界：

- 把 `add.u32` 改成另一种类型或操作模式，研究的是不同 `SF`，不能解释成同一目标的上下文效应。
- 生成结果使用 GPR、UR、立即数还是额外物化指令，是 `OBS`，不能预先写成源码输入因素。

## 为什么研究单位是 SASS 效应图

优化后的 PTX 与 SASS 是多对多关系。一条 PTX 指令可能被删除、展开、融合、复制或移动；一条 SASS 指令也可能同时服务多个 PTX 指令实例。

因此，主要研究单位是：

```text
源码模式组 + 静态上下文
→
SASS 效应图
```

SASS 效应图不仅包含核心操作，还包含为实现该语义所需的操作数准备、谓词与路径控制、地址计算、参与和完成协议，以及这些节点之间的数据、控制和顺序关系。单个 PTX 指令实例仍保留定位与归属证据，但不强制把共享的 SASS 节点切成互斥的一对一指令片段。

## 一次实验如何形成可归因的比较

一次完整实验按以下顺序进行：

1. 冻结或明确分层 `ENV`。
2. 选择指令族和一个合法的 `SF`。
3. 从适用性清单中选择可操纵的 `CTX` 因素和合法水平。
4. 选择匹配的 `FX`，生成基线、单因素、必测交互和探索用例。
5. 检查生成后的规范化 PTX/AST，确认预期的 `CTX` 处理和测量控制确实实现。
6. 在固定代码生成环境下编译，并在固定分析环境下反汇编、归属和生成结果指纹。
7. 比较 `OBS`；需要语义或性能证据时，再按声明的 `RUN` 执行。

不同变化回答不同问题：

| 发生变化的部分 | 可以解释的问题 |
|---|---|
| 同一 `SF` 内只改变 `CTX` | 静态上下文效应 |
| 在同一指令族内改变 `SF` | 不同语义形态的代码生成差异 |
| 改变编译器、目标架构或编译选项 | 环境差异 |
| 改变测试骨架、结果观测点或等价源码写法 | 测量方式与源码表现形式的影响 |
| 只改变输入、启动配置或实际执行路径 | 动态正确性或性能差异，不是静态上下文效应 |

配对比较必须保持其他可匹配坐标一致。若多个条件同时变化，只能报告联合变化，不能把结果归因于其中某一个因素。单因素测试没有出现主效应，也不能成为删除该因素或跳过交互测试的依据。

## 如何解释观测结果

`OBS` 至少记录四类信息：

- 映射拓扑和完整 SASS 效应图，包括删除、吸收、融合、展开、共享和多路径结果；
- 规范化后的目标代码落地结构，以及寄存器和谓词的分配与路由；
- 调度、控制元数据、精确编码和原始代码产物；
- 静态成本，以及与 `RUN` 绑定的动态成本。

目标被编译器消除也是一种合法结果；目标被其他指令吸收或与其他目标共享 SASS 节点时，也必须显式记录。

以下判断彼此独立：源码是否符合规范、目标是否受支持、预期源码变化是否真正生成、编译是否成功、反汇编是否完整、目标是否存在、归属是否可靠、程序是否运行成功、语义是否正确。它们不能压缩成一个“最高证据等级”。

静态目标代码落地、动态语义验证和性能测量也要分别报告。无法解析、归属、解码或建立正确性判定器的对象保留为未解决项，不能静默丢弃。

## 产物、覆盖与结论边界

实验最终形成：

1. 带上下文条件、SASS 效应图、证据和反例的候选目标代码落地规律；
2. 七组静态因素及关键交互对代码生成、资源分配和调度控制的影响矩阵；
3. 在固定环境、测试空间和结果定义下成立的观测等价类；
4. 可供后续指令选择、语义验证和成本建模使用的候选数据库，以及未解决项集合。

所有结论都限定在版本化环境、声明测试空间、覆盖分母和观测工具之内：

- 只有穷举了形式化定义的有限空间、所有可达用例都有完整且可审计的状态记录，并且未解决项为空，才能声称“相对于该测试空间完整”。
- 组合测试只能声称相应阶数的可达组合已经覆盖。
- 规则驱动或随机探索只能报告已观测候选、覆盖指标和未解决空间。
- 静态映射发现本身不证明候选语义正确，也不证明生成结果性能最优。

# ptxas 指令选择集合

## 实验目的

本实验的目标不是建立一张静态的“PTX opcode → SASS opcode”对照表，而是在固定编译环境和版本化测试模型下，系统发现并分类上下文敏感的 PTX→SASS lowering 变体。需要观察的结果包括核心指令变化、operand folding、融合、消除、寄存器类别转换，以及 operand、predicate、participation 和 completion 等准备或协议序列。

实验产物是带有上下文条件和证据的**候选 lowering 记录**：

```text
PTX semantic pattern
+
tested context condition
+
source coverage
→
observed SASS effect slice
+
core / preparation / participation / completion labels
+
legality and validation status
+
cost observations
```

在尚未形式化并穷举一个有限输入宇宙之前，结果只能称为：

> 在所声明测试空间和固定编译环境下观察到的候选 SASS lowering 变体集合。

本实验本身不证明目标架构上的绝对完整性，不单独证明候选的语义正确性，也不证明候选是最优实现。语义正确性需要独立的规范推理、差分执行或专门 oracle；最优性需要后续成本模型和选择算法验证。

## 研究对象与结果口径

优化编译后的 PTX 与 SASS 不是一对一关系。一条 PTX 指令可能被删除、展开为多条 SASS、与其他 PTX 融合、被复制或移动；一条辅助 SASS 也可能服务于多个 PTX 操作。因此主要记录单位应是**目标 PTX occurrence 及其完整 effect slice**，而不是预设的一条“核心 SASS”。

`Core operation`、`Operand preparation`、`Predicate preparation`、`Participation protocol` 和 `Completion protocol` 是 effect slice 内的二级标签。对 `tcgen05`、TMA、mbarrier、collective 等复杂指令，participation 或 completion 序列可能属于语义实现本体，不能仅凭 opcode 名称将其排除为无关 scaffold。

每个结果至少区分以下三个观察层级：

```text
exact:
    原始机器码、operand encoding、控制字段和 relocation

allocation:
    允许物理寄存器编号做 alpha-renaming，
    但保留 GPR/UR、P/UP、寄存器对、predicate polarity 等分配属性

lowering:
    对标签和无关编号规范化后的 opcode、operand、def-use 和 CFG 形态
```

删除、融合、展开、无法归属和未实现预期处理条件都应作为显式结果，而不是强行归入 `1:1` 或 `1:N`。源行或 `.loc` 信息只能作为辅助定位证据，不能单独充当 PTX→SASS 因果归属规则。

## 变量角色

实验前需要区分三类变量，避免把编译器输出误当成可独立操纵的输入：

1. **环境分层**：目标 SM、PTX ISA、`ptxas`、优化等级、RDC/LTO 等。每个完整环境元组分别形成一个结果集合，不跨环境合并。
2. **可操纵的 PTX 上下文**：operand 位型和来源、def-use 形态、producer/consumer、CFG、predicate 构造、函数和内存语义等。
3. **编译后观测或中介变量**：最终 GPR/UR/P/UP 类别、立即数是否直接编码、是否 materialize、实际 live range、spill、调度距离和融合结果等。

对第三类变量，测试应操纵其可控前因，并在编译产物中执行 manipulation check；不能仅根据源码构造宣称目标状态已经实现。

## 候选上下文维度

以下列表是用于建立测试模型的候选因素清单，不声称已经穷尽所有可能影响 lowering 的程序上下文。每个因素的精确水平、约束和上限将在实验范围中另行确定。

第一类是操作数上下文。即使语义 opcode 相同，操作数形态不同也可能改变 SASS：

```text
普通寄存器操作数
同一寄存器重复出现
不同寄存器
destination 与 source 相同或不同
不同位型和数值类别的立即数
可能处于编码或优化规则边界的立即数
整数 0、±1、最小值和最大值
浮点 +0、-0、normal、subnormal、Inf 和 NaN
uniform value
varying value
命名符号地址
纯立即数地址
寄存器地址
寄存器加立即数偏移
带 neg、abs、not 等 operand modifier
```

还需要分别测试操作数位于不同源位置的情况，因为目标指令的各个源槽位不一定具有相同的立即数、常量或 modifier 编码能力。`RZ`、直接立即数编码和 materialization 是编译后的观察结果；只有在编码规则已经独立建立并验证时，才能将“可编码/不可编码”用作预先定义的输入分区。立即数分区也不能默认由少量代表值覆盖，具体等价类需要由编码规则、边界变异和实验结果共同建立。

第二类是 def-use 上下文，也就是结果如何被使用：

```text
结果无使用
结果单次使用
结果多次使用
结果立即被下一条消费
结果距离 1 条指令后消费
结果距离 2–4 条指令后消费
结果跨基本块消费
结果作为地址
结果作为 load/store 的数据
结果作为 predicate 或控制操作数
结果作为 convert、pack 或特殊指令的操作数
结果作为函数参数或返回值
结果在相同 predicate 下使用
结果在相反或无关 predicate 下使用
结果跨 branch、loop、call 或同步边界保持存活
```

这是优先级较高的一类候选因素。single-use、multi-use、消费者类别、guard 关系和控制流边界可能共同决定中间结果是否具备融合条件，但其中任何单一条件都不能在实验前被视为充分条件。

“结果无使用”和“结果需要保活观察”应分成不同实验轨道。无使用的纯操作可能被合法删除；为了观察结果而加入 store、return 或其他 sink，又会改变 consumer、活跃区间和融合机会。因此需要把删除记为显式优化结果，并使用匹配对照和不止一种观察 sink 检查观察器效应。

第三类是生产者上下文，即当前指令的输入从哪里来：

```text
普通计算结果
move/cvt 的结果
比较结果
select 的结果
地址计算结果
不同 state space 的 load 结果
函数参数
函数调用返回值
atomic、collective 或 shuffle 的结果
uniform-valued producer
特殊寄存器
跨基本块传入的值
loop-carried value
```

这里描述的是“当前值由什么产生”，与第一类描述的“当前操作数以什么形式出现”分开。例如当前指令可能和前驱融合，或者前驱的转换可能被折叠进当前指令。改变 producer 往往同时改变延迟、副作用、值域和活跃性，因此差分结果只能解释为该构造下的条件效应，不能自动归因为单一抽象因素。

第四类是相邻指令 pattern：

```text
mul + add
add + add
shift + logic
compare + branch
address-add + load/store
convert + arithmetic
load + arithmetic
arithmetic + store
neg/abs + arithmetic
min/max/select pattern
bitfield extract/insert + logic
pack/unpack + arithmetic
wide/narrow conversion pattern
shuffle/vote + arithmetic
atomic result + arithmetic/branch
```

这份列表只能作为 pattern 家族，而不能作为穷举的 opcode pair。具体实验可以从已知的融合、folding、寻址、比较控制、类型转换和协议准备规则反向生成候选组合，但还需要保留不依赖已知规则的组合或变异测试，避免只重新发现预期中的 lowering。

连续短窗口可以作为局部 pattern 的起点，但不能被视为编译器依赖范围的上界。编译器可能沿 def-use 跨越中间指令，也可能受更长 DAG、CFG、代码尺寸和资源阈值影响。窗口、数据流图和跨基本块关系的具体上限属于后续实验范围；任何上限都必须同时进入结论边界。

第五类是 predicate 上下文：

```text
无 predicate
编译期恒真 predicate
编译期恒假 predicate
普通 P predicate
uniform UP predicate
相同 predicate 的连续指令
predicate 取反
不同且无关的 predicate
predicate 来自 compare
predicate 来自逻辑组合
uniform predicate
divergent predicate
predicate 单次使用
predicate 多次使用
生产者和消费者具有相同、相反或无关的 guard
```

相同的计算语义在 predicated 和 non-predicated 情况下，可能使用相同核心 opcode，但出现不同 predicate preparation；复杂指令甚至可能改变完整 lowering 序列。编译期恒真或恒假的 predicate 还可能被规范化或删除，应记录为优化结果。

`P`/`UP` 是编译后寄存器类别，uniform/divergent 是值的语义或分析属性，两者需要分开记录。测试应明确区分“运行时实际 uniform”“编译器可证明 uniform”和“最终分配到 UP”，不能把三者视为同一个输入因素。

第六类是寄存器类别和转换结果：

```text
GPR
UR
P
UP
寄存器对
向量或多寄存器 operand
需要 GPR→UR
需要 UR→GPR
需要 GPR/UR→P/UP
需要 P/UP→GPR/UR 或重新物化
```

特殊寄存器直接读取属于生产者上下文，不和通用寄存器类别混在一起。这类现象对 `tcgen05`、collective 和 uniform operand 尤其重要，核心 SASS 可能不变，但周围的 `R2UR`、`S2UR`、`UMOV` 等会变化。

这些类别和转换多数是 lowering 的观测结果。实验输入应描述值的来源、编译器可见的 uniformity 证据、消费者约束和 live-range 构造；编译后再检查是否真正得到预期的 GPR/UR/P/UP 类别或转换序列。未实现预期类别的 case 应标记为 `DESIGN_NOT_REALIZED`，而不是当作该类别的阴性结果。

第七类是副作用和同步边界：

```text
普通 ALU 前后
load/store 前后
atomic/reduction 前后
fence/membar 前后
barrier 前后
mbarrier 前后
async 操作前后
branch 前后
call/return 前后
exit/trap 前后
```

这些上下文主要用于观察副作用或同步边界是否改变 `ptxas` 的融合、删除、移动或复用决策，而不是仅凭编译结果判定某种变换在语义上是否合法。对于内存和同步指令，还需要与第十一类中的 memory order、scope 和别名关系组合测试，并由独立语义验证判断候选变换是否可采用。

第八类是编译环境分层：

```text
目标 SM
PTX ISA 版本
PTX target
CUDA Toolkit 版本
ptxas 精确版本
优化等级
完整编译命令和 ptxas 选项
debug、line-info 和 instrumentation 选项
RDC、device link 和 LTO 模式
寄存器数量限制和 spill 相关选项
```

“固定环境”是指在一次结果集合内固定完整环境元组，而不是永远只研究一套配置。目标架构、`ptxas` 版本、优化等级、RDC/LTO 和其他完整命令行只要不同，就应形成独立环境分层，分别报告候选集合，不能合并后仍称为固定环境。

还需要记录编译、链接和反汇编所处的阶段，以及相关工具二进制版本或哈希、完整 argv、环境变量、stdout/stderr 和原始产物。offline `ptxas`、device link 后 cubin 和 driver JIT 的结果属于不同管线。这里的寄存器数量限制是环境或编译选项；周围代码造成的实际寄存器压力属于后面的控制流与活跃性构造。

第九类是指令自身形态。它严格来说不是上下文，但如果没有先枚举或固定，就无法判断不同 SASS 是由上下文还是由 PTX 指令本身的语义差异造成：

```text
数据类型
位宽
signed、unsigned 和 bit 类型
标量和向量宽度
舍入模式
sat、ftz、approx 等修饰
多 destination 形式
state space
cache、eviction 和 prefetch modifier
memory order
thread scope
```

只组合目标 PTX ISA 明确定义为合法的形态，避免把非法组合计入正向实验空间。整数和浮点指令族、普通内存访问、atomic、tensor 和 collective 指令族应分别建立带版本和 target feature 约束的合法参数表。

`ptxas` 接受某段 PTX 只说明它通过了当前工具的检查，不自动证明整个程序具有已定义语义。实验记录应区分规范合法、成功汇编、成功反汇编、可运行和语义验证通过等证据等级。

第十类是控制流与活跃性上下文：

```text
同一基本块内
条件分支之前或之后
分支两侧
分支汇合处
循环外
循环内
loop-carried value
跨函数调用
短 live range
长 live range
与少量其他值同时存活
与大量其他值同时存活
低、中、高实际寄存器压力
```

这一类既可能影响融合和代码移动，也可能影响寄存器分配、spill、重计算以及指令选择。实际寄存器压力应通过可审计的 live-range 构造来操纵，而不是只依赖 `maxrregcount`；同时需要在编译结果中检查活跃值、寄存器数和 spill，确认名义上的“低/中/高压力”确实被实现。具体分级和阈值留待实验范围确定。

第十一类是内存依赖、地址和别名上下文：

```text
无相邻内存操作
相邻访问确定不别名
相邻访问可能别名
相邻访问确定同址
访问范围部分重叠
相同访问宽度
不同访问宽度
自然对齐
允许但非自然对齐
generic address
明确的 global、shared、local、const 或 param state space
weak、volatile、relaxed、acquire、release 和 acq_rel
cta、cluster、gpu 和 sys scope
普通、atomic、reduction 和 MMIO 访问
不同 cache policy 或 eviction hint
```

这些维度可能共同决定 load/store 是否具备合并、删除、重排或采用不同协议的条件。不是所有 memory order、scope 和 state space 组合都合法；语法合法也不保证并发程序没有未定义行为。生成实验时需要依据目标 PTX ISA 版本过滤，并将静态 lowering 观察与需要并发 litmus 或运行时 oracle 的语义验证分开。

第十二类是函数、ABI 和链接上下文：

```text
entry kernel
device function
leaf function
包含调用的 non-leaf function
可内联调用点
禁止或无法内联的调用点
直接调用
间接调用
参数通过 param space 传递
返回值
不同函数可见性和 linkage
单一编译单元
separate compilation
device link
LTO
launch bounds、maxntid、minnctapersm 和 maxnreg 等函数属性
```

这类上下文可能改变参数搬运、寄存器约定、prologue/epilogue、栈访问、内联结果和跨函数优化，因此需要与单纯的局部指令上下文分开记录。

## 实验有效性要求

### 可观察性

不存在适用于所有指令族的中性“最小可观察基线”。实验至少区分：

1. **存活 lowering**：使用运行时未知输入和匹配的观察 sink，使目标 effect 可见，并检查 sink 是否引入融合或额外协议。
2. **优化结果**：允许 dead-code elimination、constant folding、copy propagation 和 fusion 发生，将目标消失或不再具有独立 SASS 记为结果类别。

同一结论应尽可能由多个匹配基线或不同 sink 支持。除目标处理外，fixture 的参数 ABI、符号布局和无关代码应尽量保持一致；无法保持的变化需要作为伴随因素记录。

### 处理实现检查

每个 testcase 不仅要记录生成器声明的上下文，还要验证编译器实际看到或产生的条件。例如：

```text
声明 single-use      → 检查优化后是否仍为单次使用
声明跨 N 条指令      → 分开记录源码距离和最终调度距离
声明 uniform         → 区分语义 uniform、可证明 uniform 和最终 UR/UP
声明高寄存器压力     → 检查寄存器数、spill 和实际 live-range 构造
声明相同 predicate   → 检查目标 effect slice 的最终 guard 关系
```

处理没有实现时应记录 `DESIGN_NOT_REALIZED`，不能把“输出未变化”解释为该因素没有影响。

### 对照与证伪

实验框架至少需要：

```text
空白对照：
    删除目标 PTX pattern，检查提取器是否错误归属周围 SASS

阳性对照：
    使用已知会改变 lowering 的 pattern，检查框架能否发现差异

规范化阴性对照：
    仅改变虚拟寄存器名、标签名等预期无关信息，
    检查规范化后 fingerprint 是否稳定

交互故障注入：
    构造只在二阶或更高阶组合下出现的结果，
    检查组合生成和分析流程不会因缺少主效应而漏报

重复性检查：
    相同输入和环境在独立进程中重复编译，
    确认目标代码与规范化结果是否确定
```

### 证据等级

每个候选应独立记录证据等级，避免把“成功汇编”当成“语义正确”：

```text
SPEC_LEGAL
ASSEMBLES
DISASSEMBLES
TARGET_ATTRIBUTED
RUNTIME_EXECUTED
SEMANTIC_PASS
```

同时使用互斥状态记录不能进入正向候选集的情况：

```text
SPEC_ILLEGAL
TARGET_UNSUPPORTED
COMPILE_REJECTED
DESIGN_NOT_REALIZED
TARGET_ELIMINATED
ATTRIBUTION_UNKNOWN
PARSER_UNSUPPORTED
```

对于无法运行或尚未建立 oracle 的候选，可以保留静态证据，但不能升级为已经验证的选择规则。

## 枚举与交互策略

具体因素水平、测试上限和交互阶数留待实验范围确定；本节只规定不会因筛选逻辑产生系统性漏报的原则。

1. 为每个环境分层建立不可变 manifest，固定完整工具链、命令、阶段和原始产物记录方式。
2. 为指令自身形态和上下文因素建立版本化、带约束的测试模型，区分规范非法、目标不支持和生成器无法构造的组合。
3. 使用多个匹配基线做单因素差分，以理解局部条件效应和校验测试框架。单因素无差异不能用于永久淘汰该因素。
4. 组合测试必须覆盖所有纳入模型的因素，而不是只组合已经观察到主效应的因素。pairwise 或其他 t-wise 覆盖只能证明相应阶数的组合覆盖，不能推出不存在更高阶交互。
5. 对已知需要多个前提的高风险簇做受约束的组合测试，例如：

   ```text
   source slot × operand form × value class × modifier
   producer × consumer × use topology × guard
   state space × width × alignment × alias × order × scope
   value provenance × live-range construction × CFG × ABI environment
   ```

6. 使用不依赖已知 lowering 规则的 grammar-based mutation、边界变异或独立 holdout，降低只验证既有认知的偏差。
7. 对新出现的候选执行 witness 最小化，并用反向修改或删除单个 guard 的测试尝试证伪其适用条件。差分观察首先形成“候选规则”，只有经过语义和反例验证后才能升级为选择规则。
8. 保存原始 PTX、完整 argv 和环境、stdout/stderr、编译及链接产物、反汇编、资源统计，以及 exact/allocation/lowering 三层 fingerprint。规范化结果不能替代原始证据。

## 完成条件与结论强度

完成条件必须与实验声明匹配：

- 如果穷举了形式化的有限上下文宇宙，且所有 testcase 都进入互斥、可审计的终态，可以声称“相对于该版本化测试宇宙完整”。
- 如果只完成 t-wise 组合覆盖，只能声称“所有可达 t-tuple 已覆盖”。
- 如果使用规则驱动或随机探索，只能报告已观察候选、覆盖指标、独立 holdout 结果和未解决空间；若干轮没有新变体不能证明完整。

任何可达组合未覆盖、输出不确定、处理未实现、目标无法归属、程序语义未定义或解析器无法识别新 SASS 时，都必须保留为未解决状态，不能静默跳过或计入完整集合。

## 预期产物

在上述证据边界内，实验可以产生：

1. 每个 PTX semantic pattern 的已观察 lowering 候选和最小 witness。
2. 上下文因素对 core、preparation、protocol、fusion 和 elimination 的观察影响矩阵。
3. 在固定环境、测试空间和规范化规则下成立的**观测等价类**。
4. 已被证据支持的相关属性候选集；未观察到影响的属性不能直接从 Semantic IR 或 Target IR 删除。
5. 带 source coverage、guard、证据等级和成本观察的候选数据库，作为后续 Fixed-order Instruction Selection 原型的输入语料。

该数据库足以启动后续选择器原型和独立语义验证，但在 guard 尚未证伪、effect slice 尚未可靠归属或语义 oracle 尚未通过时，不能被当作可直接采用的正确规则库。

观察到 `ptxas` 生成某种 SASS 也不证明该变换能由保持源顺序的选择器实现，因为 `ptxas` 本身可能使用重排、跨基本块分析或全局资源决策。Fixed-order 能力边界需要由后续受约束原型或独立证明建立，本实验只能提供候选和反例。

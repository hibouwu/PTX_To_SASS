## 实验目标与结论边界

本实验不是建立静态的“PTX 操作码 → SASS 操作码”对照表，而是在固定编译环境和声明测试空间内，系统发现并分类受上下文影响的 PTX→SASS 目标代码落地（lowering）变体。

需要观测的不只是核心 SASS 操作码，还包括操作数/谓词准备、融合与消除、地址与协议序列、寄存器路由、调度控制以及不同执行路径。

实验产物是带上下文条件和证据的候选目标代码落地规律。除非额外完成相应证明或验证，否则不能声称：

- 已覆盖目标架构上的全部目标代码落地方式；
- 候选变换已经语义正确；
- 当前实现是性能最优；
- 若干轮没有新结果就意味着搜索空间完整。

结论始终限定在版本化环境、声明测试空间、覆盖分母和观测工具之内。

## 核心设计思路

### 以 SASS 效应图为研究单位

优化后的 PTX 与 SASS 是多对多关系：PTX 指令可能被删除、展开、融合、复制或移动，一条 SASS 指令也可能服务多个 PTX 指令实例（occurrence）。

因此主要研究单位是：

```text
源码模式组（source pattern group）
→
SASS 效应图（effect graph）
```

单个 PTX 指令实例仍保留定位和归属证据，但不强制切成互斥的一对一指令切片（instruction slice）。

### 严格分离研究对象、输入因素和观测结果

- 改变目标指令自身的类型、限定符、操作数/结果形状或操作模式，意味着改变语义形态（semantic form）。
- 只有可操纵的静态源码上下文才属于实验因素。
- GPR/UR/P/UP、寄存器溢出、值物化、融合、最终活跃区间和调度属于编译后结果，不能反向作为输入维度。
- 测试骨架（fixture）、结果观测点（sink）和运行负载（workload）用于测量或验证，不进入目标语义种子（semantic seed）。

### 只组合适用因素

不同 PTX 指令族具有不同的合法语法、语义约束和目标代码落地机制。实验不建立“所有指令 × 所有因素”的全局笛卡尔积，而是为每个语义种子声明适用因素和合法组合。

单因素测试用于理解局部效应；已知的高风险交互通过受约束的组合方案（recipe）预先覆盖；语法变异、边界变异和留出测试用于发现未知规律。单因素测试未观测到主效应，不能成为删除该因素或跳过交互测试的依据。

### 使用显式配对比较

- 在同一语义形态内改变 `CTX`，研究上下文效应。
- 改变类型、状态空间、内存序、作用域等 `SF` 字段，使用配对语义形态比较（paired-form comparison）。
- 改变 SM 架构、编译器或优化选项，使用配对环境比较（paired-environment comparison）。
- 改变测试骨架、结果观测点或源码写法，使用匹配的测量/对照比较（matched measurement/control comparison）。

配对只比较共有且可匹配的坐标，不能把同时变化的多个条件解释成单一因素效应。

### 将证据判断保持正交

规范合法、目标支持、源码处理已实现、编译成功、解析完整、目标存在、归属可靠、运行成功和语义正确是不同问题。它们必须分别判断，不能压缩成一个“最高证据等级”。

## 变量角色与维度划分

实验采用六层变量角色。只有 `CTX` 表示静态上下文因素；其他层分别表示环境、研究对象、测量条件、运行实现或观测结果。

| 层级 | 角色 | 主要内容 | 是否计入静态因素覆盖 |
|---|---|---|---|
| `ENV` | 环境分层 | 代码生成、分析和运行时环境 | 否，按环境分别报告或进行配对比较 |
| `SF` | 目标身份 | 操作码、类型、限定符、形状和目标指令固有语义 | 否，用于定义语义形态 |
| `CTX` | 静态可操纵上下文 | 操作数、数据流、控制流图、内存关系、协议、资源和 ABI | 是 |
| `FX` | 测试骨架与测量控制 | 测试骨架、结果观测点、观测路线（observability track）、对照和源码变体（source variant） | 否，作为测量区组（measurement block） |
| `RUN` | 运行负载与实际运行事实 | 输入、启动配置、实际参与集合、动态别名/对齐关系和执行路径 | 否，不增加静态覆盖 |
| `OBS` | 编译后中介与结果 | SASS 效应图、资源分配、寄存器溢出、调度、编码和成本 | 否，只作为响应变量 |

概念性的身份链为：

```text
指令族（instruction family）
→ 语义形态
→ 语义种子
→ 逻辑用例（logical case）
→ 源码与代码生成实例
→ 目标代码落地结果或运行时观测
```

具体身份字段和去重规则见详细规范。

### 环境分层

| 环境 | 回答的问题 |
|---|---|
| 代码生成环境（codegen environment） | 在什么架构契约、PTX 源码契约、编译流水线和选项下生成代码 |
| 分析环境（analysis environment） | 使用什么反汇编器、解析器、归属方法和结果指纹（fingerprint）方法观测产物 |
| 运行时环境（runtime environment） | 在什么 GPU、驱动程序、时钟/功耗策略和测量工具下执行 |

三类环境必须分开。只改变解析器不应产生新的代码生成测试用例；只改变 GPU 或输入也不应增加静态上下文覆盖率。

### `SF`：目标指令自身的语义形态

`SF` 描述目标 PTX 指令固有的语义形态，主要包括：

- 操作码与子操作（sub-operation）；
- 标量、向量、打包（packed）或张量类型链；
- 位宽、解释方式、舍入、饱和（`sat`）、非规格化数清零（`ftz`）等限定符；
- 内存状态空间、内存序、作用域、缓存/代理（cache/proxy）语义；
- 操作数/结果形状与多结果角色；
- 比较模式、洗牌模式、张量形状、完成模式等指令专属控制。

普通数据值、地址偏移量、谓词守卫、生产者和消费者不属于语义形态。跨语义形态的差异不能解释成同一语义种子的上下文效应。

### 静态上下文的七个因素组

| 因素组 | 研究内容 | 明确排除 |
|---|---|---|
| 操作数与值实例化 | 各源码槽位的表面表示、精确值、编译期已知性、修饰符和操作数同一性/定义关系 | 地址构造；最终立即数、零寄存器（RZ）或值物化结果 |
| 数据流拓扑 | 生产者、结果使用边、消费者、距离、区域和跨边界关系 | 最终 SASS 使用拓扑；独立的“相邻模式”维度 |
| 谓词守卫、控制流图与参与性 | 目标谓词守卫、控制依赖、控制流图（CFG）位置，以及编译器可见的参与/收敛构造 | P/UP 分配；运行时实际参与集合 |
| 内存、地址与访问关系 | 地址表达式、指针/对象来源（provenance）、静态对齐、相关访问、别名、代理和栅栏关系 | 目标指令自身的状态空间/内存序/作用域；实际运行地址事实 |
| 异步/屏障/张量协议生命周期 | 相邻协议节点、组/屏障状态、流水线、完成条件和资源生命周期 | 目标指令固有的完成模式；最终生成的协议序列 |
| 资源构造 | 源码层的活跃值、干涉关系、指令级并行度（ILP）、代码规模和显式内存占用构造 | 最终寄存器数、寄存器溢出、占用率和调度 |
| 函数、ABI 与源码指示符 | 函数/容器、调用、参数/返回、可见性/链接属性和源码策略 | 实际内联、函数序言/尾声、栈的目标代码落地；RDC/LTO |

生产者、定义—使用关系（def-use）、消费者、相邻模式和局部活跃性统一由数据流边/区域描述。`mul+add`、`compare+branch`、`load+arithmetic` 等属于因素组合方案，不是新的独立维度。

### 测试骨架、运行时条件与观测结果

`FX` 将目标放入可编译、可观测的程序中，并通过不同结果观测点、空白对照、伪处理对照、阳性对照、规范化阴性对照以及重复编译，估计观测工具效应（observer effect）。源码变体与真正的重复编译需要分开。

`RUN` 描述如何执行已经生成的代码产物，以及实际参与集合、地址关系和执行路径。运行时环境、运行负载意图和单次运行事实（trial fact）三者不得混合。

`OBS` 至少从以下视角记录结果：

- 映射拓扑与 SASS 效应图；
- 规范化后的目标代码落地结构；
- 寄存器/谓词分配与路由；
- 调度/控制元数据；
- 精确编码、原始代码产物和静态/动态成本。

## 原维度划分的去冗余结论

原有维度的覆盖面基本合理，但需要做以下合并和迁移：

1. 将生产者、定义—使用关系、消费者、相邻模式、控制流图/活跃性中重复的数据流关系合并到同一数据流模型。
2. 将指令自身的类型、限定符、形状、内存序/作用域等移入 `SF`，不与 `CTX` 混算。
3. 将 GPR/UR/P/UP、转换、寄存器溢出、值物化、融合和调度移入 `OBS`。
4. 将内存相关内容拆成目标固有语义、地址构造、访问关系和实际运行事实。
5. 将异步/张量/屏障相关内容拆成目标语义形态、周围协议生命周期和观测到的协议序列。
6. 将编译器、观测工具和运行时硬件拆成三类环境。
7. 将测试骨架、结果观测点、对照和运行时输入从语义种子中移出。

这样可使每个概念只有一个主要归属，同时允许组合方案引用多个因素组形成交互测试。

## 实验空间组织

整体流程为：

```text
冻结环境
→ 枚举指令族、语义形态和语义种子
→ 确定适用的 CTX 因素与合法约束
→ 生成基线、单因素、强制交互和探索用例
→ 加入匹配的测试骨架、结果观测点和对照
→ 编译、反汇编、归属并生成结果指纹
→ 按需执行运行时语义/性能验证
→ 形成候选目标代码落地规律、反例和未解决项集合
```

A/M/C/P/F 等生成器类别只负责把语义形态路由到合适的测试用例生成器，不是科学维度，也不是互斥的结果分类。

## 有效性、覆盖与结论强度

### 有效性原则

- 在生成后的源码上执行处理实现检查（manipulation check），确认预期实验处理（intended treatment）确实存在；编译器随后消除或改写该处理属于观测结果，不代表实验处理未实现。
- 使用空白、伪处理、阳性、规范化阴性、交互故障和可重复性对照，检查归属、规范化和组合生成能力。
- 目标被消除是合法的目标代码落地结果；被其他指令吸收、融合或共享时也应独立记录。
- 静态目标代码落地证据、动态语义验证和性能测量应分别报告。
- 无法解析、归属、解码或建立正确性判定器（oracle）的对象应保留为未解决项（unresolved），不能静默丢弃。

### 覆盖与完成标准

至少分别报告语义形态、因素水平（factor level）、可达 t 元组（t-tuple）、必测组合方案、测试骨架/源码、观测工具敏感性和留出测试的覆盖情况。

- 穷举形式化有限空间时，才能声称“相对于该测试宇宙完整”。
- t 阶组合测试（t-wise）只能声称相应阶数的可达元组已覆盖。
- 规则驱动或随机探索只能报告已观测候选、覆盖指标和未解决空间。
- 不同环境若合法空间不同，应分别报告分母，并在共有交集上配对比较。

## 预期产物

1. 带上下文适用条件、SASS 效应图、证据和反例的候选目标代码落地规律集合。
2. 各静态因素及关键交互对目标代码落地、资源分配和调度/控制的影响矩阵。
3. 在固定分析环境、测试空间及投影/结果指纹定义下成立的观测等价类。
4. 可供后续指令选择器、语义验证和成本模型使用的候选数据库，以及显式记录的未解决项集合。

实现这些概念所需的数据关系、原子字段、清单（manifest）、状态轴、成本记录和规模计算均定义在
